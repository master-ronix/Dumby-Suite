# UR-20261011-024 — Non-Blocking Boot Command Deploy

**Identity:** UR-20261011-024 · **Version:** 1.0 · **Date:** 11/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-11 (see the `v5.5.27` entry in `upgradation/change-log.md`).

---

## 1. Summary

With `NODE_ENV=production`, the boot's per-guild command registration (two bulk-overwrite calls per
guild) is rate-limited and took **~2 minutes 13 seconds**, during which the bot did not become ready.
The deploy is now issued **in the background** — after the guilds are registered, so the deployer's
enabled-guild resolver still sees them — and its failure is logged rather than fatal. The gateway
connection is independent of command deployment, so readiness no longer waits on it.

Ordering also changed: guilds are registered **before** the deploy, because the resolver reads the
`guilds` table.

## 3. Acceptance criteria

- **ACC-UR-034-1** — readiness is not blocked by command deployment.
- **ACC-UR-034-2** — a deploy failure is logged and never fatal.
- **ACC-UR-034-3** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 4. Rollout

Ordinary deploy. Commands appear shortly after readiness rather than gating it.

## 5. Risks & open questions

- Commands are briefly absent right after a restart until the background deploy completes. That is
  the intended trade for not blocking readiness for minutes.
- The clear-then-set pair per guild is retained (its tests pin it); it is the rate-limit cost, and
  halving it is a separate change.

## 6. Out of scope

- Reducing the per-guild bulk-overwrite calls.
- Any `_inbox/**` or `archive/**` change.
