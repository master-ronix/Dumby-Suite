# UR-20261012-089 — Twill Accepted Malformed Credentials and Identifiers

**Freeze status:** Executed — 2026-10-15 (see the `v5.5.94` entry in `upgradation/change-log.md`).

---

## 1. The finding

Twill checked that its identifiers were **present** and not that they were **well-formed**. A
registration body could name an application `Dumby Suite`, a guild `Bangwing IN`, a registrar
`master_ronix`, and a bot token `bot-secret` — and every one was stored.

The cost of accepting them was paid later and somewhere else:

- a malformed **bot token** failed at gateway login, as an authentication error naming neither the
  token nor the persona;
- a malformed **application id** failed at the OAuth leg or the command deploy;
- a malformed **guild id** bound a persona to a guild that does not exist, and surfaced as a module
  that never answers;
- a **username** as registrar was recorded as authority and never matched anything, because nothing
  looks registrars up by name.

The registrar point is the sharpest, because it is a *semantic* error rather than a format one: a
username is mutable and not unique across time, so "who authorised this" has no stable answer. A
Discord **user id** is neither mutable nor ambiguous.

## 2. The mechanism

`parsePersonaRegistration` read each field with `str(...)`, which accepts any non-empty string, and
validated only the *presentation* fields (`presenceStatus`, `note`, `accent`) — those were checked
because they were added later, in UR-081. The identifiers, which were there from the start, were never
checked at all.

The surface validated what it had most recently been asked to, and not what it most needed to.

## 3. What changed

**Three shape validators, in the model where the other patterns live** (`persona.ts`):

- `SNOWFLAKE_PATTERN` — Discord's id format: 17-20 decimal digits, anchored. Covers ids minted in 2015
  (17 digits) through current (19) with headroom, and refuses a longer digit run.
- `BOT_TOKEN_PATTERN` — three dot-separated base64url segments. The segment lengths are generous
  because Discord does not publish them; the **structure** is the claim.
- `CLIENT_SECRET_PATTERN` — a single base64url run.

**The associated-application check, which is the substantive one.**
`applicationIdFromBotToken(token)` decodes the token's first segment — Discord mints a bot token with
its application id base64-encoded there — and returns it. Registration compares it against the claimed
`discordApplicationId` and refuses a mismatched pair **naming both ids**. This is what makes "the token
belongs to the application you named" checkable without a network round trip; the ownership proof at
the surface still asks Discord, and this refuses the obvious mismatch before that call.

**The registrar is a user id.** `registrarAuthority` must be a snowflake, at registration and at the
registrar registry's grant route.

**Applied at every write, not only registration** — the binding route and the rebind route validate
their guild id; the credential route validates the token and secret shapes *and* that a rotated token
belongs to that persona's application; the registrar registry validates its authority and its optional
application id (empty remaining the documented "any application" bootstrap value).

Every refusal **names the field and says where the value comes from** — "enable Developer Mode and Copy
Server ID", "from Bot → Reset Token" — because a 400 that says "invalid" is a support ticket.

## 4. Acceptance criteria

- **ACC-UR-089-1** — a snowflake is 17-20 digits; a username or name is refused.
- **ACC-UR-089-2** — a bot token is three dot-separated segments; a malformed one is refused.
- **ACC-UR-089-3** — the application id is recoverable from a token.
- **ACC-UR-089-4** — a token minted for a DIFFERENT application is refused, naming both ids.
- **ACC-UR-089-5** — a client secret is a single base64url run.
- **ACC-UR-089-6** — `registrarAuthority` must be a Discord user id, at registration and at grant.
- **ACC-UR-089-7** — the binding, rebind and credential routes validate their identifiers too.

## 5. Recorded

**"Present" is not "valid", and the two were treated as one.** `str()` answered *is there a value*;
every caller read it as *is this a good value*. The presentation fields were validated because they
were added last, which is a reason, but not the reason the identifiers were not.

**A value with an internal structure can be checked against its sibling.** The bot token carries its
application id. That makes the pair `(botToken, discordApplicationId)` verifiable without trusting
either — and the check is cheap, local, and names both sides when it fails. Looking for that structure
in a credential is worth doing before assuming the only check available is a network call.

**A username is not an identity.** The registrar field was a free string, and free strings record what
was typed rather than who did it. The fix is not a stricter string — it is a different KIND of value.

**Every refusal says where the value comes from.** The operator pasting a token does not need to be told
it is invalid; they need to be told which portal page mints it. The messages name the field, the shape,
and the source.

**The existing tests were the ones that broke, and that is the point.** Ten route tests used
`app-9`/`g1`/`bot-secret` placeholders and had to be rebuilt with real-shaped values. Those fixtures
were the evidence that nothing had ever checked the shapes.
