**Basis:** the operator's four corrections (11/10/2026), **final authority**. `UR-20261011-010`

## 1. The corrections (verbatim, formalised)

1. The module Info says it is disabled, yet it is **still listed** in `/modules`.
2. The command stays **registered/loaded** in the guild; the real flow is ignored. The module's
   **processing must be terminated** when it is disabled — commands restricted from **everyone via
   Discord's per-guild command-integration settings**, then the guild's command registry for that
   module **unregistered via BCCM**.
3. The disabled `hello-world` still has its **dashboard page** registered.
4. The disabled module is **not offered in `/browse`** to install back.

---

## 2. The framework facts (re-read)

- **§17.6** — enabling a module registers its commands per-guild in seconds; **disabling does not
  remove them with the same immediacy**, but the framework **writes a deny override to Discord's
  native per-command permissions for `@everyone` and every configured role**, so the command
  disappears from members' effective access **instantly**; the deregistration goes through the
  change queue.
- **§13.2** — a disabled Standard module's commands leave the guild list and its **event handlers
  stop firing**.
- **§13.7 / §15.3** — the toggle is a state write; dispatch is short-circuited before the handler.
- **§13.4** — `guild_module_states` is the single source of truth for enablement.

---

## 3. Requested changes

- **R1 (2).** On disable, write the **instant deny override** — `PUT
  /applications/{app}/guilds/{guild}/commands/{id}/permissions` denying `@everyone` — for each of the
  module's registered commands (via the `applications.commands.permissions.update` scope). On enable,
  clear it (allow).
- **R2 (2).** Keep the **BCCM** enqueue of the module's commands for the batched Discord
  deregistration (as `UR-20261011-010`).
- **R3 (2).** Gate **event dispatch** by module enablement, so a disabled module's subscriptions stop
  firing (the `EventRouter` skips a handler whose module is disabled for the event's guild).
- **R4 (1).** `/modules` lists only **enabled** modules for the guild (core always; standard unless
  disabled; marketplace only when installed).
- **R5 (3).** The **dashboard** registers a page only for an **enabled** standard module.
- **R6 (4).** `/browse` lists a disabled module as **"Previously installed"** so it can be re-enabled
  (as `UR-20261011-010`; verified here).

## 7. Risks & open questions

- **Fleet-wide jobs/tasks.** A cron task or a BullMQ job is **fleet-wide**, not per-guild (§29.6); a
  per-guild toggle cannot stop another guild's instance of it, so those are **not** terminated by a
  per-guild disable. What the toggle terminates is the module's **commands** (deny override + BCCM +
  dispatch gate) and its **event handlers** (dispatch gate) — its per-guild processing. A true
  fleet-wide teardown is the *unload* path (§13.7) or a global disable, not a guild admin's toggle.
- **Configured roles.** The deny override here writes the `@everyone` deny; the spec also names
  "each configured role" — those follow the same shape and are a follow-on.
