# UR-20261026-099 — CI Enforcement Is Inert

**Identity:** UR-20261026-099 · **Version:** 1.0 · **Date:** 26/10/2026 · **Requester:** operator-directed

**Freeze status:** **Open — raised 2026-10-26.** A new record under its own id; it edits no frozen record.

**Basis.** Every check run on `feature/dev` reports `failure`. None of them is a code failure. The
annotation on both failing jobs reads, verbatim:

> The job was not started because recent account payments have failed or your spending limit needs to
> be increased. Please check the 'Billing & plans' section in your settings

**The boundary is exact.** The newest successful run on `feature/dev` is **2026-10-23T18:57:48Z**
(`docs-gates`, `9a681ce61`). Every run from **2026-10-24T21:17:26Z** (`d15af679d`) onward fails, with
no job started. Over the 300 most recent runs fetched for the branch: 165 success, 105 failure, 30
cancelled — the failures are the tail after 2026-10-23.

## 1. Objective and rationale

Record the blocker so the corpus stops asserting an enforcement it does not have, and state plainly
what may and may not be claimed until it is lifted.

This matters beyond bookkeeping. `UR-20261021-095` was raised on the premise that "a red CI blocks
every deploy — the reason production never advanced past `416864b`", and its first acceptance
criterion is "CI is green on `feature/dev`: every gate in `.github/workflows/ci.yml` passes, and the
flow + integration + docker jobs run". That criterion is not merely unmet — it is **unachievable**
while jobs are refused at start, and the change-log nonetheless records the request as Executed with
`return=met`. The real deploy blocker was never the code.

## 3. Implementation approach

- **Operator action, not a code change.** Clear the failed payment or raise the spending limit under
  **Settings → Billing & plans → Actions**. Nothing in this repository can cause or fix it, and no
  commit will change the outcome.
- **Record the blocker as a carried open item.** Add `OI-8` to the change-log's open items with its
  owner (`operator`), status (`open — blocker`) and the exact annotation, so it is not a silent unknown.
- **Correct the disposition.** `UR-20261021-095`'s disposition row gains the fact that ACC-1 is
  unverifiable until jobs start. The record itself is not edited; its claim is annotated, as history.
- **State the interim verification.** Until jobs start, the only verification available is a local run
  of the same commands CI would run. For the corpus that is
  `for g in scripts/docs/check-*.mjs; do node "$g"; done` from `docs/`, which was run and is
  **30/30 green** at the current head.

## 5. Dependencies and risks

- **Nothing in the repository can resolve this.** It is an account-level billing state. Every other
  item in this corpus that depends on CI is blocked behind it.
- **Risk — unverified code is accumulating on the branch.** No commit since 2026-10-23 has been
  compiled, linted or tested by CI, including the 2026-10-24/25 surfaces/paths/routing code track and
  the runtime-ownership track recorded in `UR-20261026-097` and `UR-20261026-098`. Those changes were
  verified only by reading, by `tsc` against the edited files, and by the corpus gate suite. Their
  unit tests have never executed anywhere.
- **Risk — a green corpus hides the gap.** The corpus gates are structural and they pass locally, so
  the corpus looks healthy while the enforcement that would catch a code regression is inert.
- **Consequence adopted by this record.** No further code change should be pushed to `feature/dev`
  until a workflow run completes. Adding unverifiable commits compounds the risk faster than it
  delivers value.

## 6. Rollback and mitigation

- No force-push, no history rewrite, no protected-branch change is involved.

## 7. Out of scope

- **Replacing GitHub Actions with another CI.** A legitimate option if the billing cannot be resolved,
  but it is an infrastructure decision with its own cost, and this record does not presume it.
- **The application test suite.** It has not been run here for a second, independent reason: this
  sandbox cannot install the pnpm workspace (Node 20.20.2 against a Node ≥ 22 requirement) and its
  bundled `esbuild` panics. Even with CI restored, that limitation stands for this environment.
- **`UR-20261021-095`'s code residuals.** PR-1 … PR-6 are on the branch and were verified by reading;
  this record does not re-open them.
