# UR-20261012-065 — The Module Icons the Core Is Holding

**Freeze status:** PROPOSED — not executed. The blocker is named in §3 and is not a coding problem.

---

## 1. The finding, from inspection

The operator's reading of the architecture is correct, and the code confirms it in one specific place.

**The intended layout exists.** `structure.md` lists `packages/modules/<slug>/assets/` for all eight
first-party modules, and `building-a-module.md` describes it as _"static assets your module serves"_.
Every one of those directories exists — and every one is **empty**.

**The icons are in the core instead.** `apps/main/src/rendering/module-emoji-upload.ts` hardcodes seven
module logos with paths into `apps/main/assets/module-icons/`:

| Emoji name        | Core path                                 |
| ----------------- | ----------------------------------------- |
| `dumby_browse`    | `../../assets/module-icons/browse.png`    |
| `dumby_dashboard` | `../../assets/module-icons/dashboard.png` |
| `dumby_health`    | `../../assets/module-icons/health.png`    |
| `dumby_modules`   | `../../assets/module-icons/modules.png`   |
| `dumby_permit`    | `../../assets/module-icons/permit.png`    |
| `dumby_persona`   | `../../assets/module-icons/persona.png`   |
| `dumby_queue`     | `../../assets/module-icons/queue.png`     |

Each module **already declares the emoji name** in its own manifest (`ui.icon`). So the fact is stated
twice — once by the module that owns the visual, and once by the core — and the core is the authority.

## 2. What the docs say the shape should be

ADR-012 sets the pattern: _"a module declares its accent and banner through its manifest UI fields;
absent a declaration, the default banner and amber apply."_ Framework chrome — dividers, footer rules,
the buffer indicator, the notice marker — stays with the framework.

Applied here:

- **Framework chrome stays in the core.** `dumby_status_online`, `dumby_status_offline`, `dumby_info`,
  `dumby_identity`, `dumby_profile`, `dumby_refresh`, `dumby_home`, `dumby_discover`, `dumby_uninstall`,
  `dumby_module`, `dumby_module_fallback`. These are the framework's own UI, and ADR-012 places them
  with the framework.
- **A module's own logo belongs to the module**, declared in its manifest, read from its own `assets/`.

## 3. The blocker — why this is not executed

**The core cannot locate a module's assets at runtime.** `LoadedModule` (registry.ts) carries a
`manifest` and its declarations, and **no path**; `loader.ts` reads no directory at all; and the
first-party modules reach the process through the seeding/promotion pipeline into a **module volume**,
not from the workspace tree.

So moving the seven PNGs into the modules today would very likely leave the core unable to read them, the
per-asset upload would skip each one (it is non-fatal by design), and every module logo would render as
the fallback — **reintroducing the exact symptom this week has been spent removing.** That packaging
cannot be verified from the repository session, so the change is not shipped on a guess.

## 4. The plan, ready to execute

1. **`LoadedModule.root`** — the module's directory, set where the loader already computes it
   (`swastik-loader.ts` resolves `moduleDir` via `realpathSync`; it currently logs it as `source` and
   discards it).
2. **`ui.iconAsset`** on the manifest UI schema — a module-relative path, mirroring how `ui.banner`
   already carries a module-supplied asset.
3. **Move the seven PNGs** to `packages/modules/<slug>/assets/icon.png` and declare
   `"iconAsset": "assets/icon.png"` in each manifest.
4. **The upload builds its module-icon list from the registry** — name from `ui.icon`, path from
   `ui.root + ui.iconAsset` — keeping only framework chrome hardcoded.

**Precondition to confirm first:** that the deploy packaging carries each module's `assets/` into the
volume. If it does not, that is a packaging change and step 3 waits on it.

## 5. Acceptance criteria

- **ACC-UR-075-1** — no module logo path is hardcoded in the core.
- **ACC-UR-075-2** — a module that declares no `iconAsset` falls back to the framework fallback icon.
- **ACC-UR-075-3** — framework chrome still registers from the core.
- **ACC-UR-075-4** — the core registers exactly the set the registry declares.

## 6. Recorded

**The core was holding a fact the modules already declare.** This is the same class as the four defects
fixed this week — two sources for one fact — with the difference that here the second source is an
_architectural_ one rather than a bug. It is recorded rather than fixed because the fix depends on a
packaging fact that cannot be verified from this session, and shipping it unverified would reproduce the
symptom it is meant to remove.
