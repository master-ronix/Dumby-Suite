# UR-20261012-085 — Registering, Binding or Re-credentialing a Persona Needed a Restart

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.90` entry in `upgradation/change-log.md`).

---

## 1. The finding

The operator registered a persona. `POST /twill/personas/register` returned `201`, the log recorded
`persona-registered`, and the persona list contained her. **She was not online.** The runtime's last
line still read `hosted=0 of 0`, and no `command-deployer` activity followed.

The same was true one step later: binding a module to her changed nothing until a restart, and so did
rotating her credentials. Each of these is a write that succeeds completely and changes nothing the
operator can see — the third, fourth and fifth instance of the shape UR-082 and UR-083 recorded.

## 2. The mechanism

The runtime reads the persona table **once**, at boot, inside `start()`. Everything it needs — who is
active, which modules are bound, which token to use, what presence to apply — is read at that moment
and never again. So any write to any of those facts is invisible until the process restarts:

- **registration** adds a row the runtime has already read past;
- **binding** changes the module list her command set is built from;
- **credential rotation** changes the token she logs in with.

`start()` had no way to host a single persona, and no way to be re-run for one.

## 3. What changed

- **`start(only?)`** takes an optional predicate, so one persona can be (re)started without disturbing
  the rest. `start()` with no argument behaves exactly as before.
- **`PersonaRuntime.reloadPersona(persona)`** — stops her, then starts her again from her **current**
  row. Stopping first prevents a doubled client and clears the stale command set; starting re-reads
  the row, so her bindings, status and token are whatever they are *now*. Her commands are re-deployed
  by the start path, so the clear is transient.
- **It returns the start result, or `undefined`** when the row no longer matches — for example she was
  revoked between the write and the reload. An absent answer, not a fabricated one.
- **The route calls it after a registration, a binding and a credential rotation**, through one shared
  helper. The helper is **non-fatal**: the write already succeeded, and a reload that fails must not
  turn a successful registration into a 500.

## 4. Acceptance criteria

- **ACC-UR-085-1** — `start(only)` hosts only the matching persona.
- **ACC-UR-085-2** — `reloadPersona` closes the old client and logs in again from the current row.
- **ACC-UR-085-3** — `reloadPersona` returns `undefined` for a row that is gone.
- **ACC-UR-085-4** — a retired persona reloads as `not-active` and is not hosted.
- **ACC-UR-085-5** — registration, binding and credential rotation each reload the persona.
- **ACC-UR-085-6** — a failing reload does not fail the operation that triggered it.

## 5. Recorded

**This is the third UR in a row with the same shape, and the first where the fix was written
proactively rather than after a report.** UR-082 found the presence applied at one moment; UR-083 found
the revoke reaching one store of three; this found three operations reading at one moment. The pattern
is now explicit enough to be a rule: **for every operation, name the stores that hold a piece of the
entity and the moments at which each is read — then check the operation reaches all of them.** UR-083
recorded the store half of that; this is the moment half.

**"Documented behaviour" is not a defence when the documentation describes a defect.** Restarting to
pick up a registration was written down, repeated to the operator, and still cost them a cycle every
time. The doc made it *predictable*, not *correct*.

**`stopPersona` made this cheap to add.** The revoke fix gave the runtime a per-entity stop; the reload
is a stop followed by a filtered start. Had the revoke been patched as a one-off — a bare
`client.destroy()` inside the route — there would have been nothing to build on, and this would have
been a third independent mechanism for the same idea.

**Non-fatal by construction.** The reload runs after the write, in its own `try`, and logs its failure.
A registration that succeeded must not be reported as failed because a gateway connection was slow.
