# UR-20261012-036 — Signing Key Custody

**Identity:** UR-20261012-036 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.43` entry in `upgradation/change-log.md`).

---

## 1. Summary

The operator asked why the build-signing keys are configured on the core bot at all, given that
developers author modules independently. Reading the spec answers it — and exposes a real flaw.

**The spec (§15.8, DIAGRAM 15-B).** A developer uploads TypeScript **source**; Swastik builds it and
signs the result: *"Swastik runs the trusted builder and produces the artifact itself; it never accepts
pre-built JavaScript."* One key signs every build because there is exactly one builder. A developer's
identity is a separate credential — a **dev id** (§15.6) — recording *who authored* a build; the
signature records *that the platform built it*. So there are not, and should not be, per-developer
signing keys.

**The flaw.** A verifier only checks signatures, so it needs only the **public** key. The runtime was
handed the **private** key and derived the public one from it — forcing the platform's signing secret
into the bot purely so the bot could discard the private half. The `signing_keys` table is documented
as "a public-key-only registry"; the runtime simply was not reading from it.

## 2. The revision

- `BUILD_SIGNING_PUBLIC_KEY` is added and **preferred**. The runtime can now be given only the public
  half, and the signing secret stays with the builder.
- `resolveSigningPublicKey(privateKey, publicKey)` returns the public `KeyObject`: from the public key
  when set, else derived from the private key (so the builder and any existing deployment keep
  working), else `undefined` — and the caller then leaves the guard disarmed.
- Both registration sites use it, and the guard arms only when a key actually resolved, so an empty
  configuration is an honest "off" rather than a warning.
- The escaped-single-line normalisation from UR-20261012-035 applies to both keys.

## 3. Acceptance criteria

- **ACC-UR-046-1** — the public key wins when both are set (proved with a mismatched private key).
- **ACC-UR-046-2** — the private key still derives the public one when no public key is set.
- **ACC-UR-046-3** — either key may be given in the escaped single-line form.
- **ACC-UR-046-4** — neither set resolves to undefined, arming nothing and warning about nothing.
- **ACC-UR-046-5** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 4. Risks & open questions

- **The builder still needs the private key.** Only the runtime's requirement is removed.
- **Reading the public key from the `signing_keys` registry** rather than from configuration remains a
  further step; configuration was chosen here because it is additive and reversible.
