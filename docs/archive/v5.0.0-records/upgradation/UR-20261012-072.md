# UR-20261012-072 — The Last Two Hooks

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.77` entry in `upgradation/change-log.md`).

---

## 1. The finding

§11.7 declares six lifecycle hooks. UR-20261012-071 added `onEnable` and `onDisable`. **Two remained**,
and the SDK declared neither:

- **`onError`** — *"cleanup on an unrecoverable error."*
- **`onConfigChange`** — *"react to a per-guild config change without a reload."*

Both are one line in the specification, so the work was not writing the declaration — it was finding
an **honest trigger** for each. A hook that is declared and never fires is worse than one that is
absent: it looks like a capability and behaves like a no-op.

## 2. Finding the triggers — and refusing to invent one

**`onConfigChange` has a real trigger, and a narrow one.** The config service already has
`setModuleConfig(guildId, moduleSlug, moduleConfig)` — the one place a *module's* per-guild config is
written. That is exactly the event §11.7 describes, so the hook fires there, with the guild id and the
new config. The service must not know the module registry, so the notifier is **injected by bootstrap**
and the service simply calls it.

**`onError` does not have the trigger the doctrine implies.** The unified modular doctrine specifies
auto-disable at **10 errors in 60 seconds** (globally for Standard, per guild for Marketplace). That
mechanism does not exist in the code. Rather than build an error-threshold tracker as a side effect of
adding a hook — a much larger change with its own design questions — the hook fires at the boundary the
framework **does** have: the point where it gives up on a module and marks it failed. A failing `onLoad`
or a failing `onReady`/`onEnable` is unrecoverable for that module, which is what the hook is for.

When the auto-disable threshold is built, it is the natural second caller. That is recorded, not
guessed at.

## 3. What changed

- `ModuleLifecycle` (the SDK) and `LoadedModule` (the app) declare `onError` and `onConfigChange`.
- The loader calls `onError` at both failure boundaries — `loadAll` and `readyAll` — through one guarded
  helper. A throw from `onError` is logged separately and **does not mask the original failure**: the
  module still reports failed for the reason it actually failed.
- The loader exposes `notifyConfigChange(moduleSlug, guildId, config)`, which is a no-op for an unknown
  module or one without the hook, and catches a throwing hook so a config write never fails because of
  it.
- `GuildConfigService` gained a notifier, attached in bootstrap after the loader exists.

## 4. Acceptance criteria

- **ACC-UR-072-1** — a failing `onLoad` reports the error to the module.
- **ACC-UR-072-2** — a failing `onEnable` reports it too; the module is DISABLED.
- **ACC-UR-072-3** — a throwing `onError` does not mask the original failure.
- **ACC-UR-072-4** — a module without the hook is unaffected.
- **ACC-UR-072-5** — `onConfigChange` receives the guild and the new config.
- **ACC-UR-072-6** — an unknown module, or one without the hook, is a no-op; a throw is caught.
- **ACC-UR-072-7** — `setModuleConfig` notifies; a config write succeeds with no notifier attached.
- **ACC-UR-072-8** — 120 files, 1225 tests, 0 failures; coverage at or above the branch floor.

## 5. Recorded

**A declared-but-uncalled hook is a lie the type system cannot catch.** The declaration is the easy
part; the honesty is in refusing to ship it until a real caller exists. For `onConfigChange` the caller
was already there. For `onError` it was not, and the choice was between building a whole error-threshold
subsystem as a side effect, or wiring the hook to the boundary that genuinely exists and saying so. This
UR takes the second.

**The spec's one-line hooks are load-bearing and under-specified.** "Cleanup on an unrecoverable error"
does not say *which* error. Where a specification leaves that open, the right move is to pick the
narrowest defensible reading, wire it, and record the wider one as future work — not to invent a
mechanism the rest of the system does not have.
