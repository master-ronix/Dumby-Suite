# UR-20261026-101 — The Ledger Covered None of the Faulted Areas

**Identity:** UR-20261026-101 · **Version:** 1.0 · **Date:** 26/10/2026 · **Requester:** operator-directed

**Freeze status:** **Open — raised 2026-10-26.** A new record under its own id; it edits no frozen record.

**Basis.** Two defects, found by auditing this corpus against the eight code findings it had just
closed.

**First.** `status/code-reconciliation.json` reported 28 rows, all `match`, `code-gap: 0`. None of the
28 covered the areas every one of the operator's faults lived in: which profile holds a module, what a
disable does to a command, who may answer a command, and how a refusal is delivered. A ledger that
does not have a row for a behaviour cannot detect that behaviour going wrong — so `28/28 match` was
true and gave no assurance about the parts that were broken.

**Second.** The anchor had not moved. `verified_commit` was `7e8ca739`, and **six commits since it
touched `apps/main` or `packages`**. `check-code-reconciliation` fails on exactly that condition, so
the ledger would have failed its own gate on a full checkout. It did not fail in the sandbox used for
this work, because the anchor commit is not present in a shallow local clone and the gate downgrades
that case to a warning — a blind spot that would have hidden the failure until CI ran. CI cannot run
(`OI-8`), so it would have been hidden twice over.

## 1. Objective and rationale

Make the code-grounding ledger able to detect the class of defect the operator kept hitting, and put
its anchor back in step with the code.

## 3. Implementation approach

- **RT-10** — four rows appended, one per faulted area, each with `doc_claim`, `code_truth`, `code_ref`,
  `verdict: match` and a `resolution` naming the record that established it. The counts block is
  recomputed from the row list rather than hand-edited.
- **RT-11** — `verified_commit` becomes the last commit to touch `apps/main|packages`, and `verified_at`
  is today. `check-side-docs` requires one canonical commit across `GAP_MANIFEST.md`,
  `status/code-reconciliation.json`, `migration/migration-prompt.md` and `README.md`, and requires
  `status/audit-age.json` to name the same commit — so all five move together, which is the convention
  `UR-20261021-094` R1 established.
- **The pre-existing rows are re-anchored, not re-derived.** Their `resolution` strings carried
  `Re-verified against HEAD <sha> — `; the sha is removed and the substance kept. Re-pointing a ledger
  is not the same act as re-verifying 28 rows, and a row must not claim an act that did not happen. The
  ledger's `note` says so explicitly, and says why the re-anchor is sound: the commits since the old
  anchor changed ownership reads, the disable path, dispatch ownership and the refusal notice — areas
  no pre-existing row covered.
- **Why the anchor is safe.** The freshness gate fails when a commit *after* the anchor touches the
  code surfaces. Anchoring at the last such commit makes that set empty until the next code change, and
  the next code change is exactly when the ledger should be re-verified.

## 4. Acceptance criteria and definition of done

- **ACC-UR-20261026-101-1** — the ledger carries a row for each of the four faulted areas, each with a
  `code_ref` that exists.
- **ACC-UR-20261026-101-2** — `counts` equals the row tally, and `total` equals the row count.
- **ACC-UR-20261026-101-3** — one canonical commit is named by `GAP_MANIFEST.md`,
  `status/code-reconciliation.json`, `migration/migration-prompt.md`, `README.md` and
  `status/audit-age.json`.
- **ACC-UR-20261026-101-4** — no commit after the anchor touches `apps/main` or `packages`
  (`git rev-list <anchor>..HEAD -- apps/main packages` is empty).
- **ACC-UR-20261026-101-5** — no `resolution` string claims a per-row re-verification.
- **ACC-UR-20261026-101-6** — the corpus gate suite is **30/30 green** after the change.
- **ACC-UR-20261026-101-7** — `git branch --show-current` prints `feature/dev` before every commit.

## 5. Dependencies and risks

- **Risk — four rows added at once invite a `match` that was not earned.** Each was written from the
  code as changed in `UR-20261026-097`, `-098` and `-100`, and each `code_ref` points at the file that
  holds the behaviour. They were read, not assumed.
- **Risk — the freshness gate cannot be exercised in a shallow clone.** This is the sandbox's
  limitation, not the ledger's: the gate downgrades a missing anchor to a warning. The anchor was
  therefore verified by the equivalent local check (`git rev-list <last-code-commit>..HEAD -- apps/main
  packages` is empty), and that check is what ACC-4 records.
- **Risk — CI cannot confirm any of this.** `OI-8`: no Actions job has started since 2026-10-23.

## 6. Rollback and mitigation

- One atomic commit per concern; `git revert <sha>` restores the previous anchor and drops the four
  rows. Nothing here is consumed by code.
- No force-push, no history rewrite, no protected-branch change is involved.

## 7. Out of scope

- **Re-deriving all 28 pre-existing rows at the new anchor.** They were re-anchored, and the note says
  so. A full re-derivation is a larger audit than this record claims to be.
- **Closing the shallow-clone blind spot in `check-code-reconciliation`.** A real improvement — the
  gate could fail rather than warn when the anchor is absent and the checkout claims to be complete —
  but it is a change to a gate, not to the ledger, and it deserves its own record.
- **`OI-8`, the CI billing block.** Unchanged and owned by the operator.
