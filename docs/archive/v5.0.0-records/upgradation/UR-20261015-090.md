## 1. Summary

The `docs/` corpus is **structurally sound and gate-green at HEAD (27/27)**, but it is **not
anchored to HEAD**, its strongest metadata fields are **empty by policy**, its **side documents
restate stale facts the traced-corpus gates cannot see**, its **version model does not
reconcile**, and its **own remediation requests remain partly unexecuted**. This request asks
for one bounded pass that (a) re-anchors every provenance claim to the shipping HEAD and makes
staleness **gate-detectable**, (b) reconciles the version model, (c) closes the side-document
and placeholder drift, and (d) dispositions the open residuals. It is a **remediation and
re-baseline of the corpus**, not a greenfield build.

**Verified state at HEAD (`feature/dev` @ `6fd4df9d`, 2026-10-15).** 319 files under `docs/`
(267 `.md`, 22 `.json`, 1 `.yaml`, 29 `.mjs`); 249 front-mattered artifacts validated by
`check-frontmatter`; 27 documentation gates present, **27 green**; `status/coverage-ledger.json`
2,246 rows / 0 orphans / 132 targets; `status/code-reconciliation.json` 22 facts, all `match`;
17 capabilities (6 implemented / 1 specified / 10 deferred); 15 normative ADRs; 96 live
`upgradation/UR-*.md` records.

## 2. Motivation & the governing conflict (read first)

The corpus's authority model rests on three claims — *single-sourced*, *gate-verified*, and
*code-grounded*. The first is genuinely enforced. The second is true only **structurally** (the
gates prove internal consistency, not truth, and do not run `tsc`). The third is currently
**false in a reproducible way**: the corpus pins provenance to a commit it does not ship at
(`8355ba4f…`, not HEAD `6fd4df9d…`), and the one gate that could catch it is a **warning**, not
a failure, and is **inert without a git work tree**.

Per the project's own governance — *anything that departs from how a thing is already defined
goes through a formal Upgradation Request first* — these are recorded here as one request. It
**adopts, re-anchors, and supersedes-in-scope** the still-open findings of
`upgradation/UR-20261010-001.md` at the current shipping HEAD and adds the findings a green
gate run cannot see (side-document drift, version-model non-reconciliation, placeholder
sections, and the counts-enforcement shortfall).

## 4. Requested changes (by workstream)

### A. Provenance & anchoring
- **R1 — Re-anchor provenance to one canonical branch and one commit.** Update every provenance
  string in the normative corpus and the side documents to name the canonical shipping branch
  and a **single** current commit SHA (at HEAD: `feature/dev` @ `6fd4df9d…`). Files in scope:
  `status/code-reconciliation.json` (`verified_commit`, `note`, and every row `resolution`),
  `blueprint/structure.md`, `spec/architecture/directory-file-structure.md`, and
  `GAP_MANIFEST.md`.
- **R2 — Make anchor staleness a hard failure, not a warning.** Extend
  `scripts/docs/check-code-reconciliation.mjs` so that, when a git work tree is present, a
  `verified_commit` that is not equal to HEAD **fails** the gate (retaining the shallow-clone
  exemption), and add a `verified_at` timestamp so the corpus records the **age** of its last
  verification. Verify fail-before / pass-after on a deliberately injected stale anchor.

### B. Verification model
- **R3 — Give `review_state` / `last_verified_commit` a real lifecycle or state the policy in
  the schema.** Either run a human review pass that flips the load-bearing normative sections
  (`spec/governance/**`, `spec/request-layer/permission-authorization-engine.md`,
  `spec/modules/module-anatomy-manifest.md`, `contracts/**`) to `review_state: verified` with a
  populated `last_verified_commit`, **or** state as corpus policy — in `docs/README.md` and in
  the `docs/_meta/frontmatter.schema.json` `$comment` — that the corpus is machine-verified only
  and that the two fields are reserved. A field that is always `null` must not be presented as
  evidence.

### C. Side documents & ledgers
- **R4 — Fix the side-document gate count and guard it.** Correct `STATUS.md` and
  `GAP_MANIFEST.md` from **25/25** to the live gate count (read it, do not hard-code it), and
  extend `check-side-docs.mjs` to fail when a side document restates a documentation-gate count
  that disagrees with the number of `scripts/docs/check-*.mjs` files.
- **R5 — Regenerate the directory entry counts from HEAD.** Replace the stale
  1,382-entry / 288-directory / 1,094-file figures in `blueprint/structure.md` and
  `spec/architecture/directory-file-structure.md` with values generated from the canonical
  branch (at HEAD: 1,551 entries, 287 directories, 1,264 files), and add a gate assertion (or a
  `check-side-docs` extension) that recomputes and compares them.
- **R8 — Broaden counts enforcement and disambiguate the UR count.** Extend `check-counts.mjs`
  to cross-check every required key that has a verifiable source (ADR count, contracts,
  bootstrap stages, middleware stages, ranks, tiers, and the live UR glob); and, in
  `upgradation/README.md`, state the 121-vs-live distinction in one line next to the
  `counts.ur_requests` note.

### D. Version model & records
- **R6 — Reconcile the version model and refresh the change-log head.** Bring the
  `upgradation/change-log.md` §2 Master Version Table and its §3 population-status note up to
  the highest recorded track (v5.5.94), update the "Last recorded" head line to the latest dated
  entry, and add one statement (in `docs/README.md` or `docs/manifest.json`) that maps
  `corpus_version` / engine / spec / change-log to a single defined meaning.
- **R7 — Populate or downgrade the placeholder normative sections.** Fill the
  `migration/migration-prompt.md` `<version>` tokens, the "Protocol revision" line, and the
  "CURRENT STATE" block from the live ledger, **or** mark them explicitly non-normative; and
  either populate the change-log §3 early-version bodies (§2 rows for v1.0.0–v4.6.1) or mark
  the section's `status` so an empty body is not read as a completed record.

### E. Residual discharge
- **R9 — Disposition the open residuals.** For each of OI-1…OI-7 and each open migration slice
  (M10, M14, M16, M18), record a disposition (executed / partially executed / deferred with
  reason) in `upgradation/change-log.md` §5 and `migration-ledger.md`, so no residual is a
  silent unknown.
- **R10 — Record the audit's age.** Add a dated "last independent audit" line to
  `docs/README.md` (or a small machine-readable audit-age ledger in the `status/` directory), so
  the corpus states when it was last audited and against which commit — making audit staleness
  visible the same way provenance staleness becomes visible under R2.

## 7. Rollout (trigger-chain discipline)

1. **Gate first** (R2, R4, R5, R8) — so subsequent edits are checked as they land.
2. **Re-anchor** (R1) — the provenance strings and the ledger move as one change.
3. **Records** (R6, R7) — version model, head line, populated sections.
4. **Evidence surfaces** (R3) — review-state lifecycle or the stated policy.
5. **Dispositions** (R9, R10) — record the open residuals and the audit age.
6. **Verify** — re-run the full gate loop; append the `v5.x` entry to
   `upgradation/change-log.md` per the change-log discipline.

## 8. Risks, assumptions & open questions

- **Anchor churn.** Re-anchoring to a moving HEAD invalidates itself as soon as the branch moves;
  R2's fail-on-stale gate is what keeps it honest. Without R2, R1 regresses on the next push.
- **False "verified".** Flipping `review_state` without a real review would manufacture evidence —
  R3 permits a policy statement precisely to avoid that.
- **Self-verification.** The corpus is authored and verified by the same program; the change-log's
  own self-verification caveat applies. This request prefers recorded, reproducible evidence over
  self-declared status.
- **Open question — branch divergence.** `feature/dev` (this corpus's basis) and `main` diverge;
  whether the corpus's canonical shipping branch is `main` or `feature/dev` must be decided and
  recorded (OI-7; also required by `upgradation/UR-20261009-001.md` R3). This request authorises
  no branch merge.
- **Open question — the 24 logged deviations.** Whether they are in scope for the next migration
  or remain a standing deferred tail is an operator decision (R9 records it, does not execute it).
