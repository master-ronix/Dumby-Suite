# UR-20261012-087 — There Was No Way to Restart One Persona

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.92` entry in `upgradation/change-log.md`).

---

## 1. The finding

The operator asked for a command to restart a persona. There was none.

UR-20261012-085 built `PersonaRuntime.reloadPersona` and wired it to three operations — registration,
binding, credential rotation. It was never exposed. So the only way to cycle a persona was to restart
the whole Railway service, which restarts the main bot too and costs a visible blip.

The capability existed in the runtime and had no surface. An operator asking to restart one persona is
not asking for something unreasonable; the management API simply did not answer.

## 2. The mechanism

`reloadPersona` was reachable from exactly three call sites, all inside the route module, all in
response to a write the route had just performed. Nothing external could ask for a reload:

- after a change made **out of band** (a direct row edit, a migration);
- after a **module's commands change** underneath a persona;
- when an operator simply wants her cycled, as a first step in diagnosis.

For those, the only instrument was a process restart.

## 3. What changed

- **`POST /twill/personas/:personaId/reload`** — reloads one persona from her current row: a fresh
  gateway login, her commands re-deployed from her current bindings, her presence re-applied. The
  response is her public view plus a `reload` field carrying what the reload did.
- **An absent result is reported, not hidden.** `reloadPersona` returns `undefined` when her row no
  longer matches — she was revoked between the read and the reload. The route returns that as
  `"reload": null` alongside her view, rather than a bare success.
- **`501` when the runtime is not enabled.** Without `PERSONA_RUNTIME_ENABLED` there is nothing to
  reload, and a `200` that did nothing would be a lie. This is the same rule as the rest of the
  surface: report what happened, not what was asked for.
- **`404` for an unknown persona**, matching every other operation on this surface.

## 4. Acceptance criteria

- **ACC-UR-087-1** — `POST /twill/personas/:id/reload` reloads the named persona.
- **ACC-UR-087-2** — an unknown persona returns `404`.
- **ACC-UR-087-3** — with the runtime disabled it returns `501`, not a `200`.
- **ACC-UR-087-4** — a reload whose row no longer matches reports `reload: null` rather than success.

## 5. Recorded

**A capability with no surface is not a capability.** `reloadPersona` was correct, tested and used
three times by the code that needed it — and the operator still could not restart a persona. Building
the mechanism and not exposing it left the original problem in place, one layer down.

**The three call sites were all writes the route itself had made.** That is a tell: when every caller
of an operation is the same module performing its own follow-up, the operation is probably also a
legitimate standalone action, and nothing is asking for it yet.

**This is the operator's second request in two URs for something that should already have existed.**
UR-085 was "why isn't she online"; this is "how do I restart her". Both were answered by capability the
runtime already had. The gap was never the mechanism — it was the surface, and that is where the work
kept being missing.
