# UR-20261012-038 — The Persona Runtime

**Identity:** UR-20261012-038 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.45` entry in `upgradation/change-log.md`).

---

## 1. Summary

A Twill-registered persona is a separate Discord application. Nothing hosted it: an invited persona
was listed and invitable but never actually ONLINE, which is the gap the operator reported as "the
persona must be online". This record is the host.

## 2. The revision

- **`PersonaRuntime`** — for every **active** persona it opens the persona's sealed bot token, builds a
  registry containing **only the modules bound to that persona**, registers those commands in the
  persona's bound guild, and logs the persona's client in. `stop()` logs them all out.
- **One failure never takes the fleet down.** Each persona is started independently; a failure is
  recorded with its reason and the loop continues. The outcome is in the log message as well as the
  fields.
- **The seams are injected** — token opener, module lookup, registry builder, client factory, command
  deployer — so the whole lifecycle is unit-tested without a gateway.
- **`filterRegistryForModules`** builds a persona's registry with the same tier bookkeeping as the
  main bot's, so a persona's router behaves identically for the modules it owns.
- **Off by default** (`PERSONA_RUNTIME_ENABLED`): each persona costs one gateway connection, which is
  an operator decision rather than a default.

## 3. Scope — what this does and does not do

**Does:** the persona is ONLINE and present in its bound guild, its commands exist there, and it holds
a router over exactly its own modules.

**Does not:** answer its in-message interactive controls. The Renderer's buttons and select menus are
dispatched by the main bot's bootstrap-local `interactionCreate` handler, which is entangled with
~20 bootstrap closures; extracting it blind would risk the main bot's command path, and this sandbox
cannot run the test suite (esbuild deadlocks), so the extraction is deliberately deferred rather than
attempted unverified. A persona therefore answers slash commands once that handler is shared; its
controls are the next step.

## 4. Acceptance criteria

- **ACC-UR-048-1** — an active persona is hosted: commands deployed, then logged in.
- **ACC-UR-048-2** — a non-active persona is skipped without touching its token.
- **ACC-UR-048-3** — one persona's failure does not stop the others.
- **ACC-UR-048-4** — `filterRegistryForModules` keeps exactly the listed modules and their tiers, and
  leaves the source untouched.
- **ACC-UR-048-5** — `stop()` logs out everything, is idempotent, and never throws.
- **ACC-UR-048-6** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 5. Risks & open questions

- **Not validated against a live gateway.** The lifecycle is unit-tested through its seams; enabling
  it in production is the first live test, and the boot log (`persona-runtime-started`,
  `persona-runtime-start-complete`) is what to read.
- **One connection per persona** — a fleet of personas is a fleet of gateways; sharding and rate
  limits become real at scale.
- **The interactive-control path is shared, not extracted** (see §3).
