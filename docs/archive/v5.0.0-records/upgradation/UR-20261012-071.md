# UR-20261012-071 — A Module Can Stop What It Started

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.76` entry in `upgradation/change-log.md`).

---

## 1. The finding

§11.7 declares six lifecycle hooks. The SDK declared **three**:

```
onLoad  onReady  onUnload                      ← what the SDK declared
onLoad  onReady  onEnable  onDisable  onUnload  ← what §11.7 specifies
(onError, onConfigChange also specified)
```

So the framework could tell a module to *initialise* and to *tear down*, but not to **stop what it had
started**. A module that opened a polling loop, a websocket or a scheduled task had nowhere to be told
to close it — the hooks the specification gives it for exactly that did not exist in its contract.

## 2. What the hooks are, and what they are not

The specification is precise about both:

- **`onEnable`** — DISABLED → ENABLED. *"start active processes: beginning a polling loop, establishing
  a voice connection, starting a scheduled task."* If it throws, **the module remains in DISABLED
  state** and the error is logged. Idempotent, ≤ 5 s.
- **`onDisable`** — ENABLED → DISABLED. *"stop active processes: ending a polling loop, disconnecting
  from voice, cancelling scheduled tasks."* If it throws, the error is logged but **the module still
  transitions to DISABLED**. **Always runs before `onUnload`.** Idempotent, ≤ 5 s.

**These are GLOBAL transitions, not per-guild ones, and that distinction is the whole point.** §13.7 is
explicit that toggling a module in a guild "never touches the module's loaded state, DI registrations,
or event subscriptions". A module can be enabled in guild A and disabled in guild B at once, and a
polling loop is process-wide — so firing `onDisable` for one guild would stop a process that other
guilds are still being served by. The per-guild case belongs to the **execution gates**
(UR-20261012-069), which suppress a module's work *for that guild* without touching the module. This UR
deliberately does **not** fire these hooks on a per-guild toggle.

## 3. What changed

- `ModuleLifecycle` (the SDK) and `LoadedModule` (the app) now declare `onEnable` and `onDisable`.
- `readyAll` calls `onEnable` **after** `onReady` succeeds — a freshly loaded module becomes ENABLED, so
  its active processes start once the gateway is up. A throw from either leaves the module DISABLED and
  is reported as a ready-failure; the bot stays live and every other module continues.
- `unloadAll` calls `onDisable` **before** `onUnload`, and catches it **separately** — a module that
  fails to stop cleanly must not be left half-unloaded. `unloadAll` is the shutdown path, so the
  framework's own shutdown now disables every module before unloading it, as §11.6 describes.

## 4. Acceptance criteria

- **ACC-UR-071-1** — `onEnable` runs after `onReady`, and only then.
- **ACC-UR-071-2** — a throwing `onEnable` leaves the module DISABLED and is reported.
- **ACC-UR-071-3** — a module without the hooks is unaffected.
- **ACC-UR-071-4** — `onDisable` runs before `onUnload`.
- **ACC-UR-071-5** — a throwing `onDisable` is logged but the module still unloads.
- **ACC-UR-071-6** — modules are disabled in reverse load order, so dependents stop first.
- **ACC-UR-071-7** — 119 files, 1216 tests, 0 failures; coverage at or above the branch floor.

## 5. Recorded

**A hook the spec gives a module but the contract does not is a capability the module does not have.**
The disable flow of UR-20261012-069 stops the framework's own processing — commands, events, jobs,
tasks — but the framework cannot stop a process it does not own. Only the module can, and only if it is
told. That is what these hooks are for, and their absence was the difference between a framework that
*looks* like it stops a module and one that actually does.

**A known divergence, left standing.** §11.6 describes shutdown disabling modules in **tier order**
(Marketplace, Standard, Core, Admin). `unloadAll` reverses the **load order**, which is topological —
dependents before dependencies, but not tier order. The topological order is arguably the safer one for
teardown, so this is recorded rather than changed without a decision.
