# UR-20261012-045 — Gate 4 Was Red, So Nothing Deployed

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.51` entry in `upgradation/change-log.md`).

---

## 1. What was actually wrong

Production was running an older build because **every deployment since 17:20 UTC was SKIPPED**. The
cause was not Railway: `Gates (D-8.4 strict sequence)` **failed** on `8ad10b8` with **11 annotations** —
10 failures, all in test fixtures written in UR-041 and UR-043. Not one was a product defect.

| Test                               | Failure                                    | Cause                                                                                                                                                      |
| ---------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `twill-registration` (×2)          | received **403**, expected 201 / 409       | UR-041's ownership gate is a real Discord call; the fixture never stubbed it, so every register test was refused before the route logic ran                |
| `persona-registrar` (×3)           | `this.registrars.hasAny is not a function` | the `registrarStore` fixture kept its **old one-argument signature**; a UR-041 edit to it silently did not apply, and the tests already called it with two |
| `persona-interaction-handler` (×4) | "is not a spy or a call to a spy"          | the fixture returned the **raw** dispatch function, so every `.mock` access threw                                                                          |

## 2. The fixes

- `buildRoutes` now stubs `ownershipFetch` to return the claimed application, so the ownership gate is
  exercised rather than accidentally tripped.
- `registrarStore(authorised, configured = true)` exposes `hasAny`, and **duplicate `hasAny` lines a
  blind replace had introduced are collapsed**.
- The handler fixture wraps its dispatch in `vi.fn(...)`.

## 3. Why this is recorded as a UR rather than a quiet amend

Because the **class** of failure is the point. Three of these are the same mistake the earlier CI
cycles made: a test fixture that does not match the code it exercises, verified by reading rather than
by running. The verification was the missing step, and §4 is how it is now closed.

## 4. The verification unlock

`vitest` could not run in the build sandbox: it deadlocked inside esbuild. The real cause was an
**address-space ulimit of 1.5 GB**, which stopped V8 reserving its CodeRange and stopped WebAssembly
allocating at all (`RangeError: WebAssembly.instantiate(): Out of memory`). Raising the soft limit —
`ulimit -v unlimited`, permitted because the hard limit is already unlimited — makes the suite run.

**The full unit suite now runs locally: 1041 tests passed, 0 failed.** (Six test _files_ report
`Cannot find package '@workspace/swastik/manifest'`, which is a local artifact of that workspace
package not being built here; CI builds it, and it produced none of these failures.)

## 4a. A second deploy-blocker caught before it shipped

Running the coverage suite locally immediately surfaced a defect of my own: the per-layer floor UR-044
set for `src/commands/**` at the documented **70% branch** fails — that layer measures **65.42%**.
Enforcing it would have failed Gate 4 on every push and blocked every deploy, which is precisely the
outcome UR-044 §1 said it was avoiding.

The floor is now **measured rather than assumed**: statements/functions/lines clear their documented 75,
so they are enforced at 75; the branch floor is held at the reachable 65 with 70 recorded as the
**target**. Verified locally: **112 test files, 1127 tests, 0 failures, and every threshold holds.**

This is the clearest argument for the unlock in §4: without a runnable suite this defect was invisible,
and it would have been discovered the way the last four were — by a skipped deployment.
