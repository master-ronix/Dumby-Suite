# UR-20261012-058 — The Scope Split, and Answering a DM

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.64` entry in `upgradation/change-log.md`).

---

## 1. The scope split — correcting my own over-correction

The operator's original instruction was that a persona registers _"the exact same guild specific
commands and global commands as main bot"_. That means the same **SPLIT**, not the same payload in both
places. `command-deployer.ts` is the authority:

| Tier                      | Scope                                                                     |
| ------------------------- | ------------------------------------------------------------------------- |
| `core`                    | **global**                                                                |
| `standard`, `marketplace` | **per guild**                                                             |
| `admin`                   | per guild (the framework's operator surface — **excluded for a persona**) |

Each command lands in **exactly one** scope.

I got this wrong twice, in opposite directions:

- **UR-055** wrote the same payload to both routes → every command twice.
- **UR-056** over-corrected to the guild only → a persona had **no global core commands**, so `/health`
  and friends did nothing in a DM or in any guild other than her bound one.

Both are the same mistake: satisfying the instruction mechanically instead of reading the deployer that
already answers it. `splitPersonaPayloads` now derives the split from the registry's own tier, and
`deployPersonaCommands` clears both scopes then registers each half once.

## 2. A direct message gets an answer

A DM invocation **threw before replying**:

```ts
if (interaction.guildId === null) {
  throw new CommandScopeDeniedError(name, "main-bot", "core", null);
}
```

Nothing had been sent, so Discord showed **"The application did not respond"** — which tells the member
nothing. DM use is prohibited by design; the refusal now says so, through a new `replyNotice` (the
existing `editNotice` edits a reply that already exists, and here there is none).

## 3. The emoji upload names its application

`module-emoji-ready` / `-created` / `-failed` now carry `app=<applicationId|main>` **in the message
string**, so a persona's upload can be confirmed from a log viewer that drops structured fields.
