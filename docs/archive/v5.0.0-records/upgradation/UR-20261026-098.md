# UR-20261026-098 — A Private Refusal

**Identity:** UR-20261026-098 · **Version:** 1.0 · **Date:** 26/10/2026 · **Requester:** operator-directed

**Freeze status:** **Open — raised 2026-10-26.** A new record under its own id; it edits no frozen record.

**Basis.** `UR-20261026-097` finding RT-5 made the refusal notice *honest*: it declared the grammar it
was delivered with, so it became a public formal notice carrying the framework accent. That closed the
contradiction the operator reported but not its cause. The operator's actual expectation — stated in
the fault report — was that a refusal is for the member who tried it and should be hidden. This record
delivers that, and supersedes RT-5's interim answer.

## 1. Objective and rationale

Make the module-refusal notice **private**, without giving up the in-place page update that a
component interaction depends on.

The obstacle is structural, not cosmetic. The component registry acknowledges every control with
`deferUpdate` **before** the handler runs — a *public* acknowledgement whose whole purpose is that the
handler can then edit the existing message in place. `editReply` cannot change an existing message's
ephemerality. So a notice that rides the edit is public by construction, and asking for the private
grammar on it produced exactly what the operator saw: no accent, and not hidden.

A follow-up is a **new message**, and a new message can be private. That is the whole of the fix.

## 2. Findings and residuals to resolve

| # | Residual | Sev | Where | Corrective action |
|---|---|---|---|---|
| RT-6 | The refusal notice could not be private: it was delivered by editing a publicly acknowledged message, so it carried the private grammar on a channel-visible card and destroyed the page it replaced | medium | `interactions/core-frame.handlers.ts`, `rendering/core-renderer.ts`, `interactions/interaction-registry.ts`, `bootstrap/bootstrap.ts` | deliver it as a private `followUp`; give the page controls the one guard exception they need to do that; restore `ephemeral: true` on the notice |

## 3. Implementation approach

- **The guard gains one declared exception.** `CoreRenderer.createReadOnlyInteraction` accepts
  `{ allowFollowUp }`. `reply` and `showModal` stay blocked — a second initial response is rejected by
  Discord and a modal is not a message — and `followUp` is blocked unless the caller opts in. The
  registry passes `handler.allowFollowUp` through, so the exception is per-control and visible in the
  handler's declaration rather than implied by its behaviour.
- **The page controls declare it.** The `ACT_PREFIX` handler sets `allowFollowUp: true`. It is the one
  control whose answer has no other honest route.
- **The refusal is sent first, then the page is refreshed.** `interaction.followUp?.(payload)` runs
  before `dispatch(interaction, 'browse')`, and the refresh is wrapped so a failure there cannot cost
  the member their notice. The order matters: this path once sent the refusal *after* the refresh and
  a failing refresh swallowed it, so the member saw nothing at all. Sending first makes the notice the
  part that cannot be lost.
- **The notice declares the private grammar again.** `ephemeral: true` is correct once the message is
  genuinely private, so RT-5's `ephemeral: false` is superseded.
- **A `logger` reaches the frame handlers.** The refresh failure is logged, not swallowed, so an
  operator can see it. `CoreFrameHandlerDeps` gains an optional `logger`, wired from `bootstrap`.

## 4. Acceptance criteria and definition of done

- **ACC-UR-20261026-098-1** — the refusal notice declares `ephemeral: true` and is delivered with
  `followUp`, never with `editReply`.
- **ACC-UR-20261026-098-2** — `createReadOnlyInteraction` blocks `reply`, `followUp` and `showModal`
  by default, and permits `followUp` only when `allowFollowUp` is set.
- **ACC-UR-20261026-098-3** — the registry passes each handler's `allowFollowUp` to the guard.
- **ACC-UR-20261026-098-4** — the page controls declare `allowFollowUp: true`.
- **ACC-UR-20261026-098-5** — the browse page is still refreshed after a refusal, and a refresh failure
  is logged rather than thrown.
- **ACC-UR-20261026-098-6** — the corpus gate suite is **30/30 green** after the change.
- **ACC-UR-20261026-098-7** — `git branch --show-current` prints `feature/dev` before every commit.

## 5. Dependencies and risks

- **Depends on** `deferUpdate` remaining the acknowledgement for the page controls. If a control ever
  moves to `ack: 'ephemeral'`, the whole interaction becomes private and the page stops editing in
  place — a different design, and not this one.
- **Risk — `followUp` after `deferUpdate` must be accepted by Discord.** It is a follow-up on an
  already-acknowledged component interaction, which Discord supports, but this was **not** exercised
  against the live API in this sandbox. It is the one part of this change that only a real click can
  confirm.
- **Risk — the exception widens a guard.** `allowFollowUp` reopens one exit that Appendix C #20 closed.
  It is opt-in per handler, it is asserted by a test in both directions, and `reply`/`showModal` stay
  shut — but a future handler could abuse it, so the flag is documented at the contract.
- **Risk — the application toolchain was not run here.** No pnpm workspace install is possible (Node
  20.20.2 against a Node ≥ 22 requirement) and the bundled `esbuild` panics in this sandbox, so the
  new and changed unit tests were NOT executed locally. `tsc` was run over all four edited sources and
  reported no error attributable to this change; CI is the verification.

## 6. Rollback and mitigation

- One atomic commit; revert it with `git revert <sha>`. The interim behaviour from RT-5 (a public
  notice with the accent) returns intact, and it is coherent on its own.
- No data is written by any part of this change. Every edit is to how an existing message is delivered.
- No force-push, no history rewrite, no protected-branch change is involved.

## 7. Out of scope

- **Making the whole page interaction private.** `ack: 'ephemeral'` on the page controls would make
  every response private and stop the page editing in place. This record deliberately keeps the page
  public and the refusal private.
- **The BCCM push cadence.** Still a separate decision about Discord's 200-per-day guild-command
  creation limit; unchanged by this record.
- **`/hello` answering on the main bot while a persona holds it.** Intended, documented at
  `commands/command-router.ts`, and untouched.
