# UR-20261011-019 — Self-Describing Warnings

**Identity:** UR-20261011-019 · **Version:** 1.0 · **Date:** 11/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-11 (see the `v5.5.20` entry in `upgradation/change-log.md`).

---

## 1. Summary

Three boot-time signals — `discord-client-error`, `build-signing-key-invalid` and
`module-provenance-unverified` — carried their detail only in the log record's **structured fields**,
which the operator's log viewer drops. The result was a recurring `discord-client-error` with no
visible cause, and a signing-key warning whose reason was invisible.

The repo already solves this for `command-execution-error` (`command-router.ts`): the message string
carries the text directly. This UR applies that same pattern to the three signals.

## 2. The fixes

- **`discord-client-error` / `discord-client-warn`** (`discord/client-builder.ts`) — the message now
  reads `discord-client-error: <err>` / `discord-client-warn: <msg>`.
- **`build-signing-key-invalid`** (`bootstrap.ts`, both arming sites) — the message now carries the
  `createPublicKey` error plus the remedy: *BUILD_SIGNING_PRIVATE_KEY must be a single-line PEM with
  escaped newlines*.
- **`module-provenance-unverified`** (`module-system/swastik-loader.ts`) — the message now carries its
  `reason`.

No behaviour changes: the structured fields are retained alongside the message text.

## 4. Acceptance criteria

- **ACC-UR-029-1** — a Discord client error is readable from the message string alone.

- **ACC-UR-029-3** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 5. Rollout

Ordinary deploy. No configuration change is implied — the signing-key remedy is the operator's to apply.

## 6. Risks & open questions

- The `discord-client-error` cause is still unknown; this change only makes it visible. Diagnosing it
  needs the next deploy's log.
- The signing-key remedy remains an operator action (a valid single-line PEM), not a code fix.
