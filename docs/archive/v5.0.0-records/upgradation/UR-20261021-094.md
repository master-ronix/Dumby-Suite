## 1. Objective and rationale

Re-ground the documentation corpus at the current `feature/dev` tip so that its three stated
guarantees — *single-sourced*, *gate-verified*, and **code-grounded** — are true again, and so that
the code track that landed after the last reconciliation (UR-20261019-101 … UR-20261019-104) is
recorded, reconciled, and enforced.

The corpus is designed to catch exactly this class of divergence: *where the specification and the
running code diverge, the divergence is recorded in `status/code-reconciliation.json` — never smoothed
over*. The divergence exists today; the ledger that should record it is anchored 27 commits behind
HEAD, two of its rows now assert a contract the code contradicts, and the guard that would prove
freshness never fires in CI because the docs-gates workflow checks out shallow. This request is a
remediation and re-baseline of the corpus, not a greenfield build and not a change to the
specification's intent.

## 5. Dependencies and risks

- **Depends on the code track already being landed.** UR-20261019-101 … UR-20261019-104 are on
  `feature/dev`; this pass records and reconciles them, and changes no code.
- **Risk — re-anchoring to a commit that then advances.** A later code commit re-opens freshness; that
  is the correct behaviour (a code change invalidates a code-grounding claim). Docs-only commits after
  re-anchoring do not.
- **Risk — the app toolchain is not run here.** This pass cannot run `tsc` / `vitest` / the integration
  suite (they need a full pnpm workspace and live Postgres/Redis). The docs-side changes are verified
  by the gate suite only; the application gates remain CI's job and are reported as not-run, never as
  green.
- **Risk — a normative spec edit.** R3 changes body prose, not a heading or a normative rule id, so the
  coverage ledger and the ledger-content gate are unaffected; it is verified by the gate suite.
