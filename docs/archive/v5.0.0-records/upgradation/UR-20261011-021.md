# UR-20261011-021 — BCCM Put-Failure Observability & Test Correction

## 1. Summary

Two corrections after the first real (non-dry-run) BCCM push and the first CI run of UR-020:

- **`bccm-batch-put-failed` carried no cause.** With `BCCM_BATCH_PUSH_DRY_RUN=false`, the batch push
  logged `bccm-batch-put-failed` with `sent=0` and nothing else — the error text sat only in the
  record's structured `error` field, which the operator's log viewer drops. The fix is the same
  `command-execution-error` pattern UR-019 used: the message string now carries the error text (which
  for a Discord API error includes the HTTP status and code) and names the status when present.
- **Two UR-020 tests asserted the wrong thing.** `refreshDue`'s tests set `refreshLeadMs: 1000` while
  their fixtures expired in 2 seconds (`expiresIn: 2` → 2000 ms), so `2000 > 1000` and the loop
  correctly skipped them — the service was right, the test was wrong. The lead is now `1_000_000` ms,
  so the 2-second fixtures count as near-expiry and the 7-day fixture does not.

## 5. Risks & open questions

- The **cause** of the live `bccm-batch-put-failed` is still unknown; this change only makes it
  visible. The report's guesses (an invalid command payload, a permissions problem, a rate limit) can
  be confirmed from the next occurrence. Until then, `BCCM_BATCH_PUSH_DRY_RUN=true` is a safe pause.
