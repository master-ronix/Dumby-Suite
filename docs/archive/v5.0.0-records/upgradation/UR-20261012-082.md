# UR-20261012-082 — A Presence Set Through Twill Did Not Reach the Running Persona

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.87` entry in `upgradation/change-log.md`).

---

## 1. The finding

UR-20261012-081 added a persona's presence — `presenceStatus`, `note` — and applied it at login.
It was applied **only** at login.

`persona-runtime` calls `client.setPresence` inside the start loop, once per persona, at boot. Nothing
re-applied it afterwards. So a `PATCH /twill/personas/:id` that changed the presence wrote the column
correctly and changed **nothing** in Discord until the next restart.

The operator's own requirement is that the status is the bot's status "on profile". A field that only
takes effect at the next restart is, from the operator's seat, a field that does nothing — they set it,
look at Discord, see no change, and conclude the feature is broken. The column was honest; the
behaviour was not.

This is the same class of defect UR-081 recorded and then committed one instance of: **a stored value
that is read at exactly one moment is indistinguishable from a value that is never read, until that
moment comes.** UR-081's presence was read at boot; that is one moment, and it is not the moment the
operator sets it.

## 2. The mechanism

- `PersonaRuntime.start()` applies the presence after `login()` — correct, and the only call site.
- `updatePersona` writes the column and returns. It has no reach into a running client, and the
  runtime's `clients` map is private.
- The route is the composition point: it holds both the service and (now) a hook to the runtime.

## 3. What changed

- **`PersonaRuntime.applyPresence(personaId, presence)`** — a public method that finds the persona's
  running client and applies the presence to it, non-fatally, exactly as at boot. It returns
  `true` when applied and `false` when the persona is not currently hosted (or its client has no
  presence port), so a caller can tell "applied" from "there was nothing to apply it to" rather than
  assuming success.
- **The PATCH route applies it.** When an update touches `presenceStatus` or `note`, the route calls
  the hook after the write succeeds. Two cases are logged distinctly rather than silently:
  - the persona has no presence configured → left as-is, and said so;
  - the persona is not currently hosted → the change lands at the next restart, and said so.
- **Bootstrap wires the hook late-bound.** The persona runtime is constructed inside a conditional
  block, while the Twill surface is built later in the same function; a function-scope reference is
  assigned when the runtime is constructed, and the hook resolves through it.

## 4. Acceptance criteria

- **ACC-UR-082-1** — the configured presence is applied at login.
- **ACC-UR-082-2** — an update re-applies the presence to the RUNNING client.
- **ACC-UR-082-3** — `applyPresence` returns `false` when the persona is not hosted.
- **ACC-UR-082-4** — a client without a presence port is reported as not applied, not as success.

## 5. Recorded

**A write that reaches the database is not a write that reaches the world.** The presence column was
correct and the operator's experience was unchanged. The test that would have caught it is not "does
the column hold the value" but "does the running thing behave differently" — and only the second is
what was asked for.

**This is the second instance in two URs of the same shape, which is why it is recorded rather than
just fixed.** UR-081 wrote the presence and applied it at one moment; this found that the moment was
the wrong one. The general form: for every value that is *applied* rather than merely *stored*, ask
which moments read it, and check that the moment the operator changes it is among them.

**Returning a boolean rather than nothing is the point.** `applyPresence` cannot succeed when the
persona is not hosted — that is not an error, but it is also not success, and a `void` return would
have let the route log a confident line about a change that did not happen.
