# UR-20261012-050 — `commands=0` Was The Only Signal

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.56` entry in `upgradation/change-log.md`).

---

## 1. The report

The first live persona came online but registered **no commands at all** on its bound server.

## 2. What the code says

The audit cleared every candidate defect, which is the useful part of this record:

| Checked                             | Result                                                                                                                                                                          |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `guild_persona_bindings.moduleSlug` | **Exists.** Migration `…000034` drops and recreates the table with `moduleSlug` and a composite primary key `(guildId, moduleSlug)`. The earlier `…000021` shape is superseded. |
| `bind()` / `listForPersona()`       | Correct: conflict target `(guildId, moduleSlug)`, read filtered by `personaId`.                                                                                                 |
| `filterRegistryForModules`          | Correct: matches `def.moduleId` against the bound slugs and carries the tier.                                                                                                   |
| What `moduleId` is                  | `mod.manifest.name` — so the slug an operator binds (`hello-world`) is the same key the registry uses.                                                                          |
| `toApiPayloads()`                   | Correct: `all().map(c => c.data)`, and every `defineCommand` carries a `description`.                                                                                           |

So nothing was broken. **A persona deploys commands for its bound modules and nothing else** — core
modules stay with the main bot — and the deploy **returns early on an empty payload**:

```ts
const body = registry.toApiPayloads();
if (body.length === 0) return 0; // no bindings ⇒ nothing to send ⇒ no request at all
```

That early return is correct behaviour, and it is also why the symptom was silent: the only signal was
`persona-runtime-started … commands=0`, which cannot distinguish **"nothing is bound"** from **"a bound
slug matches no registered module"**. The second is the quiet one — a binding for a slug that is not a
module id contributes nothing and says nothing.

## 3. The fix

The runtime now **reports which case it is**, in the message (the operator's log viewer drops structured
fields):

- `persona-no-modules-bound id=… — it will come online with NO commands; bind a module and restart`
- `persona-bound-module-unregistered id=… modules=<slugs> — bound but contributing no commands`

And `persona-runtime-started` now carries **both** counts, so the line alone is diagnostic:

```
persona-runtime-started id=… guild=… bound=2 commands=7
```

## 4. Also recorded: a persona never registers GLOBAL commands

By design, and worth stating because the report asked for them. A persona is single-server-bound, so it
registers **guild commands in its bound guild only** (`Routes.applicationGuildCommands`). "No global
commands" is not a defect and never will be.

## 5. Operator note: the deploy happens at boot, and it needs the application in the guild

Two ordering facts that follow from the same code:

- The command deploy runs **at boot**. A binding added afterwards needs a restart before it takes effect.
- The deploy is a guild-command `PUT`, and Discord refuses that for a guild the application is not in.
  If it is refused, `deployCommands` throws, the runtime catches it, and the persona is reported
  `persona-runtime-failed` — **offline**, not command-less. So a persona that is _online with zero
  commands_ is an empty-registry case, and a persona that is _absent_ is more likely a failed deploy.

**The order that works: invite the persona first, then bind a module, then restart.**
