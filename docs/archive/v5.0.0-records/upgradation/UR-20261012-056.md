# UR-20261012-056 — Register Once

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.62` entry in `upgradation/change-log.md`).

---

## 1. What I got wrong in UR-055

UR-055 PUT the **same payload** to the global route and the guild route:

```ts
await put(`/applications/${applicationId}/commands`, payloads);
await put(
  `/applications/${applicationId}/guilds/${guildId}/commands`,
  payloads,
);
```

That registers **every command twice**. Discord then lists each one as both a global command and a
this-server command — the operator saw exactly that.

## 2. What the main bot actually does

`command-deployer.ts` **clears both scopes, then registers each command in exactly ONE scope**:

- **Development** — clear the global set, clear the guild set, then register **every** tier to the
  development guild.
- **Production** — clear the global set, register **core** globally, then for each guild clear that
  guild's set and register that guild's own commands.

Never both. That is why the main bot never shows a duplicate.

## 3. The fix

A persona is bound to one guild, so its case **is** the development case: clear both scopes, register
everything to the bound guild.

```ts
await put(`/applications/${applicationId}/commands`, []);
await put(`/applications/${applicationId}/guilds/${guildId}/commands`, []);
await put(
  `/applications/${applicationId}/guilds/${guildId}/commands`,
  payloads,
);
```

The clear is what retires a stale set; registering once is what prevents the duplicate.

- **ACC-UR-066-2** — the payload reaches **exactly one** registration route.
- **ACC-UR-066-3** — an empty payload still clears both scopes.

## 5. Recorded

**UR-055 fixed the right problem with the wrong mechanism.** The operator's model — "register the same
set the main bot does" — was correct, and I satisfied it by writing the payload to every scope instead
of reading how the main bot decides which scope a command belongs to. The main bot already answered
this question; I did not go and read it.
