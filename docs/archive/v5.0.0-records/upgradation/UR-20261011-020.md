## 1. The flow Discord requires, and whether refresh tokens rotate

- **Flow.** Discord's *Edit Application Command Permissions* endpoint — the guild's Server Settings →
  Integrations permissions — accepts only a **user** Bearer token carrying
  `applications.commands.permissions.update`, from a user with **Manage Server** and **Manage Roles**
  in that guild; a bot token is rejected. Of the three OAuth2 grants, only the **authorization-code
  grant** yields both an access token and a refresh token from a user. The **implicit grant** returns
  an access token but **no** refresh token, and the **client-credentials grant** is app-level, with no
  user to satisfy the Manage Server requirement. So the durable flow is the **authorization-code
  grant**.
- **Rotation.** Discord's refresh response returns a fresh `access_token` **and a `refresh_token`**.
  The safe behaviour — and the one implemented here — is to **persist whatever the refresh returns**
  and never reuse a superseded refresh token; if Discord rotates, reusing the old one is refused, and
  storing the latest is correct either way. Revoking any one token for an authorization invalidates
  the whole set.

## 2. What this adds

The dashboard's OAuth2 client (§19.7) already performed the authorization-code exchange but had **no
callback**, stored nothing, and requested only `identify`/`guilds`. This UR completes the flow:

- **`guild_command_permission_tokens`** — one row per guild, holding the authorizing user, the token
  expiry, a status, and the **ids of two sealed credentials** (access and refresh). The token *values*
  are never stored in the clear; they are sealed with the same envelope root key the credentials
  service uses (`ENCRYPTION_ROOT_KEY`), so a database dump alone yields no usable token.
- **`/auth/callback`** — validates the CSRF `state` cookie, exchanges the code, verifies the user can
  **Manage the guild** via `/users/@me/guilds`, then stores the sealed token set.
- **`/dashboard`** — a page carrying the **"Authorize Dumby"** button and the connection status.
- **Automatic refresh** — a scheduled task (`command-permission-token-refresh`, every 6 hours) refreshes
  any active token within 24 hours of expiry and stores the rotated refresh token. A `400`/`401`
  refusal (`OAuth2RefreshError`) marks the guild **revoked** and logs a message naming the remedy
  ("re-authorize from the dashboard").
- **Resolution with fallback.** The command-permissions write prefers the stored per-guild token, then
  the operator's static `DISCORD_COMMAND_PERMISSIONS_TOKEN`, and absent both keeps the current
  behaviour — the state write plus the batched BCCM deregistration.

## 4. Acceptance criteria

- **ACC-UR-030-1** — the dashboard's button authorizes and stores a sealed token set.
- **ACC-UR-030-2** — a near-expiry token refreshes automatically and the rotated refresh token is stored.
- **ACC-UR-030-3** — a revoked/expired token is surfaced as such, with a re-authorize message.
- **ACC-UR-030-4** — with no stored token the command-permissions write uses the env token, else keeps
  the current behaviour.
- **ACC-UR-030-5** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 5. Rollout

1. Set `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`, `OAUTH_REDIRECT_URI` on the Railway service.
2. Open `/dashboard` and press **Authorize Dumby** once.
3. `DISCORD_COMMAND_PERMISSIONS_TOKEN` remains a valid fallback but is no longer needed.

## 6. Risks & open questions

- The dashboard is not itself authenticated; it exposes only the status and the authorize redirect, and
  the callback verifies Manage Server, so authorization cannot be granted without the guild permission.
- A revoked token stops the instant hide but never blocks the state write or the BCCM deregistration.

## 7. Out of scope

- Any `_inbox/**` or `archive/**` change.
