# ADR-011: Persona Creation Surface — the Twixter Registration API

**Status:** Accepted — 18/09/2026
**Deciders:** Dumby Core Engineering — Quixotic Mnemonics
**Supersedes:** The MDIS-only persona-creation wording in the interface reference as previously stated.
**Governing sections:** blueprint.md 5.0.0 §35, §22.3 · interface.md 5.0.0 (persona pages)

## Context

The interface documentation worded persona creation as an MDIS concern: a reader would
conclude that a guild administrator creates a persona through the persona page in the
dashboard surface. The actual creation surface in the v5.0 design is the Twixter
registration API — consistent with the persona model itself, in which the administrator
supplies their own bot token and application in a bring-your-own-identity registration,
Dumby hosts the resulting instance, and the persona binds to exactly one server. An MDIS
page cannot be the creation surface for a credential the guild administrator holds, and
documentation that implies otherwise misroutes users and misdescribes the system.

The competing options were:

1. Keep the MDIS-only wording and treat registration as an implementation detail.
2. Document the Twixter registration API as the creation surface, with MDIS pages
   cross-linking it.

## Decision

The **Twixter registration API is the persona-creation surface.** Registration — supplying
the bot token/application and creating the persona binding — happens through the
registration API. MDIS persona pages do not create personas; they **cross-link** the
registration API so a reader on a persona page can reach the real creation surface in one
step. The MDIS-only wording is superseded wherever it appears.

## Consequences

- **interface.md** persona pages cross-link the Twixter registration API and no longer
  imply in-page creation; the persona-creation open question closes against this ADR.
- **Guild administrators** follow one documented path: register through the API, then
  manage the persona through MDIS pages once the binding exists.
- **The single-server invariant is stated at the creation surface:** one persona = one
  server, enforced at registration and at dispatch ("occupied by another persona"
  rejection), not by later reconciliation.
- **concept.md and master-prompt.md** describe Twixter consistently with this surface —
  registration API for creation, MDIS for management and display.
- **Invariant:** exactly one creation surface for personas; any second surface requires a
  superseding ADR.
