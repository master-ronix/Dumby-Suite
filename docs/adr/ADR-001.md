# ADR-001: Ban on Classic Embeds — All Presentation Is Renderer-Issued Components v2

**Status:** Accepted — 18/09/2026
**Deciders:** Dumby Core Engineering — Quixotic Mnemonics
**Supersedes:** The 4.5.1 SDUI compromise (the SDUI scope decision recorded as current in documentation.md through v4.5.1), which permitted modules to construct their own classic embeds.
**Governing sections:** blueprint.md 5.0.0 §4, §17, §20 · directive.md 5.0.0 (ban registry) · interface.md 5.0.0

## Context

The 4.5.1 SDUI compromise left presentation split: the server drove UI structure, but
modules could still construct classic `EmbedBuilder` / `MessageEmbed` payloads for their own
surfaces. The v5.0 program introduces the core Renderer — a static Components v2 grammar
(frames, dividers, title/subtitle, footer) with dynamic slots (accent, banner, module
identity, content) and Modes D/M/C — and renderer-only authoring, under which module
authors declare command schemas and the renderer derives presentation, components, and
flows.

Under that model, classic embeds in module code are not a harmless legacy: they fragment
the surface grammar, duplicate presentation logic across every module, bypass the buffer
embed and the formal notice frame (which compose with the edit-in-place navigation
invariant), and contradict the "one operational surface" principle. The prefix-command ban
already demonstrated the pattern this program trusts: a ban is real only when it is
enforced at multiple layers, so a compromise that survives in module code quietly
re-creates the drift it was meant to remove.

The competing options were:

1. Keep the SDUI compromise and document embeds as a sanctioned secondary channel.
2. Permit embeds alongside the Renderer with per-module opt-in.
3. Ban classic embeds outright, enforced the same way the prefix-command ban is enforced.

## Decision

Classic `EmbedBuilder` / `MessageEmbed` construction is banned from module code. All
presentation on every surface is renderer-issued Components v2. The ban is enforced through
four enforcement layers mirroring the prefix-command ban, recorded in the directive.md ban
registry with a coverage audit that extends to the new ingestion surfaces (GitHub triggers,
TypeScript compilation, the renderer pipeline). A migration window runs before enforcement
activates; enforcement then fails closed at the designated layers.

## Consequences

- **Module authors** must migrate imperative payload construction to declared command
  schemas before the migration window closes; the renderer then owns frames, slots, and
  flows on their behalf.
- **interface.md** removes embed patterns from component guidance and documents the
  Components v2-only rule; documentation.md carries a superseded-decision marker pointing
  at this reversal.
- **directive.md** records the ban, its four enforcement layers, and the coverage audit in
  the extended ban registry.
- **Maintainers** verify the ban under adversarial testing: standard embeds must fail
  closed at designated layers, exactly as prefix simulation, DM dispatch, precompiled
  artifacts, and cross-module imports do.
- **Invariant:** no module may render anything the Renderer did not issue; the buffer embed
  and the formal notice frame (reason codes + trace correlation ID) are the only
  interaction-opening surfaces, and both belong to the Renderer.
- Status badges restating Components v2 implementation state are re-audited at phase exits
  so the docs never claim enforcement that has not landed.
