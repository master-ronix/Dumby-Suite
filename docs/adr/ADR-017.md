# ADR-017: Identity Is Issued Systematically, by the Services That Own It

**Status:** Accepted — 08/10/2026
**Deciders:** Dumby Core Engineering — Quixotic Mnemonics
**Supersedes:** — (refines ADR-016 by replacing ad-hoc id assignment with systematic issuance).
**Governing sections:** the developer registration (§15.6) · the secured upload pipeline (§15.8) · the credentials service (§22.8)

## Context

ADR-016 made `devId` and `buildId` numbers, but they were assigned with a `max()+1` query inside the request handler. That is a race — two concurrent registrations read the same maximum — and it is not an issuance system: the id is not produced by the service that owns identity, and nothing coordinates the two services that issue ids.

## Decision

Identity is **issued systematically** by the service that owns it, from one shared, persisted, atomic sequence.

- A single **identity issuer** allocates every identity number from the `identity_sequences` table — one row per kind, incremented in a single atomic statement. Two processes issuing at the same instant receive two different numbers; a restart never reissues.
- **Who issues what.** The **Credentials Service** issues the developer number (§15.6) and the credential handle (§22.8). **Swastik, the deployment service**, issues the build number (§15.8) and the license handle. Swastik mints no developer identity and no credential — it asks the Credentials Service and records what it is given.
- **Coordination.** Both services draw the same shared sequence table, so build issuance is coordinated with credential issuance rather than independent of it.

This replaces the `max()+1` assignment entirely; a random identifier is no longer used for any identity that must be unique.
