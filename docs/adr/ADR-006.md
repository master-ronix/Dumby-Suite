# ADR-006: Reload Automation Boundary — Diff-Based Updates, Human-Gated First Promotion

**Status:** Accepted — 18/09/2026
**Deciders:** Dumby Core Engineering — Quixotic Mnemonics
**Supersedes:** None — records and restates the automation boundary previously left implicit across blueprint §15.4/§15.9.
**Governing sections:** blueprint.md 5.0.0 §15.4, §15.8, §15.9, §15.10, §13.7, §33.2, §29

## Context

The v5.0 program automates the deployment loop end-to-end: push → Swastik deployment →
promotion → reload → health verification. Automation of that loop risks blurring the one
boundary the trust model depends on — the human review that stands between unproven code
and a live volume. Review every deployment and the loop's zero-operator developer story
collapses; approve every deployment and first-contact code reaches production without a
human ever seeing it. The previous prose left this boundary implicit, which is how each
implementer could resolve it differently and re-create the drift this program exists to
eliminate.

The competing options were:

1. Human gate on every deployment, first or otherwise.
2. Full automation: any validated build promotes and reloads.
3. Split the boundary by kind of change: first contact is human, subsequent updates are
   automated under verification.

## Decision

The boundary is split by kind of change. **First promotion of any module is human-gated**:
a person reviews and approves before that module first reaches a live volume. **Module
updates are auto-approved on a diff basis**: subsequent deployments of an already-promoted
module proceed without a human when the diff against the currently-live version passes
validation. Every promotion — first or update — then follows the same verified loop:
promotion → reload signal → verified health-check → automatic rollback on failure. No path
bypasses the gate.

## Consequences

- **Operators** keep exactly one review obligation per module — its first promotion — and
  can see, per deployment, whether it was human-gated or diff-approved, and against what
  diff.
- **The reload loop is closed and safe**: reload signals are consumed bot-side, the swap
  runs under lock with a selftest gate, health-checks verify the module actually serves,
  and failure rolls back to the prior live version without operator intervention.
- **Audit rows** record the decision path — human approval or diff-based auto-approval —
  so the automation boundary is inspectable after the fact.
- **Maintainers** treat the boundary as an invariant: no new automated approval path may be
  added without a superseding ADR, and the "no gate bypass" rule covers CI triggers,
  repository bindings, and any future ingestion surface.
- **Invariant:** unreviewed code never reaches a live volume for its first promotion;
  reviewed code never requires re-review to ship an update that passes diff validation.
