# ADR-003: Envelope Encryption Scoped to In-Process-Readable Credentials

**Status:** Accepted — 18/09/2026
**Deciders:** Dumby Core Engineering — Quixotic Mnemonics
**Supersedes:** None — amends the Argon2id-only at-rest posture recorded at blueprint §32.7; the Argon2id rule itself stands unchanged.
**Governing sections:** blueprint.md 5.0.0 §32.7, §32.1, §22.8, §35, §16, §23, §27, §41

## Context

The 4.x line states a single at-rest rule: Argon2id one-way hashing for secrets. That rule
is correct for anything the system only ever needs to *verify* — operator passwords,
developer tokens after the devId-hashing corrections. But a subset of stored values must be
*read back in process*: credentials the system itself must present or use, such as CLAI
keypairs, service-to-service credentials, and signing keys. One-way hashing cannot serve
those, so the honest choice is either plaintext-with-filesystem-permissions (indefensible
for a system with a five-vector leak model) or a second, reversible at-rest scheme.

The risk of adding a second scheme is operator confusion: two at-rest schemes that are not
clearly distinguished get misapplied — values hashed that needed decryption, or worse,
values encrypted that only needed hashing because "encrypted" felt safer (risk register,
envelope-encryption item).

The competing options were:

1. Keep Argon2id-only and leave in-process-readable credentials in plaintext.
2. Introduce envelope encryption as a general second scheme for "sensitive values."
3. Introduce envelope encryption with a hard, narrow justification boundary.

## Decision

A second at-rest scheme — envelope encryption with a root key wrapped chain: root key →
data-encryption keys (DEKs) → per-record AES-256-GCM — is adopted, and it is justified
**only** for in-process-readable credentials: stored values the system must decrypt to
use. Everything else remains under the Argon2id one-way hashing rule. Any future widening
of the envelope-encryption boundary requires a new superseding ADR.

## Consequences

- **Operators** manage exactly two at-rest schemes with distinct, documented justifications;
  blueprint §32.7 states both and the boundary between them.
- **concept.md** gains a glossary entry for envelope encryption that explicitly
  distinguishes it from Argon2id hashing, so the two cannot be conflated.
- **Key lifecycle** — root-key custody, DEK rotation, per-record re-encryption — is part of
  the operator runbooks, not left as an implementation detail.
- **Maintainers** treat the boundary as an invariant in review: a pull request that
  encrypts a value the system never reads back is a defect, and so is a hashed value the
  system must present.
- **Invariant:** no at-rest secret outside the in-process-readable credential set may be
  reversibly encrypted; no in-process-readable credential may be stored under a one-way
  hash.
