## 1. Summary

The `docs/` corpus is **structurally sound and gate-green at HEAD**, but it is **not anchored to
HEAD**, its strongest metadata fields are **empty by policy**, several **reader-facing files have
drifted from the tree they describe**, and the corpus's **own remediation requests remain
unexecuted**. This request asks for one bounded pass that (a) re-anchors every provenance claim to a
single canonical branch and commit, (b) moves freshness from audit-detectable to gate-detectable,
(c) closes the metadata and empty-section gaps, (d) fixes the reader-facing drift a green gate run
cannot see, and (e) **discharges or explicitly dispositions** the open parent requests. It is a
**remediation and re-baseline of the corpus**, not a greenfield build.

**Verified state at HEAD (`feature/dev` @ `039da060`).** 228 files under `docs/`; 160 front-mattered
artifacts; 25 documentation gates present, 25 green; `status/coverage-ledger.json` 2,246 rows / 0
orphans / 132 targets; `status/code-reconciliation.json` 22 match / 0 gap.

## 2. Motivation & the governing conflict (read first)

The corpus's authority model rests on three claims — *single-sourced*, *gate-verified*, and
*code-grounded*. The first is genuinely enforced. The second is true only **structurally** (the gates
prove internal consistency, not truth, and do not run `tsc`). The third is currently **false in a
reproducible way**: the corpus pins provenance to commits it does not ship at, its directory
reference describes a tree that no longer matches, and it asserts code landings whose verification
was explicitly deferred.

Per the project's own governance — *anything that departs from how a thing is already defined goes
through a formal Upgradation Request first* — these are recorded here as one request, distinct from
`upgradation/UR-20261009-001.md` (which raised the same class at `main` @ `9e29e855`) and
`upgradation/UR-20261008-001.md` (human-attestation). This request **adopts, re-anchors, and
supersedes-in-scope** those findings at the shipping HEAD and adds the findings a green gate run
cannot see.

## 4. Requested changes (by workstream)

### A. Provenance & anchoring
- **R1 — Re-anchor provenance to one canonical branch and one commit.** Update every provenance
  string in the normative corpus to name the canonical shipping branch and a **single** current
  commit SHA. Files in scope: `blueprint/structure.md`, `spec/architecture/directory-file-structure.md`,
  and the `note` field of `status/code-reconciliation.json`.
- **R2 — Collapse `status/code-reconciliation.json` to one HEAD and make it self-consistent.**
  Set `verified_commit` to the single canonical commit; replace the seven row `resolution` strings
  that cite `b6ae1a6d` and REC-017's `c510a35f` anchor with the same commit. The `note` and
  `verified_commit` must agree, and the freshness of `GAP_MANIFEST.md` (AF-5) must be re-stated
  against the same commit.
- **R2b — Add a provenance/freshness gate.** Extend the gate suite (or
  `scripts/docs/check-code-reconciliation.mjs`) so CI fails when the ledger's `verified_commit` is
  older than the corpus's declared basis, when a provenance string names a branch other than the
  canonical one, or when a `resolution` cites a HEAD that disagrees with `verified_commit`.

### B. Verification model
- **R4 — Give `review_state` / `last_verified_commit` a real lifecycle.** Either run a human review
  pass that flips at least the load-bearing normative sections (`spec/governance/**`,
  `spec/request-layer/permission-authorization-engine.md`, `spec/modules/module-anatomy-manifest.md`,
  `contracts/**`) to `review_state: verified` with a populated `last_verified_commit`, **or** state as
  corpus policy (in the reader-facing README and the front-matter schema note) that the corpus is
  machine-verified only and that the two fields are reserved. A field that is always `null` must not
  be presented as evidence.
- **R9 — Discharge the open parent requests and record code-verification evidence.** For each of
  `upgradation/UR-20261008-001.md`, `upgradation/UR-20261009-001.md`, and
  `upgradation/UR-20261009-002.md`: record a disposition (executed / partially executed / deferred
  with reason) in `upgradation/change-log.md`. Separately, for every change-log landing that records
  *"typecheck/lint/unit pending on the real toolchain"* (AF-4), append the actual verification result
  or mark the landing **unverified** so the record does not read as a completed, verified change.

### C. Ledgers & metadata
- **R3 — Regenerate the directory counts from the canonical branch.** Replace the stale
  921-entry / 242-dir / 679-file figures in `blueprint/structure.md` and
  `spec/architecture/directory-file-structure.md` with values generated from the canonical branch
  (at HEAD: 1,279 entries, 288 directories, 1,093 files).
- **R6 — Complete the contract and capability metadata.** Populate the null `id`/`title` fields for
  `contracts/openapi.yaml`, `contracts/rbac.enums.json`, and `contracts/ui-renderer.schema.json`, and
  give CAP-017 a title, in `status/compliance.json` and its `status/capabilities.json` source; the

- **R5 — State the version model.** Add one statement (in the reader-facing README or
  `docs/manifest.json`) mapping `corpus_version` to its parts, so `5.0.0` / `5.2.0` / `5.3.0` /
  `5.4.0` / `5.5.0` across the corpus resolve to a defined meaning rather than unrelated numbers.
- **R10 — Give the logged deviations an owner.** Reconcile
  `spec/governance/appendix-c-logged-deviations-and-open-items.md`'s 24 *"M9 residual"* items with
  `status/capabilities.json`, so each is either owned by a capability row or explicitly recorded as
  deferred — no silent unknowns.

### D. Reader-facing docs
- **R7 — Populate or downgrade the empty normative sections.** Fill `upgradation/change-log.md` §1,
  §2, §4, §5 (and the §2/§3/§7 chain-contract placeholders) — or re-state their `status` so an empty

## 7. Rollout (trigger-chain discipline)

1. **Gate first** (R2b) — so subsequent edits are checked as they land.
2. **Re-anchor** (R1 + R2 together) — the provenance strings and the ledger must move as one change.
3. **Ledgers** (R3, R5, R6, R10) — counts, version model, metadata, deviation ownership.
4. **Evidence surfaces** (R4, R7) — review-state lifecycle; populated sections.
5. **Dispositions** (R9) — record the open parent requests and the deferred verifications.
6. **Reader-facing** (R8) — README, `replit.md`, quarantine confirmation.
7. **Verify** — re-run the full gate loop; append the `v5.x` entry to `upgradation/change-log.md` per
   the change-log discipline.

## 8. Risks, assumptions & open questions

- **Anchor churn.** Re-anchoring to a moving HEAD invalidates itself as soon as the branch moves;
  R2b's gate is what keeps it honest. Without R2b, R1/R2 regress on the next push.
- **False "verified".** Flipping `review_state` without a real review would manufacture evidence —
  R4 permits a policy statement precisely to avoid that.
- **Self-verification.** The corpus is authored and verified by the same program; the change-log's
  own *self-verification caveat* applies. This request prefers recorded, reproducible evidence over
  self-declared status.
- **Open question — branch divergence.** `feature/dev` (this corpus's basis) and `main` diverge;
  whether the corpus's canonical shipping branch is `main` or `feature/dev` must be **decided and
  recorded** (as `upgradation/UR-20261009-001.md` R3 also requires). This request does not authorise
  any branch merge.
- **Open question — the 24 logged deviations.** Whether they are in scope for the next migration or
  remain a standing deferred tail is an operator decision (R10 records it, does not execute it).
