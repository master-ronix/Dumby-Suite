## 1. The corrections (verbatim, formalised)

1. Know what you are working on — read the corpus and understand the established framework behind each
   feature.
2. The Home control on `/modules` redirects to the **dashboard**, not the `/modules` main page.
3. The module Info card may use **medium (M) or compact (C) density**.
4. The Info card looks messy — its contents are split by **dividers/separators**; it must read as a
   formal, professional, meaningful module info page.
5. The data in the Info section is not meaningful.
6. The developer shows **`dev_first_party`**, which is meaningless per the corpus definitions.
7. The disable/uninstall control does not function: disabling a standard module must mark it disabled,
   relist it in the catalogue, and stop its commands on the server through the framework's
   sub-systems (BCCM and the dispatch gates) — a sensitive area.
8. Disable must work on a standard module (`/modules`), and enable/install must work on `/browse`
   through the dropdown.
9. Do not even render a disable/uninstall control on a **core** module's Info.

## 2. The framework facts this implements (from the corpus)

- **§13.2** — Core is permanently loaded with **no disable mechanism**; Standard is disableable by a
  guild admin, and a disabled Standard module's commands leave the guild list and it relists as
  **"Previously Installed"**.
- **§13.7 / §15.3** — a per-guild toggle is a **state-table write** that short-circuits dispatch
  before the handler; it never unloads the module, its DI registrations, or its event subscriptions.
- **§13.7** — command removal is **two-phase**: an immediate deny (the state gate) and a **batched
  deregistration** on the guild command change queue.
- **§6.4 / §17.7** — BCCM batches a command's `disable`/`enable` through `guild_command_queue`.
- **§1.5 / §11.6** — a surface attributes the module's **real developer** (from `devId`), and
  framework-shipped surfaces attribute to **Quixotic Mnemonics**.
- **§11.7** — `/modules` Mode M is "tier-grouped counts + dropdown".

## 3. Requested changes

- **R1 (2).** The `/modules` Home control returns to **`/modules` page 0** (this surface's own main
  view) — not the dashboard — matching Home on every other surface.
- **R2 (3/4).** The module Info card renders at **Mode M** (no banner, no per-field dividers) as a
  **single content block**.
- **R3 (5).** The card shows **meaningful fields**: display name + tier, description, developer,
  version, status, and the command inventory.
- **R4 (6).** The developer is resolved by **name** through a developer-identity helper (first-party →
  **Quixotic Mnemonics**), never the raw `devId`.
- **R5 (7/8).** Disable/enable **function**: the state write (`guild_module_states`), the immediate
  dispatch gate, and a **BCCM** enqueue of the module's commands (deregistration on disable,
  re-registration on enable). A disabled module relists in `/browse` as "Previously installed".
- **R6 (8).** `/browse` lists what a guild can **install or re-enable** — marketplace modules not
  enabled for the guild and standard modules the guild has disabled — so the dropdown re-enables a
  disabled module.
- **R7 (9).** A **core** module's Info renders **no** uninstall control at all.

## 7. Risks & open questions

- **Toggle scope, stated honestly.** Per §15.3 a per-guild toggle is a **state write**, not an unload:
  it does not stop fleet-wide cron tasks or close queue workers (that is the *unload* path, §13.7).
  The disable therefore stops the module's **commands** (state gate + BCCM deregistration) and its
  **event handlers** (dispatch-gated), and relists it — it does not tear the module down fleet-wide.
  If the operator wants a true fleet-wide teardown on disable, that is a different mechanism and needs
  its own request.
- **Developer registry.** `developers` has no reader yet (a recorded gap); a third-party `devId`
  therefore shows verbatim until a developer-name service exists.
