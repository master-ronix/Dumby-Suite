# UR-20261012-048 — `persona-` Is Not A UUID

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.54` entry in `upgradation/change-log.md`).

---

## 1. The report

The first real persona registration — `ELSA`, application `1387991780934553600`, guild
`1062427177326497863` — failed with:

```
Registration failed
insert into "persona_identities" (...) values (...) -
invalid input syntax for type uuid: "persona-…
```

Not a validation error, not an authorization error: **Postgres refused the row.** The id the service
generated was not a UUID.

## 2. The disagreement

Two declarations of the same fact, and only one of them was right:

| Where                                             | Says                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------ |
| `20260101000020_create_persona_identities.ts`     | `table.uuid('id').primary().defaultTo(gen_random_uuid())`                |
| `20260101000021_create_guild_persona_bindings.ts` | `table.uuid('personaId')…references('id').inTable('persona_identities')` |
| `personas/persona.ts` → `nextPersonaId()`         | `` `persona-${randomUUID()}` ``                                          |

The schema is **consistently `uuid`** — the primary key _and_ the foreign key that points at it. The
generator added a decorative `persona-` prefix, and a prefixed string is not a UUID, so the insert was
rejected **before anything was created**.

**Registration could therefore never have succeeded** — not for any input, not in any environment. This
is not an edge case; it is the whole path.

## 3. The fix

`nextPersonaId()` returns a **bare `randomUUID()`**. Nothing reads the prefix — it was decoration, and
the schema was the side that was right.

Appendix C #23's requirement is unaffected: the point of that note is that ids must not come from a
process-local counter, and a v4 UUID satisfies it directly.

## 4. Why nothing caught it

`buildPersonaIdentity` had **no unit test**, and the route tests stub the service — so the generator's
output was never asserted against the column it is written into. The new
`tests/unit/persona-identity.test.ts` closes that: it pins the id against a UUID shape, pins that it
carries no prefix, and pins that 200 identities never collide.

**The general lesson, recorded:** a generated identifier and its column type are one fact expressed
twice. Where they can drift, a test must bind them.

## 5. Acceptance criteria

- **ACC-UR-058-1** — the id is a bare UUID and carries no prefix.
- **ACC-UR-058-2** — 200 identities never share an id.
- **ACC-UR-058-3** — the registered fields survive unchanged, and `registrarAuthority` is _not_ stored
  on the identity (it is a logged attestation, not a column).
- **ACC-UR-058-4** — `dmBehavior` defaults to `prohibited` and `shardAllocation` to `1`.
- **ACC-UR-058-5** — an empty name is refused before anything is built.
- **ACC-UR-058-6** — full suite green with coverage: 113 files, 1139 tests, 0 failures, no threshold
  error; `typecheck`, `lint`, `format`, corpus gates 27/27.

## 6. Operator note — rotate the credentials from that attempt

The registration was attempted with live credentials pasted into a chat. **The persona's bot token, its
OAuth2 client secret, and the `INTERNAL_API_KEY` used must all be treated as exposed and rotated**, even
though the attempt failed and nothing was created: the request body reached the service, and the log
records the attempt.
