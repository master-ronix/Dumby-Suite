## 1. Summary

The corpus's governance rule **D-4.10** (`spec/governance/part-4-module-system-framework.md`) requires
that *where the signing subsystem is not yet present, hash-bound provenance verification against the
build record is the enforced floor*. At HEAD the runtime does not enforce that floor: the loader runs
**no** load-time provenance verification — neither the artifact-hash check nor the signature check —
unless a signing key is registered, and the deployment currently configures none. So the "enforced
floor" is, in practice, **fail-open**, and the log line `module-provenance-unverified` is the visible
symptom. This request asks for one bounded change that makes the floor hold without a signing key.

## 2. Motivation & the governing conflict (read first)

The corpus's module-delivery contract rests on the claim that an uploaded module is *untrusted input
until validation and promotion*, and that a promoted artifact is verified on load (§15.8/§15.9,
`spec/modules/swastik-hot-reload-dynamic-module-management.md`). D-4.10 states the fallback that keeps
that claim true while the signing subsystem is absent: **hash-bound verification against the build
record**. The code implements both checks together and gates them on the signing key, so removing the
key removes the floor rather than degrading to it.

This is a divergence the corpus is designed to catch, and it did: it is recorded as REC-025. Per the
project's own governance — *anything that departs from how a thing is already defined goes through a
formal Upgradation Request first* — the fix is requested here.

## 4. Requested changes

- **R1 — Decouple hash-bound verification from the signing key (primary).** The loader must verify a
  promoted module's on-disk artifact against its build record (the `builds` row / the
  `build-provenance.json` sidecar) **before import, whenever a build record exists — independent of
  whether a signing key is registered**. The signature check remains an additional layer that arms
  when a key is present. This is the D-4.10 floor: hash-bound verification, not signature
  verification, is what MUST hold while the signing subsystem is absent.
- **R2 — Fail closed when the floor cannot run (alternative / fallback).** Where neither a build store
  nor any verifier is available, the loader must **refuse to load** the module (quarantine it and
  continue) rather than import it unverified — and log at error, not warn. A load that cannot be
  verified is not a normal state. R1 is preferred; R2 is the acceptable fallback where R1 cannot be
  landed in the same pass.
- **R3 — Prove the floor with a test.** A unit test that fails before and passes after: with no signing
  key configured, a promoted module whose artifact hash does not match its build record is **not**
  imported (R1), and a module with no build record is refused (R2). Record which assertions are
  mechanism gates and which are no-regression controls.

## 8. Risks, assumptions & open questions

- **Fail-open vs fail-closed is a behavioural choice.** R2 changes load behaviour for a deployment with
  no build store; it must quarantine rather than crash, and must not regress a legitimate
  first-party-module load. R1 is the lower-risk primary.
- **A signing key is a mitigation, not the fix.** Supplying `BUILD_SIGNING_PUBLIC_KEY` arms the full
  guard, but the spec's floor is hash-bound verification *where the signing subsystem is absent*, so
  the code change (R1) is the correct remedy and the key is optional hardening.
- **Assumption.** A build record exists for every promotable artifact (§15.8 promotion writes it), so
  R1 has data to verify against.
- **Open question.** Whether R2 should be the default when no build store is configured at all (a
  greenfield deployment with no modules) — a load-time refusal there is correct, but the message must
  distinguish "no modules" from "unverifiable module".
