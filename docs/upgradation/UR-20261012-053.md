# UR-20261012-053 — One Fact, Written Twice

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.59` entry in `upgradation/change-log.md`).

---

## 1. How it surfaced

UR-20261012-051 put an **Info** control and an **Invite** link on the persona profile, admin-only. The
operator ran `/persona` on the build that contained them and **saw neither** — because
`isGuildAdmin(interaction)` returned false for them.

## 2. Defect one — the admin gate compared bit VALUES against NAMES

```ts
const ADMINISTRATOR_PERMISSION = "8"; // the Discord bitfield value
const MANAGE_GUILD_PERMISSION = "32";
permissions.includes(ADMINISTRATOR_PERMISSION);
```

Every producer of `memberPermissions` emits **names** — `'Administrator'`, `'ManageGuild'` — because the
rank bundles are expressed in names:

```ts
export const ADMINISTRATOR_BUNDLE = ["Administrator"] as const;
export const MODERATOR_BUNDLE = [
  "KickMembers",
  "BanMembers",
  "ModerateMembers",
  "ManageMessages",
] as const;
```

So `includes('8')` could never match, and **`isGuildAdmin` was false for every guild administrator who
was not the owner.** Only the owner was recognised, through `isGuildOwner` — which is exactly what kept
the bug invisible for so long.

**Fixed:** the constants are the names.

## 3. Defect two — the adapter omitted `ManageMessages`

The interaction adapter collected a **hand-written** list of permission names to ask a member about:
`Administrator, ManageChannels, ManageGuild, ModerateMembers, BanMembers, KickMembers`.

It omitted **`ManageMessages`** — the one permission that both `MODERATOR_BUNDLE` and `HELPER_BUNDLE`
require. So `holdsEveryBit` could never be satisfied for either bundle and a moderator or helper
**evaluated as MEMBER**, failing any command that requires MODERATOR or above.

**Fixed — by derivation, not by adding the missing name.** `rank.ts` now exports
`TRACKED_PERMISSION_NAMES`, built from the three bundles plus the two names the dispatch path asks about
directly, and the adapter uses it. The two lists can no longer disagree, because there is now only one.

## 4. Why this is recorded as one UR

Both defects are the same failure: **a fact expressed in two places, in two forms, disagreeing.** One
list said `'8'`, the other said `'Administrator'`. One list forgot `ManageMessages`, the other required
it. Neither is a logic error — both are drift, and both were invisible because the owner path masked the
first and no test exercised the second.

## 5. Acceptance criteria

- **ACC-UR-063-1** — a guild administrator is recognised from the permission **name**.
- **ACC-UR-063-2** — the guild owner is recognised without any permission bit.
- **ACC-UR-063-3** — an ordinary member is not an administrator.
- **ACC-UR-063-4** — every name a rank bundle requires is in the tracked list.
- **ACC-UR-063-5** — a member holding the MODERATOR bundle is ranked MODERATOR, end to end through the
  adapter; likewise HELPER.
- **ACC-UR-063-6** — full suite green: 113 files, 1159 tests, 0 failures; `typecheck`, `lint`, `format`,
  corpus gates 27/27.

## 6. Recorded

**A test that only exercises the owner path will not find an administrator bug.** `isGuildOwner` short-
circuits ahead of the permission check, so every owner-shaped test passed while every non-owner
administrator was refused. The new tests assert the **name-based** path specifically.
