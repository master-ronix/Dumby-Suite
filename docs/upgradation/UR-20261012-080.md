# UR-20261012-080 — A Persona Could Not Run Any Core Command

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.85` entry in `upgradation/change-log.md`).

---

## 1. The finding

A screenshot shows the persona (Magma) running `/dashboard` and receiving:

```
⚠ Not permitted
Your permissions do not allow this action.
reason: FORBIDDEN
```

`/dashboard` is a **core** command. §13.2 is explicit: *"Core is `shared`: no profile owns it, every
profile runs it."* A persona being refused it is not a permissions decision — it is a defect, and it is
one UR-20261012-078 introduced.

## 2. The mechanism

UR-078 made the ownership read answer `'main'` for any module that is **enabled** with no persona
binding. That is correct for standard and marketplace modules. It is wrong for **core**, because:

- a core module has **no binding** — nothing binds a shared module; and
- a core module is **always enabled** — the read short-circuits core to `true` by design.

So both conditions held, and **every core module read as the main bot's**. The dispatch assertion then
saw `owner = 'main'` against a persona's own id and refused:

```
if (owner === (this.options.residentPersonaId ?? 'main')) return;
throw new PersonaOccupiedError(...);
```

The blast radius was every core command — `/dashboard`, `/modules`, `/browse`, `/persona`, `/permit`,
`/queue`, `/health`. A persona could run almost nothing. `PersonaOccupiedError` maps to `FORBIDDEN`,
which is why the notice said "your permissions do not allow this action": the wrong message again, for
the same reason as UR-074.

## 3. What changed

- **The dispatch assertion short-circuits the shared tiers.** Core and admin return before the
  ownership check, so a shared module is never "occupied".
- **The read states the truth.** `resolveCommandOwner` answers `'shared'` for a core or admin module
  rather than `'main'`. Its callers that matter already short-circuited the tier (the page's `ownedBy`
  returns true for core; the module-context resolver skips `resolveOwner` when the module is shared) —
  but a read that states something false is a read waiting for a caller that believes it.
- The tier comes in as another optional dependency, absent meaning "not special-cased here".

## 4. Acceptance criteria

- **ACC-UR-080-1** — a persona runs a core command; it is not refused.
- **ACC-UR-080-2** — a persona is still refused a standard module the main bot holds.
- **ACC-UR-080-3** — `resolveCommandOwner` answers `'shared'` for a core or admin module.
- **ACC-UR-080-4** — with no tier dependency the read behaves as before, not worse.

## 5. Recorded

**A read that answers a question it was not asked is dangerous.** The read answers *"who owns this
module"*. For a shared module the honest answer is "nobody", and the code said "the main bot" — which is
a claim about ownership where there is none. Two of three consumers happened to guard against it; the
third did not, and the guard in the first two was never the reason it worked.

**The third instance of the same lesson in three UR's, which is the real finding.** UR-078 changed a
read; UR-079 found a *presentation* consumer that keyed on the old sentinel; this found a *decision*
consumer that never accounted for the new value. The pattern is not "check the consumers" — it is that
a shared read with a newly-possible return value needs the new value enumerated at every consumer, and
"the other two short-circuit" is not a reason the third will.

**A live regression was found by a screenshot, not by the suite.** 1238 tests passed with a persona
unable to run any core command. The tests covered the tiers separately and the ownership read
separately, and nothing exercised the two together — a persona, a core command, and the ownership
assertion on one path.
