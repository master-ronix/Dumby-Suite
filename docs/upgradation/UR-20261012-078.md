# UR-20261012-078 — The Main Bot Owns What the Main Bot Enabled

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.83` entry in `upgradation/change-log.md`).

---

## 1. The finding

The install path's claim branch is **persona-only**:

```ts
if (owner === undefined && acting !== undefined) {
  await personaBindingService.bindModuleToPersona({ guildId, moduleSlug: moduleId, personaId: acting.id });
}
```

So the **main bot never records a claim.** It enables a module, leaves no binding, and `owner` stays
`undefined` — which means **any persona may later claim a module the main bot enabled.**

The operator's rule is the opposite:

> *"if the hello module is enabled by the main bot then it is the property of the main bot only"*

Under the code as it stood, that rule was not enforced, because the main bot's ownership was never
written down anywhere.

## 2. The model was assumed in three places and stated in none

Worth recording, because it is why this is a one-line answer rather than a schema change. Three callers
already behaved as if the main bot owned an unbound module:

- the router's standing build: `(await resolveCommandOwner(...)) ?? 'main'`
- the page-data holder check: `(await holderOf(...)) ?? MAIN_PROFILE_ID`
- the module context's standing (UR-20261012-070)

Each papered over the same `undefined`. The ownership **read** now answers it once, and those fallbacks
become redundant rather than load-bearing.

## 3. What changed

`resolveCommandOwner` — the ONE ownership read — answers in order:

1. a live persona binding's `personaId`;
2. **`'main'`** when the guild has the module **enabled** and no persona holds it;
3. `undefined` otherwise.

The enablement read is an **optional, late-bound** dependency, so a read-only caller can still construct
the service; absent, ownership is **unanswered rather than guessed**. A failing read is logged and leaves
it unanswered — never claimed. `'main'` cannot collide with a persona id, which is a UUID.

Two sites had to learn the main bot's own id, because inferring `'main'` would otherwise have made the
main bot **refuse its own module**:

- the dispatch assertion compared `owner === residentPersonaId`, and the main bot's `residentPersonaId`
  is `undefined` — it now compares against `residentPersonaId ?? 'main'`;
- the install path's actor comparison used `acting?.id`, also `undefined` for the main bot — now
  `acting?.id ?? 'main'`.

## 4. Acceptance criteria

- **ACC-UR-078-1** — a persona binding answers first.
- **ACC-UR-078-2** — an enabled module with no binding answers `'main'`.
- **ACC-UR-078-3** — a disabled module with no binding answers `undefined`.
- **ACC-UR-078-4** — with no enablement read, or a failing one, the answer is unanswered, not a guess.
- **ACC-UR-078-5** — a persona is still refused a module the main bot owns.
- **ACC-UR-078-6** — 121 files, 1237 tests, 0 failures; coverage at or above the branch floor.

## 5. Recorded

**A rule that lives only in the operator's head is not a rule the system has.** Three separate callers
independently assumed the main bot owned an unbound module; none of them could enforce it, and the
claim path contradicted it. Writing the assumption down in the one read is what turns an informal
understanding into a property of the system.

**Inferring an owner creates a new failure mode: the owner refusing itself.** Both comparisons that
decided *who may act on* a module compared against `residentPersonaId`, which is `undefined` for the
main bot. Adding `'main'` to the ownership answer without fixing those two would have replaced "a persona
can steal the main bot's module" with "the main bot cannot use its own". A change to a shared read is
only half done when the read is fixed; the comparisons have to agree.
