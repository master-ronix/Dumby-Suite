# UR-20261012-051 — The Page Opened On The Wrong Identity

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.57` entry in `upgradation/change-log.md`).

---

## 1. The report

Two defects, both about `/persona`:

1. **Run from the main bot, the page opened on a PERSONA's profile** instead of the main bot's own. The
   operator's requirement is unambiguous: _"main page must show profile from which persona/bot command
   is ran."_
2. **There was no way to reach the invite.** No info control on a profile, and no invite method.

## 2. Defect 1 — the default profile

```ts
const currentProfileId =
  ownerOf.get(moduleId) ?? guildRegistration?.id ?? MAIN_PROFILE_ID;
```

The chain asked two questions, and neither is the right one:

- `ownerOf.get(moduleId)` — **which persona owns the `persona` MODULE**. A module's owner is not the
  identity issuing the command.
- `guildRegistration?.id` — **the persona registered for this guild**. So `/persona` from the main bot
  opened on the persona, exactly as reported.

The question the page was always trying to answer is **which identity is running this command**. That
is `PERSONA_ID`: empty in the main bot's process, set in a dedicated persona process.

**Fixed:** the opening profile is the resident identity, falling back to the main profile when
`PERSONA_ID` is unset or names a persona this guild does not have. The ownership map and the guild
registration still decide **which profiles are listed** — they simply no longer decide which one opens.

## 3. Defect 2 — the invite had no way in

The invite URL was **computed and parsed and never rendered**. `page-data` built it, `persona-blocks`
read it into the profile shape — and nothing drew it. The only path to it was a control labelled
**"OAuth setup"**, offered to guild admins only, whose card carried the invite. "OAuth setup" reads as a
configuration chore, not as _"here is how to add this persona"_.

**Fixed — two controls on the profile row:**

| Control    | Behaviour                                                                                                                                             |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Info**   | Icon-only (no label), opens the card carrying the profile's identity, the callback URL to register, the portal guide, and the invite link.            |
| **Invite** | A direct **link** button (style 5), rendered **only when an invite URL exists** — so summoning the persona is one click, not a detour through a card. |

Both remain admin-only: the invite is a privileged action.

## 4. Acceptance criteria

- **ACC-UR-061-1** — the opening profile is the identity running the command; the main bot's own
  `/persona` opens on the main profile.
- **ACC-UR-061-2** — a guild registration does **not** become the opening profile.
- **ACC-UR-061-3** — the tiers describe the opening profile, not a persona chosen for the guild.
- **ACC-UR-061-4** — an admin sees an icon-only **Info** control and, when an invite URL exists, a
  direct **Invite** link (style 5).
- **ACC-UR-061-5** — a non-admin sees no control row at all.
- **ACC-UR-061-6** — full suite green: 113 files, 1151 tests, 0 failures; `typecheck`, `lint`, `format`,
  corpus gates 27/27.

## 5. Recorded

**A value that is computed, carried through a type, and never rendered is invisible in a way that reads
as "the feature was never built".** `inviteUrl` had a field in two modules and no consumer. Where a
surface is expected to offer an action, the assertion belongs on the RENDERED output — which is what the
persona-blocks test now checks.
