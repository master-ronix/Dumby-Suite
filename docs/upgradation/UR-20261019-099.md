## 1. Summary

The specification requires a `buildId` in the module manifest **and** says Swastik assigns a fresh
`buildId` per accepted version, with no statement of which is authoritative. The manifest contract,
the `builds` row, and the provenance sidecar can therefore disagree about an artifact's identity. This
request makes the **platform-issued** `buildId` authoritative and removes the ambiguity from the
manifest contract.

## 2. Business / engineering justification

The build-provenance work (UR-20261018-093 / REC-025) keys the hash-bound floor on the `buildId`:
the loader verifies the on-disk artifact against the `builds` row **for its `buildId`**. If the
artifact's identity has two sources — an author-declared manifest field and a platform-issued id — the
verification key is ambiguous, and the same "one fact, two sources" defect class the corpus's audits
keep finding is baked into the contract the fix depends on. Fixing the provenance floor without fixing
`buildId` leaves the chain anchored to a contested key.

## 3. Scope & impact

- **In scope:** the manifest `buildId` contract; the manifest spec text; the Swastik assignment text;
  the `builds` PK documentation.
- **Out of scope:** the provenance fix itself (UR-20261018-093) and the signing ceremony.
- **Systems / audiences affected:** module authors; Swastik; the Credential Service; the Power Engine;
  every framework module manifest.

## 4. Current state (evidence)

- `spec/modules/module-anatomy-manifest.md` §82 — `buildId` is **required**, "the identifier for this
  specific uploaded version … the registry validates the `devId`/`buildId` pair before load."
- `contracts/module-manifest.schema.json` — `buildId` is in the `required` array.
- `spec/modules/swastik-hot-reload-dynamic-module-management.md` §238 — "Swastik assigns a fresh
  `buildId` and signs the full provenance byte set …".
- `spec/data/database-architecture.md` L59 — `builds … buildId string PK`.
- `spec/reference/appendix-implementation-status-audit-register.md` L842 — "Deep-Analysis describes
  buildId as per-version identifier; Design upgrades it to semver+hash."
- **[Reported]** (blueprint §3, not verified here): the code hardcodes `build_<slug>_1_0_0` in the
  framework manifests while Swastik generates its own id and never reconciles the two.

## 5. Proposed change

Choose one and state it in the manifest spec:

- **(A) Platform writes the issued id.** The manifest's `buildId` is populated **by the platform** at
  promotion (not authored); the schema keeps the field but marks it platform-written; the deployed
  manifest, the `builds` row, and the sidecar carry the same value.
- **(B) Drop it from the schema.** Remove `buildId` from `contracts/module-manifest.schema.json`
  `required` (and the manifest), keep it only in the `builds` row and the sidecar, and stop the
  framework manifests hardcoding `build_<slug>_1_0_0`.

Recommended: **(A)** if a deployed manifest must carry its own identity; **(B)** if the identity lives
only in the platform record. Either way, name the single owner.

## 6. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Manifest-contract change breaks existing manifests | High | Migrate the framework manifests in the same change-set; validate against the schema |
| The three services' `buildId` roles are not yet agreed | Medium | Confirm the division of labour (Credential Service / Swastik / Power Engine) before landing |
| Divergence from the in-flight provenance work | Medium | Sequence with UR-20261018-093; this is its workstream W4 |

## 7. Rollback / reversal plan

Revert the spec and schema edits and the manifest migration; the prior (ambiguous) contract returns.
No runtime behaviour changes in this request alone.
