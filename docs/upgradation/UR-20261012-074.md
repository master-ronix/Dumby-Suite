# UR-20261012-074 — A Disabled Module Is Not a Permission Problem

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.79` entry in `upgradation/change-log.md`).

---

## 1. The finding

Screenshots from a live server showed `/dashboard` refused with:

```
Not permitted — Your permissions do not allow this action.   reason: FORBIDDEN
```

UR-20261012-068 had already split the notice by cause, so that an **unreadable** state stopped being
reported as a refusal. But the case where the module is genuinely **disabled in that guild** still
reported as `FORBIDDEN` — telling a member they lack permission when the truth is that an admin turned
the module off. That is the exact confusion the operator described, still live.

## 2. Why the obvious fix would have been wrong

The first attempt mapped `scopeCause === 'module-disabled'` to a new reason code. Four existing tests
failed immediately — and they were right to.

`CommandScopeDeniedError` is thrown from **eight** sites, and only one of them means "the module is
disabled":

| Site | What it actually is |
|---|---|
| `!enabled` | the module is switched off here — the one genuine case |
| the permission resolver denying | a **permission** decision |
| a DM where the command is guild-only | out of scope |
| an admin command in the wrong guild | out of scope |
| an unresolved tier | out of scope |
| the two `state-unreadable` guards | the state could not be read |

All the others used the **default** cause, which was `'module-disabled'`. Mapping on that value would
have relabelled every DM refusal and every admin-guild refusal as "this module is switched off" — a new
lie in place of the old one.

## 3. What changed

- `CommandScopeCause` gained **`'out-of-scope'`**, and it is now the **default** — a neutral cause, so
  an unspecified refusal is never silently reported as something it is not.
- Only the `!enabled` site passes `'module-disabled'`.
- The permission resolver's denial passes `'permission-denied'`, so it keeps saying what it is.
- `NoticeReasonCode` gained **`MODULE_DISABLED`**, with its own heading (*"This module is switched off"*)
  and an explanation that names the remedy: *"so this is not a permissions problem. A server admin can
  turn it back on from /browse."*

## 4. Acceptance criteria

- **ACC-UR-074-1** — a module-disabled refusal says so, and does not say "your permissions do not allow
  this action".
- **ACC-UR-074-2** — a permission-resolver denial still reports `FORBIDDEN`.
- **ACC-UR-074-3** — an admin command refused outside the dev guild still reports `FORBIDDEN`.
- **ACC-UR-074-4** — the notice names the remedy, not just the refusal.
- **ACC-UR-074-5** — 120 files, 1228 tests, 0 failures; coverage at or above the branch floor.

## 5. Recorded

**A test that pins the wrong behaviour is a bug with a guard on it.** One of the four failing tests
asserted `reason: FORBIDDEN` for a disabled module — it had encoded the defect as the contract. When a
change makes a test fail, the first question is whether the test is right; here, three were right and
one was the bug.

**The default value of a cause is a claim.** `'module-disabled'` as the default meant every throw that
did not name a cause silently asserted one. Making the default neutral is what makes the explicit
causes mean something.
