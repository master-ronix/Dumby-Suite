# UR-20261012-055 — Register Everything, Answer Only What You Own

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.61` entry in `upgradation/change-log.md`).

---

## 1. What was wrong

A persona built a **filtered** registry — only its bound modules — and deployed only **guild** commands:

```ts
buildRegistry: (slugs) => filterRegistryForModules(commandRegistry, new Set(slugs)),
deployCommands: async (persona, botToken, registry) => {
  const body = registry.toApiPayloads();
  if (body.length === 0) return 0;          // nothing bound ⇒ no request at all
  await rest.put(Routes.applicationGuildCommands(...), { body });
}
```

Two consequences, and the operator hit both:

- **A persona with nothing bound registered nothing**, because the payload was empty and the deploy
  returned before making a request. So a freshly registered persona had no commands at all — and looked
  broken rather than empty.
- **Stale registrations were never cleared.** A `PUT` to a command route is a **bulk overwrite** — the
  set sent replaces whatever was registered — but that only helps if the `PUT` happens. With an empty
  payload the early return skipped it, so whatever an earlier state had registered stayed.

## 2. The model, as stated

A persona registers **the same global and guild command set as the main bot**. What it may **answer** is
decided by **ownership**, in the router (`assertPersonaOwnsCommand`), not by what it registers. Because
a persona is bound to exactly one guild, its registration in any other guild is inert — and its own
router refuses commands belonging to modules it does not hold.

Registration is therefore _not_ the restriction. The binding is.

## 3. The fix

- `buildRegistry` returns the **full** registry.
- The deploy now PUTs **both** routes, **always**, via an extracted and testable
  `deployPersonaCommands(applicationId, guildId, payloads, put)`:

```ts
await put(`/applications/${applicationId}/commands`, payloads);
await put(
  `/applications/${applicationId}/guilds/${guildId}/commands`,
  payloads,
);
```

An empty payload still PUTs, because **the overwrite is the clear**.

The boot warning is reworded to match: `persona-no-modules-bound` now says the persona **OWNS nothing**
and will refuse what it is not bound to — not that it will have no commands, which is no longer true.

## 4. Acceptance criteria

- **ACC-UR-065-1** — the deploy PUTs the global route then the guild route, with the same payload.
- **ACC-UR-065-2** — an empty payload still PUTs both routes, so a stale registration is cleared.
- **ACC-UR-065-3** — the persona builds the full registry, not a filtered one.
- **ACC-UR-065-4** — the boot warning describes ownership, not the command set.

## 5. Recorded

**An early return that skips a request also skips the cleanup that request performs.** The empty-payload
guard read as a sensible optimisation — "nothing to send, so send nothing" — but a `PUT` on a command
route is not only an install, it is a **replacement**. Skipping it preserved exactly the state the
operator wanted gone.
