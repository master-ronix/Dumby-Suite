# UR-20261012-030 — Persona Authorization (Route A + Route B)

**Identity:** UR-20261012-030 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.35` entry in `upgradation/change-log.md`).

---

## 1. Summary

A persona is a separate Discord application, so the instant-hide override for its commands needs a
user token issued by *that* application — the endpoint is
`/applications/{application.id}/guilds/{guild.id}/commands/…` and rejects a token minted by any other
application. The operator asked for Route A (per-persona OAuth) as the primary path and Route B (the
bot-token delete) as a fallback only.

## 2. The revision

- **Route A — the credential.** The Twill registration payload gains an optional sealed
  `oauthClientSecretSealed`, stored envelope-encrypted like the bot token (ADR-003), and carried
  through the identity model and its repository.
- **Route A — the client.** `personas/persona-oauth.ts` resolves an OAuth2 client for a persona
  application: its application id as the client id, its opened secret as the client secret, and the
  shared callback URL as the redirect URI. An application with no usable secret resolves to nothing —
  which is exactly when Route B applies.
- **Route A — the flow.** `/auth/authorize` accepts `app=<applicationId>`; that application's client
  runs the authorize leg and the application is recorded in a cookie. `/auth/callback` exchanges the
  code with THAT application's client only, and stores the token against it. An unresolvable
  application is refused rather than silently exchanged by the wrong client.
- **Route A — the dashboard.** `/dashboard` lists each registered persona with an
  *Invite + authorize* link pinned to its bound guild, so inviting and authorizing are one step.
- **Route A — the owner.** `setModuleCommandAccess` now resolves which application OWNS the module in
  the guild (the persona bound to it, else the main bot) and uses that application's endpoints and
  token. The static env token applies to the main bot only.
- **Route B — the fallback.** With no user token, a DISABLE still hides at once by deleting the
  guild commands with the owner's own bot token — a bot-token operation needing no authorization. A
  404 counts as already removed. The BCCM re-creates the commands on the next enable, which is the
  batched path it already owns.

## 4. Acceptance criteria

- **ACC-UR-040-1** — a persona application resolves an OAuth2 client from its sealed secret; absent
  one it resolves nothing.
- **ACC-UR-040-2** — authorize and callback use the persona's own client, and the token is stored
  against that application.
- **ACC-UR-040-3** — an unresolvable application is refused, never exchanged by another client.
- **ACC-UR-040-4** — the access override follows the module's owning application.
- **ACC-UR-040-5** — with no user token, a disable removes the commands with the owner's bot token.
- **ACC-UR-040-6** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 5. Rollout

Ordinary deploy. The migration adds a nullable column, so no existing persona changes. Route A is
inert until a persona is registered WITH a client secret.

## 6. Risks & open questions

- **The Twill HTTP endpoint is still a stub (501)**, so a persona — and therefore its client secret —
  cannot yet be created in production. The registration *service* and the model accept the secret
  today; un-stubbing the endpoint is a separate, deliberate decision (ADR-011).
- **Route B spends the daily create quota** when a disable is later re-enabled, because the command is
  genuinely removed and must be re-created. The BCCM's existing daily-limit guard refuses rather than
  failing the batch.
- **Route B changes the command id.** Per-command permission overrides written earlier do not follow
  a re-created command.
- **The owner lookup runs per disable/enable.** It is one indexed read; a failure degrades to the main
  bot rather than throwing.
