# UR-20261012-031 — Persona Invites, Install Permissions, a Cleaner Dashboard

**Identity:** UR-20261012-031 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.36` entry in `upgradation/change-log.md`).

---

## 1. Summary

The operator called the previous flow confusing, and named three concrete faults: a registered persona
was not presented as available-and-invitable, `/dashboard` showed a guild list beside an install
button, and Discord's authorization screen offered no permissions step the way a real bot install
does. This record supersedes the presence-as-status reading of UR-20261012-029.

## 2. The revision

- **A persona reads Online, and presence is stated separately.** A registered, non-retired persona is
  **Online** — it exists and is invitable — and whether its bot is already in the guild is a second,
  honest fact in the headline subtext ("In this guild" / "Not in this guild yet"). Presence no longer
  drives the status.
- **One invite control, on the persona profile.** A guild admin sees the persona's invite link
  directly on the page. With an OAuth2 client secret registered the link is the combined
  install+authorize leg (`/auth/authorize?app=…&guild=…&bot=1`), so one click adds the bot AND
  captures its token; without one it is a plain Discord bot install pinned to the bound guild. Never a
  menu of options, and never shown to a non-admin.
- **OAuth configuration stays optional, behind the info control.** The admin-only `OAuth setup`
  control still opens the private card stating the callback URL to register and the guide. The card
  now also carries the persona's own invite link, and names the persona.
- **Install permissions.** The install leg sends a `permissions` bitfield
  (`BOT_INSTALL_PERMISSIONS`, default `84992` — View Channels, Send Messages, Embed Links, Read
  Message History), which is what makes Discord render its standard permissions step.
- **A single-purpose dashboard.** The guild list and the per-guild Authorize controls are removed.
  `/dashboard` is one paragraph and one control: *Add Dumby to your server*, with the guild and the
  bot's permissions chosen on Discord's own screen. Personas no longer appear there.
- **Link buttons in page blocks.** `PageActionButton` gains an optional `url`; a control carrying one
  renders as a Discord link button (style 5), so the invite can sit in the profile rather than behind
  an extra card.

## 5. Rollout

Ordinary deploy. `BOT_INSTALL_PERMISSIONS` defaults sensibly; the dashboard loses its guild list, so
authorizing a specific guild now happens through Discord's own picker on the install link.

## 6. Risks & open questions

- **Presence still needs the guild in the member cache.** It is now informational rather than
  load-bearing, so an uncached guild no longer mislabels a persona.
- **The invite link is built from `OAUTH_REDIRECT_URI`'s origin.** A wrong redirect URI yields a wrong
  base; the plain install is used when the base is empty.
- **A retired registration stays Retired** and offers no invite.
- **Fixed v1.1 — and it was a real production bug, not a test fault.** The v1.0 commit left the
  `extras` expression unchanged, so the permission bitfield was attached only when a guild was named:
  the dashboard's own guild-less install link (`/auth/authorize?bot=1`) still sent no `permissions`,
  and Discord still arrived without its permissions step — the very fault this record set out to fix.
  The install leg now always carries the bitfield, with the picker pinned only when a guild is named.
  Two further CI failures were faults in the new tests: a sealed fixture opened with a different root
  key than it was sealed with, and an assertion expecting HTML-escaped `&amp;` in a URL that carries a
  raw `&`.
