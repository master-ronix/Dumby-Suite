# UR-20261027-105 — Module Boundary

**Identity:** UR-20261027-105 · **Version:** 1.0 · **Date:** 27/10/2026 · **Requester:** operator directive

**Freeze status:** **Open — raised 2026-10-27.** It edits no frozen record and moves no file.

**Basis.** The operator directive of 2026-10-27 states three policies for the module boundary. All four
items are now implemented: `MB-1` … `MB-3` in this record's first run, and `MB-4` in a follow-up run of
the same record (§3.4), after the operator settled its four open decisions. The audit behind the directive was read against the tree at
`feature/dev` @ `5d01df7`.

Item IDs use the `MB-` prefix (module boundary). They are new to this corpus and are declared here
rather than borrowing `DOC-`, which is the documentation-audit series.

---

## 1. Objective and rationale

**Objective.** After this record lands: no module — first-party or third-party, standard or marketplace
— is handed the internal core base; a module can share data with another module on exactly one channel
and cannot reach another module by any other route; and every module process is a first-class citizen of
the same registry, ownership and state model that commands and modules already live in.

**Rationale.** The three policies are one policy: **the module boundary is not enforced, so it is not a
boundary.** The evidence, read from the tree:

- `loader.ts:278` called `mod.onLoad?.(this.container)` — the whole DI container, with all 22 core
  tokens on it. A Standard or Marketplace module could resolve `core.Db` (SQL, and every row the
  framework holds), `core.CommandRegistry` (every slash command registered to any profile or guild),
  `core.Scheduler`, `core.Queue`, `core.EventBus` and `core.ModuleRegistry`, exactly as a Core module
  can. The four tier entrypoints in `@workspace/swastik` (`core.ts`, `admin.ts`, `standard.ts`,
  `marketplace.ts`) were byte-identical, so the tiers differed in name only.
- `packages/modules/eslint.config.mjs` banned cross-module imports but advertised an escape hatch
  ("except through a declared `*.forCrossModuleRead` accessor") that no code implements, and it did not
  ban a module importing the core base's own source.
- The manifest schema declares `provides` and `services` (module-to-module service sharing), and
  nothing wires them — a coupling channel that exists on paper and would become a hole the moment it
  was implemented.
- Process gating exists but is per-surface and divergent: commands fail closed per guild
  (`enablement.ts`), events and jobs fail open per guild, and cron tasks are gated **fleet-wide**
  ("runs while at least one guild wants the module", `scheduler.ts`). None of them carries the
  provenance tuple the directive asks for, and none of them terminates work that is already running.

## 2. Scope

**In scope.** `packages/swastik/src/**` (the module authoring surface), `apps/main/src/module-system/**`
(the guard, the loader, the global data channel), `packages/modules/eslint.config.mjs` (the static half
of the boundary), and `apps/main/tests/unit/**` (the tests).

**Out of scope.** Any change to what a Core module may do; the shipped behaviour of the eight first-party
modules (none of them uses the container it was handed, so the guard changes nothing for them); the
`provides`/`services` schema fields (declared, unwired, and now explicitly non-wirable — see `MB-3`).

**Branch boundary.** All work happens on `feature/dev`. No commit, merge or push touches `main`,
`master`, `release` or any other branch.

### 3.1 MB-1 — the capability surface (implemented)

- **Defect.** `loader.ts:278` passed the raw `Container` to `onLoad`, for every tier.
- **Approach.** `module-capabilities.ts` defines one capability list and the tier→capability map. Core
  and Admin hold all of it; Standard and Marketplace hold the baseline only — `logging`, `config.read`,
  `cache`, `metrics`, `i18n`, `presentation.render`, `permissions.resolve`, `global.data.emit`. The
  loader wraps the container per module with `withModuleCapabilities`, which intercepts `resolve`,
  `tryResolve`, `has` and `register`, refuses anything outside the tier, and refuses `freeze`,
  `createChild` and `createScope` to non-privileged tiers (a module that could freeze or fork the root
  container could reshape the framework for every other module — the same boundary by another route).
  The refusal is a throw (`ModuleCapabilityDeniedError`), so a module reaching for the database fails
  during its own load rather than quietly getting a half-working handle.
- **Why a guarded container and not a new parameter.** The container keeps its type, so no module's
  `onLoad` signature breaks and a third-party module that already uses an allowed token keeps working.
  Enforcement is at runtime, which is where the capability is actually exercised.
- **Acceptance criteria.**
  1. A Standard module resolving `CORE_TOKENS.Db`, `CommandRegistry`, `Scheduler`, `EventBus` or
     `ModuleRegistry` throws `ModuleCapabilityDeniedError` naming the module, the tier and the capability.
  2. A Core module resolves the same tokens unchanged.
  3. `register` is allowed only for the module's own `module.<slug>.*` namespace.
  4. `freeze` / `createChild` / `createScope` are refused to Standard and Marketplace.
  5. Every token in `CORE_TOKENS` maps to a capability, and an unmapped token is unreachable by every
     tier — adding a token must not silently widen the surface.

### 3.2 MB-2 — isolation (implemented)

- **Defect.** Cross-module imports were banned with an escape hatch nothing implements; the core base
  was importable from a module package; nothing gave modules a sanctioned sharing channel.
- **Approach.** `global-data-emit.ts` implements the global data emit channel: `emit(topic, payload)` /
  `on(topic, handler)`, built on the internal event bus under the reserved `global.data.<topic>`
  namespace, with two structural properties — the payload is validated as JSON, so no function, class
  instance or database client can travel through it, and every delivery is stamped with the emitting
  module (`{source, topic, payload}`), so a subscriber can never address the emitter back. The internal
  event bus is not a capability any non-core tier holds, so a module reaches the shared channel and not
  the bus underneath it. `packages/modules/eslint.config.mjs` drops the escape-hatch wording and adds a
  `@workspace/dumby` ban, so the static half agrees with the runtime half.
- **Acceptance criteria.**
  1. A non-JSON payload is refused with `GlobalDataError`.
  2. A topic is one lowercase segment; the framework namespaces it.
  3. A delivery carries `source`, `topic` and `payload`, and the source cannot be supplied by a caller.
  4. A Standard or Marketplace module cannot resolve `core.EventBus` (no subscribing to internals).
  5. `packages/modules/eslint.config.mjs` bans `@workspace/dumby` and every other module package.

### 3.3 MB-3 — the tier entrypoints (implemented)

- **Defect.** `core.ts`, `admin.ts`, `standard.ts` and `marketplace.ts` were byte-identical.
- **Approach.** Each now states the tier's surface: core and admin re-export the full capability set and
  `ModuleRuntime`; standard and marketplace export `baselineCapabilities` and the runtime types only,
  with the withheld capabilities named in the file so a module author reads the boundary at the import.
- **Known limitation.** This is a documentary and ergonomic boundary, not a type-level one: a module can
  still annotate its own `onLoad` with the wider `ModuleRuntime` type, because the SDK's
  `defineModule<Container>` is generic. The load-bearing enforcement is MB-1's runtime guard. Closing the
  type-level half needs per-tier `defineModule` overloads and is a follow-up.

### 3.4 MB-4 — process ownership, provenance and termination (implemented)

**Implemented in a follow-up run of this record**, after the operator settled the four decisions below.
The approach below is the specification it was built to; §3.4.1 records what was built and how it was
verified.

**The four decisions (operator, 2026-10-27).** Termination is *cooperative* — an `AbortSignal`, with
re-arming stopped; a task that ignores the signal finishes its current await, because JavaScript cannot
pre-empt a running function. The process gate *fails closed* for module-owned work, like command
dispatch, recording `reason: 'state-unreadable'`. Cron tasks are *profile + guild scoped*, with
fleet-wide an explicit opt-in rather than the default.

#### 3.4.1 As executed

| Piece | File | What it does |
|---|---|---|
| one standing read | `apps/main/src/module-system/process-standing.ts` | `forGuild` / `forFleet`; core/admin never consult the row; unreadable state answers `state-unreadable` and refuses |
| the process register | `apps/main/src/module-system/process-registry.ts` | one row per live process with `{moduleId, name, kind, profileId, profileKind, guildId, trigger, enabledBy, enabledAt, startedAt, state}`; missing fields refused, an unknown enabler recorded as `provenanceComplete: false` |
| the cancellation contract | `apps/main/src/queue/base-processor.ts` | `execute(signal?)` and `process(job, signal?)`, both optional so no existing signature breaks |
| the scheduler | `apps/main/src/queue/scheduler.ts` | task scope (profile, guild, `fleetWide`), the standing gate, one controller per task, `terminateModule` / `resumeModule` |
| the queue | `apps/main/src/queue/queue-manager.ts` | the standing gate replaces the fail-open one; one in-flight controller per job; `terminateModule` |
| the wiring | `apps/main/src/bootstrap/bootstrap.ts` | both the worker and the main scheduler/queue pairs share one registry and one standing read, late-bound like the gates they replace, and refuse until the enablement read exists |

- **Defect.** A module's *processes* — cron tasks (`Scheduler`), queue jobs (`QueueManager`) and the
  loops a module starts in `onEnable` — are not held to the same registry, ownership and state model as
  its commands:
  - **Divergent gates.** Commands fail **closed** per guild; events and jobs fail **open** per guild;
    cron tasks are gated **fleet-wide** (`isModuleEnabledAnywhere`), which is a different question from
    "is it enabled for the profile and guild this process serves".
  - **No provenance.** A process does not carry `{profileId, kind, guildId, moduleId, enabledBy,
    enabledAt, trigger}`. The execution context carries the profile and guild for jobs, events and tasks
    (`execution-context.ts`), but not who enabled the module or when, and a fleet-wide task has no guild
    at all.
  - **No termination.** Disabling a module stops the **next** tick or dequeue. Work already running
    continues to completion — the opposite of the directive's "instantly".
- **Approach (in dependency order).**
  1. **One standing read.** Add `moduleProcessStanding(moduleId, {guildId, profileId})` beside
     `enablement.ts`, returning `{allowed, tier, enabledBy, enabledAt, reason}`. Every process surface
     reads it; the per-surface predicates collapse into it. Fail **closed** for module-owned process
     work (a skipped process is recoverable; work for a disabled module is not) — the same asymmetry
     `enablement.ts` already documents for commands, applied to processes.
  2. **A process record.** Add a `ProcessRegistry` holding one row per live process:
     `{moduleId, name, kind: 'task'|'job'|'loop', profileId, kind of profile, guildId, trigger,
     enabledBy, enabledAt, startedAt, state}`. It is the process-side counterpart of
     `guild_module_states` and is what the directive means by "just like commands and modules".
  3. **Cancellation.** Give `BaseTask.execute` and `BaseProcessor.process` an optional
     `AbortSignal` (`execute(signal?: AbortSignal)`); the scheduler owns one `AbortController` per
     registered task and the queue one per in-flight job. A disable signal aborts the controller, stops
     re-arming, and records `state: 'terminated'`. Modules that ignore the signal finish their current
     `await` — JavaScript cannot pre-empt a running function — so the contract is *cooperative
     termination with immediate re-arm suppression*, and the record must say so rather than promise a
     kill it cannot deliver.
  4. **The trigger.** Emit `module.state.disabled` on the internal event bus from the disable path
     (the same write that already drives BCCM deregistration and the `EventRouter` gate), and have the
     scheduler, the queue and the `ProcessRegistry` subscribe to it. That is a core-side subscription;
     no module gains the bus.
  5. **Provenance on the context.** Extend `ModuleExecutionContext` with `enabledBy` and `enabledAt`,
     read from `guild_module_states`, so a process can answer the directive's questions the way a
     command already can.
- **Acceptance criteria.**
  1. With the module disabled for the guild, a job dequeued for that guild does no work and records
     `skipped` with the reason.
  2. With the module disabled everywhere, a cron task does not fire, and one already running is
     aborted at its next `await` and not re-armed.
  3. Every live process row carries the full provenance tuple; a row missing one fails validation.
  4. Re-enabling restarts the process without a reload (§13.7 is unchanged: a per-guild toggle never
     touches the loaded state).
  5. The scheduler and queue unit suites pass, including a new case per acceptance criterion above.
- **Risk.** A fail-closed process gate turns an unreadable `guild_module_states` row into skipped work.
  The mitigation is the same one the command path uses: the read is a single indexed lookup, its failure
  is logged at `warn`, and the record carries `reason: 'state-unreadable'` so an operator can see it.

## 6. Dependencies, risks and rollback

### Dependencies

- **`feature/dev` write access.** Available through the GitHub connector's Git Data API (the `git` and
  `gh` credentials are read-only; see `UR-20261027-104`'s delivery note).
- **CI as the verifier.** No dependency tree is installed in the run environment, so `tsc` and `vitest`
  cannot run locally. Every type and test claim in this record rests on the CI run for the pushed commit.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A first-party module resolves a token the guard now denies | low | high | none of the eight uses the container it is handed (`onLoad()` takes no argument); the guard's denial is a named throw, so CI's module tests would fail loudly rather than silently |
| A third-party module relies on the container for something outside the baseline | medium | high | the baseline covers presentation and plumbing; a module needing more is asking for the core base, which is the policy. The refusal message names the capability and points at the data channel |
| The Proxy diverges from `Container` for a method added later | low | medium | the guard delegates every unlisted member to the real container for privileged tiers and refuses it for the rest, so a new method is denied by default rather than leaked |
| MB-4 lands late and processes stay un-wired in the meantime | high | medium | recorded as not implemented, specified in §3.4, and carried in the change-log as open work |

### Rollback

- Each step is one atomic commit with an item ID in its body; `git revert <sha>` undoes exactly one.
- No file is deleted. The loader change is four lines; reverting it restores the raw container.
- Nothing is irreversible and no force-push is involved.
