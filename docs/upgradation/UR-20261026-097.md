# UR-20261026-097 — Runtime Ownership and Command-Path Truth

**Identity:** UR-20261026-097 · **Version:** 1.0 · **Date:** 26/10/2026 · **Requester:** operator-directed

**Freeze status:** **Open — raised 2026-10-26.** A new record under its own id; it edits no frozen record.

**Basis.** An operator test pass across `/dashboard`, `/health`, `/browse`, `/modules` and `/hello` on
two profiles (the internal profile and one Twilio-registered persona) in one guild, reported as a
sequence of contradictory readings: a module shown as "occupied by Dumby Profile" on `/browse` while
the main bot neither held nor listed it; `/health` and `/dashboard` disagreeing about which profile
held it; a disable that de-registered `/hello` from Discord instead of restricting it; and a refusal
notice that carried neither an accent nor privacy.

**What the boot log settles.** The disagreement is in the READS, not in the stored state. At boot the
runtime prints the three facts that can disagree:

```
module-state guildId=1062427177326497863 moduleId=hello-world tier=standard
  enabledBy=7a498256-… binding=7a498256-… resolvedOwner=7a498256-… agrees=true
```

`enabledBy`, `binding` and `resolvedOwner` all name the persona, and `agrees` is true. So the state of
record was consistent and correct; four independent *readers* of that state were not. That reframes
every finding below: none of them is a data-corruption bug, and none is fixed by repairing rows.

## 1. Objective and rationale

Make one ownership fact produce one answer on every surface, and make a module disable do what the
specification already says it does. Two of the five findings (RT-1, RT-4) are the direct cause of the
operator's most damaging observations — a frozen holder and a de-registered command — and RT-4 is a
code-versus-specification divergence, not a design question: `spec/request-layer/command-framework-routing-engine.md`
§17.7 already states that a disable's command removal "never take[s] effect immediately at the
registration layer" and is "entries in one shared queue table". The code added a third, immediate path.

## 2. Findings and residuals to resolve

| # | Residual | Sev | Where | Corrective action |
|---|---|---|---|---|
| RT-1 | The holder of a module was memoised in a `Map` declared beside the page-data provider, so the answer was frozen for the life of the PROCESS — nothing ever invalidated it | high | `rendering/page-data.ts`, `holderOf` | delete the memo; read fresh per call; log a failed read instead of silently answering `undefined` |
| RT-2 | `/browse` computed `occupied` as `!ownedBy(...)`, which is true both for "another profile holds it" and for "nobody holds it", and then coerced that "nobody" into the internal profile for the label | high | `rendering/page-data.ts`, `marketplace` | require a defined holder for `occupied`; label from that holder only |
| RT-3 | A hosted persona's `/health` counted from her runtime registry while `/modules` and `/dashboard` counted from ownership, so her standard-tier count read 0 while a page was drawn for one | medium | `rendering/page-data.ts`, `health` | use the ownership read for the held set on every profile; keep the runtime registry as fallback only |
| RT-4 | A disable DELETED the module's guild commands whenever the permission override applied zero — which is what an absent Bearer token returns, and that token defaults to empty | high | `bootstrap/bootstrap.ts`, `setModuleCommandAccess` | remove the third path; a disable is the instant restrict plus the queued BCCM removal, and nothing else |
| RT-5 | The refusal notice declared `ephemeral: true` but is delivered through `editReply` on a publicly acknowledged interaction, so it carried the private grammar (no accent, no footer) on a channel-visible message | medium | `bootstrap/bootstrap.ts`, `moduleRefusalNotice` | declare the grammar it is delivered with; record the private refusal as a follow-up |

## 3. Implementation approach

- **RT-1** — `holderOf` becomes a straight `resolveOwner` call. The memo saved at most a handful of
  duplicate reads inside one render, and the callers already await in parallel. A throw is now logged
  as `page-data-owner-read-failed` rather than swallowed: "unreadable" and "nobody holds it" are
  different facts and conflating them is what produced RT-2's symptom.
- **RT-2** — `occupied = !mine && holder !== undefined && guildEnabled`, with `mine` read once and
  reused. The label is built from `holder` alone, so a `undefined` holder can no longer be named as
  the internal profile. `MAIN_PROFILE_ID` still labels the main bot when it genuinely holds the module.
- **RT-3** — the held set comes from `heldModulesInGuild` (the ownership read) for every profile;
  `acting.moduleSlugs` is the fallback only when that dependency is absent. Inventory is ownership;
  the runtime registry is what is *loaded*, which is a different question.
- **RT-4** — delete the `applied === 0 && !allowed` branch and its `deleteGuildCommands` call, and
  drop the two imports it orphaned. The consequence is deliberate and is the specification's own
  behaviour: with no Bearer token, a disabled module's command stays REGISTERED and the router refuses
  it with `MODULE_DISABLED` — "switched off in this server" — instead of the command vanishing and
  producing `UNKNOWN_COMMAND`.
- **RT-5** — `ephemeral: false` on the refusal notice. The message is public either way; this makes the
  grammar match the delivery, so it gains the framework accent instead of silently dropping it. A
  genuinely private refusal needs the install control acknowledged with `ack: 'ephemeral'`, which would
  also make the post-install page private — a designed follow-up, not a one-line change.

## 4. Acceptance criteria and definition of done

- **ACC-UR-20261026-097-1** — a module the resolver reports as unheld is offered on `/browse`, is not
  marked occupied, and names no profile.
- **ACC-UR-20261026-097-2** — two consecutive `/browse` renders with a changed holder report the
  second holder; no answer survives a render.
- **ACC-UR-20261026-097-3** — a hosted persona whose runtime registry is empty still has her
  standard-tier count reported from ownership on `/health`.
- **ACC-UR-20261026-097-4** — `setModuleCommandAccess` contains no command deletion: a disable writes
  the override, enqueues the change, and leaves the registration intact.
- **ACC-UR-20261026-097-5** — the refusal notice declares `ephemeral: false`.
- **ACC-UR-20261026-097-6** — the corpus gate suite is **30/30 green** after the change.
- **ACC-UR-20261026-097-7** — `git branch --show-current` prints `feature/dev` before every commit.

## 5. Dependencies and risks

- **Depends on** the ownership resolver (`resolveCommandOwner`) remaining the single source of truth.
  Every finding here is a reader that bypassed or cached it.
- **Risk — with no `DISCORD_COMMAND_PERMISSIONS_TOKEN`, a disable is no longer instant on the Discord
  side.** The command stays visible until the BCCM push runs. That is §17.7's model and the operator's
  stated intent, but it is a behaviour change for a deployment that had come to rely on the deletion.
  Provision the token to get the instant restrict.
- **Risk — RT-3 changes what a hosted persona's `/health` reports.** A persona whose runtime registry
  disagreed with ownership will now report the ownership answer. Where the two disagreed, the previous
  number was the wrong one.
- **Risk — RT-5 does not make the notice private.** It makes it honest. The privacy defect is recorded
  as a follow-up in §7 rather than half-fixed.
- **Risk — the application toolchain was not run in this sandbox.** No pnpm workspace install was
  possible (Node 20.20.2 against a Node ≥ 22 requirement) and the bundled `esbuild` panics here, so
  the new unit tests were NOT executed locally. They are written to run in CI, and the code changes are
  verified by CI, not by a local run. `tsc` was run on both edited sources and reported no error on any
  edited line — only the expected missing-`@types/node` and unresolved-import diagnostics.

## 6. Rollback and mitigation

- Each concern is a separate atomic commit on `feature/dev`; revert any one with `git revert <sha>`.
- RT-4 is the only change with an operational consequence. Reverting it restores the immediate delete
  for deployments that want it; no data is written by either version.
- RT-1 and RT-2 are pure reads. Reverting them restores the contradictory display, not lost state.
- No force-push, no history rewrite, no protected-branch change is involved.

## 7. Out of scope

- **A genuinely private refusal notice.** It needs the install control to be acknowledged with
  `ack: 'ephemeral'` (or a dedicated `customId` prefix), which changes the post-install page from a
  public edit-in-place to a private reply. That is a designed follow-up with its own acceptance test.
- **`UR-20261012-030`'s Route B decision.** That record is a request record and is not edited. RT-4
  supersedes its Route B row; the record stands as history, and its own listed risks — the daily
  create-quota spend on re-enable, and the command id changing so earlier permission overrides do not
  follow — are corroboration for this reversal rather than casualties of it.
- **`/hello` still answering on the main bot when a persona holds the module.** This is intended and
  documented at `commands/command-router.ts`: registration is where ownership is enforced, and the
  router logs `command-scope-owned-elsewhere` rather than refusing a registered command. No change.
- **The BCCM push cadence.** A queued removal lands on the batch's own schedule. Shortening it is a
  separate decision about Discord's 200-per-day guild-command creation limit.
