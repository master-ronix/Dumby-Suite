# UR-20261012-084 — A Revoked Persona Kept Its Application Id Forever

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.89` entry in `upgradation/change-log.md`).

---

## 1. The finding

Re-registering the persona's own application after a revoke failed:

```
duplicate key value violates unique constraint "persona_identities_discordapplicationid_unique"
```

The persona had been revoked — retired, soft-deleted, absent from every read. Its application id was
still taken. `20260101000034_align_persona_model` declared the column with a **plain** `.unique()`:

```ts
table.string('discordApplicationId').notNullable().unique();
```

A plain unique constraint constrains **every row**, including soft-deleted ones. So revoking a persona
made its application permanently unregistrable: the row was gone from the operator's view and its key
was still held. The only way to reuse an application was to hard-delete the row, which the revoke does
not do and should not need to.

**This is a documented behaviour that was never true.** UR-20261012-081 states that a revoked persona's
"application id becomes free to register again, which is the difference between 'revoked' and
'temporarily switched off'". That sentence was written from intent, not from the schema, and it was
false. UR-081 now carries a correction note rather than a silent edit.

## 2. The mechanism

- Soft delete is the corpus's mechanism for removal: `addSoftDelete` sets `deletedAt`, and every read
  filters on it.
- Uniqueness on a soft-deletable table must therefore be **partial** — unique among live rows only.
- The corpus already has exactly this: `createPartialUniqueNotDeleted(knex, table, columns)` builds a
  unique index `where "deletedAt" is null`, and it is used by `guild_members`, `guild_roles`,
  `guild_module_states` and others.
- `persona_identities` never got it. Its application id was declared with a plain constraint at a point
  when the table had just been realigned, and the partial-index helper was not applied.

## 3. What changed

Migration `20260101000052_persona_application_id_partial_unique`:

- **Creates the partial unique index first**, then **drops the plain constraint**. The order matters:
  there is never a window in which an application id is unconstrained.
- `down()` restores the plain constraint and drops the partial index.

No application code changed. The read and write paths were already correct; the schema was not.

## 4. Verification

Verified against a real PostgreSQL, not by inspection. The migration was applied through
`knex.migrate.latest()` and the schema and behaviour were then asserted directly:

- the index on `discordApplicationId` is `... WHERE ("deletedAt" IS NULL)`;
- zero unique **constraints** remain on the table;
- a soft-deleted persona's application id **can** be registered again;
- a second **live** persona with the same application id is **still refused**.

Both directions matter: the first is the fix, the second is the property the plain constraint was there
to provide and which the partial index must preserve.

## 5. Acceptance criteria

- **ACC-UR-084-1** — a soft-deleted persona's application id can be registered again.
- **ACC-UR-084-2** — a second LIVE persona with the same application id is still refused.
- **ACC-UR-084-3** — no plain unique constraint remains on `persona_identities.discordApplicationId`.
- **ACC-UR-084-4** — the migration is reversible.

## 6. Recorded

**A claim about behaviour that is not checked against the schema is a guess with a confident tone.**
UR-081's sentence read as a statement of fact and was written as one. It was never tested, because no
test could have caught it: the API returned `204`, the list came back empty, and the only way to
discover the falsehood was to try to register the application again — which is what the operator did.

**Soft delete and uniqueness have to be designed together.** Any unique key on a soft-deletable table
is a decision about what happens after deletion, and "unique" defaults to a decision nobody made. The
corpus has the right primitive; this table simply predated its use. A sweep for `.unique()` on
soft-deletable tables is the mechanical follow-up.

**The sweep was done, and this was the only instance.** Every other plain `.unique()` in the migration
corpus — `signing_keys.keyId`, `sealed_credentials.credentialId`, `developers.username` — is on a table
that is **not** soft-deletable (no `addSoftDelete`), where a plain unique constraint is exactly right: an
immutable key is never superseded, so there is no post-deletion question to answer. The bug needed two
things together — a soft-deletable table and a unique key — and `persona_identities` was the only place
they met.

**The verification is the deliverable here.** This migration is four lines of SQL. It was proved by
booting a real PostgreSQL, running the real migration chain, and asserting both directions of the
constraint — because the failure mode being fixed is precisely a schema assumption that nobody checked.
