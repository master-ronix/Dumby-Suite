# UR-20261026-100 — A Module and Its Commands Are One Bound Pair

**Identity:** UR-20261026-100 · **Version:** 1.0 · **Date:** 26/10/2026 · **Requester:** operator-directed

**Freeze status:** **Open — raised 2026-10-26.** A new record under its own id; it edits no frozen record.

**Basis.** The operator's ruling, verbatim in substance: *"Obviously main bot will refuse when persona
holds the module and the command will be registered for persona at guild only scope. Module & Command
are joint bounded and associated to each other. Wherever the module is and what's state of module
decides how command calling deployment registration will be working."*

That reverses a deliberate earlier decision. `command-router.ts` used to log
`command-scope-owned-elsewhere` and **proceed**, on the theory that registration is where ownership is
enforced, so a command that is registered for this application is one the profile may answer. The
operator has settled it the other way.

## 1. Objective and rationale

Make dispatch obey the same ownership rule that registration already obeys, and stop the two from
disagreeing.

The deployer already registers a guild-scoped module's commands for its **holder only**, at guild
scope, and suppresses the internal profile in a guild where a hosted persona answers. Dispatch was the
one place that did not apply the rule — so a stale, renamed, or carried-over registration let the main
bot answer a persona's module. That is the "no single owner of a command" shape the operator keeps
hitting: registration said one thing, dispatch another.

## 2. Findings and residuals to resolve

| # | Residual | Sev | Where | Corrective action |
|---|---|---|---|---|
| RT-8 | Dispatch logged `command-scope-owned-elsewhere` and answered anyway, so a profile that does not hold a module could still run its commands whenever a registration was stale | medium | `commands/command-router.ts`, `assertPersonaOwnsCommand` | refuse with the neutral `out-of-scope` cause; the holder still answers |
| RT-9 | The command-permission authorization (the only route to instant command hiding) was undocumented outside code comments, so an operator could not tell it from the static env fallback | medium | `apps/main/docs/runbooks/` | add a runbook covering the redirect registration, the connect URL, verification, the per-persona case and token lifetime |

## 3. Implementation approach

- **RT-8** — `assertPersonaOwnsCommand` throws `CommandScopeDeniedError` with the **neutral**
  `'out-of-scope'` cause when the resolver names a different profile. Neutral on purpose: this is
  neither a permission failure nor a disabled module, and reporting either would send the member to
  the wrong fix. Core and admin keep their existing short-circuit (`'shared'`), so no persona is
  refused a core command. The holder is unaffected: her own id is the owner, so the command is hers.
- **The test that encoded the old decision is reversed, not deleted.** It becomes "the main bot REFUSES
  a module a persona holds", with a companion test proving the holder still answers. The audit trail is
  the product; a silently deleted test would hide the reversal.
- **RT-9** — `apps/main/docs/runbooks/command-permission-authorization.md`. It is application-local and
  non-normative, like `module-deployment.md`, and it separates the three things that look alike: the
  **install** flow (`bot=1`, no user token), the **connect** flow (`/auth/authorize?guild=…`, which
  yields `applications.commands.permissions.update`), and the **static fallback**
  (`DISCORD_COMMAND_PERMISSIONS_TOKEN`, internal profile only, never refreshed, cannot serve a persona).

## 4. Acceptance criteria and definition of done

- **ACC-UR-20261026-100-1** — the main bot does not execute a command whose module a persona holds, and
  answers with the neutral "not available in guild" notice rather than the unreadable-state notice.
- **ACC-UR-20261026-100-2** — the profile that holds the module still executes it.
- **ACC-UR-20261026-100-3** — a core or admin command is never refused by this path.
- **ACC-UR-20261026-100-4** — the command-permission authorization runbook exists and states the
  redirect registration, the connect URL, the verification query and log line, the per-persona

- **ACC-UR-20261026-100-5** — the corpus gate suite is **30/30 green** after the change.
- **ACC-UR-20261026-100-6** — `git branch --show-current` prints `feature/dev` before every commit.

## 5. Dependencies and risks

- **Risk — this is the second reversal of this exact line.** It previously threw, was changed to log
  and proceed because a throw produced "FORBIDDEN for a working module", and now throws again on the
  operator's instruction. The difference from the first version is scope: core/admin still short-circuit,
  and the refusal carries the neutral cause, so the notice no longer reads as a permissions bug.
- **Risk — a stale registration now fails visibly.** A member invoking a command their profile no
  longer owns gets a refusal instead of a working command. That is the intended trade: the deployer's
  registration is the primary control, and this is the guard against it lagging.
- **Risk — CI cannot verify this.** Every Actions job on `feature/dev` is refused at start by an account
  billing block (`UR-20261026-099`), so the changed unit tests will not run until that is resolved. The
  change was verified by reading and by `tsc` against the edited file only.
- **Not verified:** the runbook's redirect-registration step is a Discord-portal action that no API can
  read back; the runbook says so rather than implying the app can check it.

## 6. Rollback and mitigation

- One atomic commit; `git revert <sha>` restores the log-and-proceed behaviour and its original test.
- No data is written by this change; it decides whether an already-registered command executes.
- No force-push, no history rewrite, no protected-branch change is involved.
