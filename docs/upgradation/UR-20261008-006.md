## 2. The Identity Model

Four identifiers, distinct in source and in surface:

| Field | What it is | Issued by | Surface |
|---|---|---|---|
| `devId` | the registered developer identifier | the Credentials Service at developer registration (§15.6) | **never user-facing** — as sensitive as a bot token (§32.12) |
| `buildId` | the identifier of one uploaded version | Swastik, per accepted version (§15.8) | the footer, first field |
| `devName` | the developer's display name | the account registry (from `devId`) | the attribution line: `Developed by <devName>` (§1.5) |
| `devUsername` | the developer's registered @handle | the account registry (from `devId`) | the footer: `<buildId> · @<devUsername>` |

**Workflow.** A user registers on the Dumby website with a display name, a unique username and a password (optionally email-linked). To publish modules they switch to a developer account through the developer portal, and the Credentials Service issues a `devId` (public) and a dev token (private). A license is bound to the `devId`; a module manifest's `devId` must equal the license's subject. On upload, Swastik assigns a fresh `buildId` and signs the full provenance tuple.

## 3. Requested Changes

1. The title attribution is the developer's **name** (`Developed by <devName>`), per §1.5 — not the @handle.
2. The footer carries the **`buildId`** and the registered **@handle** (`<buildId> · @<devUsername>`).
3. The raw **`devId` is never rendered** on a user-facing surface; an unregistered `devId` falls back to the framework developer, not to the identifier.

## 4. Acceptance Criteria

- The attribution names the developer; the @handle appears only in the footer.
- No surface prints a raw `devId`.
- The documentation gate suite stays green.
