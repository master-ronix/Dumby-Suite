## 1. Summary

Deployment is documented in two places that disagree, and the document describing the path actually
in use is the one document outside the corpus. `spec/lifecycle/infrastructure-deployment.md` presents
Kubernetes as the reference production topology; `deploy/railway.md` describes a Railway deployment
and is unclassified and ungated; the runtime's environment-variable surface is not enumerated
anywhere. This request brings the deployment documentation into the corpus, reconciles the two
topologies, and enumerates the environment surface.

## 2. Business / engineering justification

An operator following `spec/lifecycle/` would provision Kubernetes; the live system runs on Railway.
The corpus records this only as an *unverified surface* (OI-3), never as a *documentation* divergence,
so a reader cannot tell which topology is authoritative. Meanwhile `deploy/railway.md` — the doc that
matches reality — is the only `/docs` file with no front-matter, no manifest entry, and no gate, so it
can drift from the config it describes with nothing to catch it. And the runtime sets variables
(`SWASTIK_LIVE_VOLUME_PATH`, `SWASTIK_STAGING_VOLUME_PATH`) that appear in no live document.

## 3. Scope & impact

- **In scope:** `deploy/railway.md` (front-matter + classification); `manifest.json`; `check-frontmatter`
  globs; the K8s-vs-Railway statement in `spec/lifecycle/infrastructure-deployment.md`; an
  environment-surface list; the new `audits/` directory.
- **Out of scope:** rewriting the deployment content; changing the runtime.
- **Audiences affected:** operators; maintainers; the gate suite.

## 4. Current state (evidence)

- `deploy/railway.md`: no front-matter; absent from `manifest.json`; not scanned by `check-frontmatter`
  (globs `spec blueprint documentation adr upgradation`); referenced by no gate or ledger (DA-3).
- `spec/lifecycle/infrastructure-deployment.md` §41.2/§41.3 describe Kubernetes; L155–156 name the K8s
  manifests as deploy artifacts; L74 `livenessProbe → /health/liveness`. `change-log.md` OI-3 records
  "Railway is not a cluster" (DA-7).
- `deploy/railway.md` enumerates only six bot variables; `SWASTIK_LIVE_VOLUME_PATH` is absent from the
  live corpus and `SWASTIK_STAGING_VOLUME_PATH` appears only in `archive/v4.5.1/` (DA-9).
- **[Reported]** the runtime healthcheck is `/health/liveness`; the doc mentions only the api-server's
  `/api/healthz` (R-5).

## 5. Proposed change

1. Add front-matter to `deploy/railway.md` (`kind: documentation`, `status: derived` or an extended
   enum) and a `deploy/` entry to `manifest.json`.
2. Add `deploy` to `check-frontmatter`'s globs.
3. Classify the new `audits/` directory so it is not a second unmanaged tree.
4. **Reconcile the topologies (DA-7).** State in `spec/lifecycle/infrastructure-deployment.md` which
   topology is the reference and which is in use; mark K8s as a target (not the current path), or
   document the Railway path there, and cross-link `deploy/railway.md`.
5. **Enumerate the environment surface (DA-9).** List the runtime variables (incl. the Swastik
   volume-path variables) in the deployment doc or a config contract.
6. **Validate the doc against the deployed config (R-5).** Add a check that the doc's claims — watch
   patterns, volume mount, healthcheck path, variable names — match the deployed configuration where
   that is reachable read-only.

## 6. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|

| `audits/` becomes unmanaged | High | Classify it in this request |

## 7. Rollback / reversal plan

Remove the front-matter and manifest entry; revert the spec wording. Content is otherwise unchanged.
