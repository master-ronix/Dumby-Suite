## 1. Summary

The `/modules` command is the module-management surface. Three prior requests
(`UR-20261011-009/010/011`) specified its current arrangements — the fallback-logo/decoration split,
the inline ephemeral Info card, the developer-by-name rule, and the full disable/enable enforcement.
The operator reports that the landed implementation **does not honour them**: the white square is
being used as the fallback icon (it is the command decoration), the Info card is divided and shows a
raw `dev_first_party` developer token, the Home control returns to the dashboard instead of
`/modules`, and a "disabled" module stays listed, keeps its registered commands, keeps its dashboard
page, and never relists in `/browse`.

This is therefore a **correction + enforcement** request. It re-states the specified behaviour as
binding, fixes the presentation, and makes disable actually terminate per-guild processing through
the documented mechanisms (deny override, BCCM, dispatch gate) — nothing invented, nothing
misinterpreted.

## 2. The directive (formalised)

### 2.1 Corrections

- **R1 (c1) — Fallback logo vs command decoration.** A module that declares no `ui.icon` MUST show
  the framework **fallback logo** (`module-fallback-icon.png`, `dumby_module_fallback`) — a **newly
  generated** default asset. The white-square asset (`dumby_module`) MUST NOT be used as a logo
  fallback: it is the neutral **command decoration** rendered beside each command on the dashboard's
  **module-specific page** (§9.10).
- **R2 (c2) — Listing legibility.** Each module row MUST render its name, a **title-cased tier**
  label and a clean description (`-#` subtext) — not the current vague/malformed labels (§9.10).
- **R3 (c3) — Controls placement.** The standalone per-module Uninstall/disable button rows MUST be
  removed. The per-module **Info** control MUST sit **in-line after each module** in the listing (a
  Section accessory), **not** below the footer (§9.10).
- **R4 (c4) — Uninstall/disable relocation and icon.** The uninstall/disable control MUST live
  **inside** the module Info card, as an **icon-only** control (a newly generated bold white icon,
  `dumby_uninstall`, **no label**), and MUST be **disabled** for a core-tier module and for an
  uninstalled/disabled marketplace-tier module (§9.10).
- **R5 (c5) — Navigation consistency.** The `/modules` navigation MUST match the other surfaces —
  an icon-only **Home** plus **Next page** / **Previous page**, title-cased labels, a control
  disabled at its bound (§9.10).
- **R6 (c6) — Info is always ephemeral.** The Info card MUST render **hidden (ephemeral) always** —
  never as a public message (§9.10).

### 2.2 Updates

- **R7 (u2) — Home target.** The `/modules` **Home** control MUST return to **`/modules` page 0**
  (this surface's own main view), **never** the dashboard (§9.11).
- **R8 (u3) — Info density.** The ephemeral Info card MAY render at **medium density (Mode M)** or
  **compact density (Mode C)** — the operator's latitude. Either way it is a **single content
  block** (§9.11, §1.4).
- **R9 (u4) — Info formality.** The Info card MUST read as one formal, professional block — **no
  per-field dividers or separators** (§9.11).
- **R10 (u5) — Meaningful content.** Every field on the Info card MUST be meaningful: name + tier,
  description, developer, version, status, and the command inventory — no filler, no raw tokens.
- **R11 (u6) — Developer by name.** The developer MUST be resolved **by name**; a framework-shipped /
  first-party module attributes to **Quixotic Mnemonics** (its `devId` is `qm-dev-001`). The raw
  `devId` / `dev_first_party` MUST NEVER be shown as the developer (§9.11, §1.5).
- **R12 (u7/u8) — Disable/enable enforcement.** Disabling a **Standard** module MUST actually
  terminate the module's **per-guild processing** and demote it to the marketplace as **"Previously
  installed"**; enabling MUST be functional from `/browse` through the install dropdown. The
  mechanism is the documented one: an **instant `@everyone` deny override** via Discord's per-guild
  command-integration permissions API (§17.6), a **BCCM** enqueue of the module's commands for the
  actual deregistration (§17.7), and an **`EventRouter` dispatch gate** so the disabled module's
  handlers stop firing (§13.2/§13.7). Enabling is the inverse (clear the override + BCCM
  re-registration).
- **R13 (u9) — No control on core.** A **core** module's Info card MUST render **no**
  uninstall/disable control (§9.11, §13.2).

### 2.3 Current status (observed violations — the acceptance target)

- **S1** — the Info card says a module is disabled, yet the module is still listed in `/modules`
  (violates R12/§9.12 listing exclusion).
- **S2** — the Info card says a module is disabled, yet its command stays **registered/loaded** in
  the guild; the module's processing is not terminated (violates R12/§9.12).
- **S3** — the disabled `hello-world` still has its **dashboard page** registered (violates
  R12/§9.12 dashboard gating).
- **S4** — the disabled module is **not offered in `/browse`** to install back (violates
  R12/§5.17).

## 7. Risks & open questions

- **Fleet-wide work is not per-guild (must not be misread).** The directive says "all processing …
  including monitoring, schedule, queue, listening to event … any kind of functionality" must
  terminate. The specification's honest boundary is narrower: a per-guild toggle terminates the
  module's **per-guild** processing — its **commands** (deny override + BCCM + dispatch gate) and its
  **event handlers** (dispatch gate). A **cron task or BullMQ job is fleet-wide, not per-guild**
  (§29.6) and is **not** stopped by a guild admin's toggle; that is the **unload** path (§13.7) or a
  global disable. This record does not widen the toggle beyond §13.7; if the operator intends a
  true fleet-wide teardown on a per-guild disable, that is a **separate specification change** and
  must be raised as its own request.
- **Configured roles.** The deny override here writes the `@everyone` deny; the spec also names "each
  configured role" (§17.6) — those follow the same shape and are a follow-on.
- **Developer name source.** R11 needs the developer's display **name**, which is not a manifest
  field today; the resolver must map first-party → "Quixotic Mnemonics" and third-party → a
  registered name. The mapping source is an open implementation detail.
- **Interaction paths need a live run.** Deny override, BCCM and the dispatch gate require live
  Discord + Redis; the corpus gates cover the documentation, not the interaction.
