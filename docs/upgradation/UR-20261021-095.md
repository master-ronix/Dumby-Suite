# UR-20261021-095 — Production Readiness — CI Deploy-Blocker, Module-Deployment Pathway, Twill Client-Secret Requirement

**Identity:** UR-20261021-095 · **Version:** 1.0 · **Date:** 21/10/2026 · **Requester:** operator-directed

**Freeze status:** **Open — raised 2026-10-21.** A new record under its own id; it edits no frozen record.

**Basis.** Three production-readiness residuals raised by the operator, plus the CI deploy-blocker that
kept production at `416864b`. The Railway deployment runs from `feature/dev` with `checkSuites: true`,
so a red CI blocks every deploy — the reason production never advanced past `416864b`.

## 1. Objective and rationale

Make `feature/dev` deployable again, make the module-deployment pathway complete and non-bypassable,
and make the Twill registration API require its credentials like the bot token. Production is a
service that has been unable to advance; this record closes the blockers and the named gaps.

## 2. Findings and residuals to resolve

| # | Residual | Sev | Corrective action |
|---|---|---|---|
| PR-1 | CI red on `feature/dev` — the fail-fast gates job died at Gate 3b, so no commit after `416864b` could deploy | S1 | drop the retired `SWASTIK_LIVE_VOLUME_PATH` from the ConfigMap + env surfaces |
| PR-2 | Gate 4 + the modules contract suite red — `buildId` removed from the manifest (UR-20261019-103) but fixtures still carried it | S1 | remove `buildId` from every manifest fixture; assert it is rejected |

## 3. Implementation approach

- **PR-1** — remove `SWASTIK_LIVE_VOLUME_PATH` from `apps/main/deploy/k8s/base/configmap.yaml`,
  `apps/main/.env.example`, `apps/main/docker-compose.yml`, `deploy/railway/testing.env.example` and
  the config-service test fixture. Verified by `check-configmap-keys`.
- **PR-2** — remove the `buildId` field from the manifest fixtures in the 4 unit files, 3 modules
  spec files, the flow module fixture and 3 further fixtures; assert an author-declared `buildId` is
  rejected; make the two quote-coupled schema specs quote-agnostic.
- **PR-3** — `tests/flow/flow-env.ts` generates an ephemeral Ed25519 keypair and arms the verifier;
  `tests/flow/harness.ts` gains a `beforeBootstrap` hook; `module.flow.test.ts` signs its fixture and
  seeds the `developers` + `builds` rows the loader reads.
- **PR-4** — add `POST /internal/developers/:devId/approve` and `POST /internal/developers/:devId/decline`
  to `src/entry/swastik.ts`; the `/internal/*` prefix is `INTERNAL_API_KEY`-gated by the Swastik route
  policy. Approve activates the licence (`pending → under-review → approved`); decline revokes it.
- **PR-5** — `src/personas/twill-registration.ts`: `parsePersonaRegistration` requires
  `oauthClientSecret`; the credential-rotation route requires it too.
- **PR-6** — the runbook (application-local, non-normative).

## 5. Dependencies and risks

- **Depends on** the UR-20261019-101…104 code track being on `feature/dev` (it is).
- **Risk — a signing key is now required to boot.** Any deployment without `BUILD_SIGNING_*` fails at
  boot. Production must configure a keypair (`apps/main/scripts/gen-l2-key.sh`).
- **Risk — Option A ships no modules.** A deploy of the current branch ships an image with no modules;
  the tier volumes must be populated with `build:modules` + `push:modules`, or the bot serves nothing.
  This is the operator/Railway step that satisfies PR-6's "latest bot alive with modules".
- **Risk — the app toolchain was not run in the corpus sandbox** (no pnpm workspace / Node 22). The
  code changes are verified by CI, not by a local app run.

## 6. Rollback and mitigation

- Each change is a separate atomic commit on `feature/dev`; revert any one with `git revert <sha>`.
- The approval endpoints are additive; removing them restores the prior (un-approvable) state.
- Making the client secret required is reversible by restoring the prior `parsePersonaRegistration`
  and the rotation route.
- No force-push, no history rewrite, no protected-branch change is involved.
