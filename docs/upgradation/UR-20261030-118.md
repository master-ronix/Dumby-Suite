# UR-20261030-118 — Module-Provided Services

**Identity:** UR-20261030-118 · **Version:** 1.0 · **Date:** 30/10/2026 · **Requester:** operator directive

**Freeze status:** **Open — raised 2026-10-30.** It edits no frozen record.

## 1. The one thing UR-20261027-106 could not move

UR-20261027-106 moved every module surface that a **request** touches: pages, renderer schemas,
commands, assets, icon sets and tests. `REC-040` records what is left, and it is one item:

| file | lines | what it is |
|---|---|---|
| `apps/main/src/personas/twill-registration.ts` | 917 | the persona's Twill registration |
| `apps/main/src/personas/persona-runtime.ts` | 613 | spawning and owning bot clients — **framework** |
| `apps/main/src/personas/persona.ts` | 510 | the persona domain model |
| `apps/main/src/personas/persona.repository.ts` | 346 | the persona's own tables |
| `apps/main/src/personas/persona-command-binding.service.ts` | 317 | binding commands to a persona |
| `persona-oauth.ts`, `persona-invite.ts`, `persona-presence.ts`, `persona-credentials.ts`, `persona-registrar.repository.ts`, `profile-label.ts`, `application-ownership.ts` | ~600 | the rest of the domain |

`persona-runtime.ts` is correctly the framework's: it spawns a bot client per persona and serves every
persona, so it belongs to no single module. **The domain — roughly 2,000 lines — is the persona
module's**, and it cannot move as a file move. The measurement that settles this:

```
$ for f in apps/main/src/personas/*.ts; do ... grep outside apps/main/src/personas ... done
persona                      : apps/main/src/bootstrap/bootstrap.ts, apps/main/tests/...
persona.repository           : apps/main/src/bootstrap/bootstrap.ts, apps/main/src/entry/twill.ts
persona-command-binding.service : apps/main/src/bootstrap/bootstrap.ts, apps/main/src/di/tokens.ts, apps/main/src/entry/twill.ts
persona-registrar.repository : apps/main/src/bootstrap/bootstrap.ts, apps/main/src/entry/twill.ts
```

The **core imports the domain statically at boot**, and modules load dynamically through the manifest
contract. A static import of a module package from the core would invert the dependency and break the
plugin model: the core would have to know a module exists. That is why this is not a refactor.

## 2. The seam that already exists

The framework already has the mechanism; nothing uses it for a *service*:

- `apps/main/src/module-system/loader.ts:300-305` — `onLoad` receives
  `withModuleCapabilities(container, { moduleId, tier, globalData })`, a **guarded** container. A module
  can already call `register` and `resolve` through it.
- `apps/main/src/module-system/registry.ts:28-54` — `LoadedModule` already declares `jobs`, `events`,
  `tasks` and `pages` as module-owned surfaces; the loader copies each one.
- `apps/main/src/di/container.ts:60,97` — `register<T>(token, factory)` and `resolve<T>(token)`.

So a module **can** provide an implementation today. What does not exist is the discipline: a token the
core declares, a right to register it that the manifest must grant, and a resolution point that is
lazy — after the modules have loaded, not at import time.

## 3. The request

**R1 — a service contract the core declares and a module implements.** For each service the core needs
from a module, the core declares a token in `apps/main/src/di/tokens.ts` and an interface in a
framework-owned file. The core resolves the token; it never imports the implementation.

**R2 — the right to register is granted by the manifest, and enforced.** A module may register only
the service tokens its manifest declares:

```json
{ "provides": [{ "token": "core.PersonaService", "version": 1 }] }
```

`withModuleCapabilities` refuses a `register` for any token the module did not declare, loudly, the way
it already refuses a `resolve` outside the module's tier. The `provides` field exists in the manifest
schema today and is **declared and never wired** — `REC-039` records exactly that. This request wires it.

**R3 — resolution is lazy and fails visibly.** The core resolves the service **after** the load loop,
never at import. A missing implementation is a startup failure naming the module and the token, not a
`undefined` that surfaces three layers later as a rendering bug.

**R4 — the core may not import a module package, and a module may not import the core.** Both
directions are gated (`scripts/check-module-packages.mjs` already checks the surfaces; this adds the
import direction).

**R5 — the domain moves last.** The order is: contract and guard first, then the persona domain into
`packages/modules/persona/src/services/`, then the core's call sites resolve the token. Each step is
green before the next starts, so a failure is attributable.

## 4. What this does NOT move

`persona-runtime.ts` stays in the core: it spawns and owns bot clients for every persona, and it is
framework in the same sense `apps/main/src/queue/` is — one instance serving all modules. Moving it
into the persona module would give one module the fleet's bot runtime, which is the inverse of
isolation. This is recorded here so the next reader does not "finish the job" by moving it.

## 5. Acceptance

1. The core declares a token and an interface per service; no core file imports a module package.
2. A module registering an undeclared token is refused by the guard, with a test that proves the refusal.
3. A module registering a declared token is resolvable by the core after load, with a test that proves
   the resolution and that resolution before load fails visibly.
4. `provides` is no longer "declared and never wired": `REC-039`'s second half closes with it.
5. The persona domain lives in `packages/modules/persona/src/services/`, its own tests with it, and the
   core's call sites resolve the token.
6. A live deploy the operator confirms, because the load order changes.

## 6. Slices

| slice | what | risk |
|---|---|---|
| 0 | the guard refuses an undeclared `register`; `provides` wired and tested | low — additive |
| 1 | a token + interface for one small service, resolved lazily after load | low |
| 2 | the persona domain moves; `bootstrap`, `di/tokens`, `entry/twill` resolve the token | **high** — load order |
| 3 | the import-direction gate, both ways | low |

Slices 0 and 3 are additive and can land without touching a single persona file. Slice 2 is the one
that needs a live deploy confirmed.
