# UR-20261012-063 — The Rename That a Restart Undid

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.69` entry in `upgradation/change-log.md`).

---

## 1. What the operator saw

`/hello` renamed to `namaste` through the BCCM `/queue`, and afterwards **neither name** was visible in
that guild — while the persona still answered `hello`.

## 2. What is actually right

The rename mechanism is **sound**. `applyBatch` removes the old key and adds the new, and
`resolveCommandPayloads` inherits the source command's real definition, so a renamed command carries its
description and options rather than a description repeating its own name. On a successful push the
rename is also written to the persistent `guild_command_renames` table (guildId, commandKey, newName).

## 3. The defect

**`command-deployer.ts` never read that table.** It had no reference to `bccm`, `rename`, `alias`,
`queue` or `overrides` at all. So at every boot it re-registered the guild's command set **from the
registry** — the manifest's names — and silently **reverted** every applied rename.

The result is a flapping state: the rename lands on a queue window, the next restart puts the old name
back, and a later window re-applies it. Depending on when the operator looked, they saw the old name,
the new one, or neither.

## 4. The fix

The deployer takes a `commandRenames(guildId)` dependency, wired in bootstrap to read
`guild_command_renames`, and applies it to the set it registers — **reusing `resolveCommandPayloads`
with a source map**, the same machinery the BCCM push uses, so a renamed command keeps its real
definition on both paths.

## 5. Acceptance criteria

- **ACC-UR-073-1** — the deployer registers the RENAMED name, not the registry's.
- **ACC-UR-073-2** — the renamed command carries its source's definition (description, options).
- **ACC-UR-073-3** — with no renames the registered set is unchanged.
- **ACC-UR-073-4** — 115 files, 1169 tests, 0 failures; coverage 68.17% branch, no threshold error.

## 6. Recorded

**Two components wrote the same fact and only one read it.** The push wrote `guild_command_renames` and
honoured it; the deployer wrote the registry's names and honoured nothing else. The table existed the
whole time — the deployer simply had no dependency that could see it.

**Still open (recorded, not fixed):** the same table persists **renames only**. An `alias` or a
`disable` applied through the queue is not persisted, so those are still reverted by a boot.
