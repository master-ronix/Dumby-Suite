# UR-20261012-040 — Boot Safety

**Identity:** UR-20261012-040 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.47` entry in `upgradation/change-log.md`).

---

## 1. Summary — a live outage this record's predecessor caused

Production was **FAILED**: the service built, then died on boot with `ERR_OSSL_UNSUPPORTED`, and the
Railway healthcheck never passed.

**Cause, and it is this record's predecessor's fault.** Before UR-20261012-036 the key was resolved
*inside* a `try`/`catch`: an undecodable PEM produced `build-signing-key-invalid` and the bot booted
with the provenance guard off. UR-20261012-036 restructured that block and moved
`resolveSigningPublicKey(...)` — which calls `createPublicKey` — **outside** the `try`. A malformed key
therefore threw during boot and killed the process.

The deployment had `BUILD_SIGNING_PRIVATE_KEY` set and no `BUILD_SIGNING_PUBLIC_KEY`, so the fallback
path ran, and the key could not be decoded. **No configuration change could have fixed this**: the
runtime must survive a bad key, which is exactly what the old code did and the new code stopped doing.

## 2. The revision

- **`armBuildProvenance(verifier, keyId, privateKey, publicKey)`** does resolution *and* registration
  inside one helper that **cannot throw**, returning `{ armed, error? }`. A bad key is a warning and a
  disarmed guard, as before.
- Both registration sites use it, and the warning text now says the guard stays off and boot
  continues — so the next person reading the log is told what happened.
- **The same class of risk was audited and closed elsewhere in the batch:**
  - `seedRegistrarsSafely` — a boot-time registry write that fails is warned about and returns 0
    rather than propagating. An unwritable seed leaves the registry as it was, and registration
    already fails closed.
  - `PersonaRuntime.start` catches a failure to list personas and yields an empty run rather than
    throwing out of the boot path.

## 3. Acceptance criteria

- **ACC-UR-050-1** — a malformed key returns unarmed with a reason and **does not throw**.
- **ACC-UR-050-2** — an empty key id, or no key material, arms nothing without an error.
- **ACC-UR-050-3** — a valid public key, and a valid private key, each arm the guard.
- **ACC-UR-050-4** — a verifier that rejects the key is caught, not propagated.
- **ACC-UR-050-5** — a failing registrar seed is warned about and returns 0.
- **ACC-UR-050-6** — a failing persona listing yields an empty run.
- **ACC-UR-050-7** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 4. Risks & open questions

- **No configuration action is required.** The service boots and warns; the provenance guard stays off
  until a decodable key is supplied. Nothing needs regenerating, and no signing identity changes.
- **A regression test now exists for the exact failure**, so the next person to touch that block has
  the guard in front of them.
- **The real lesson is procedural.** UR-20261012-036 was verified by `typecheck`, `lint` and the gates
  — none of which execute a boot path. A change to a boot-time branch needs the *test* to prove it,
  which is why the helper moved into a tested module rather than staying inline.
