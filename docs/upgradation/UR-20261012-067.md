# UR-20261012-067 — Who Is Running This, and Where

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.72` entry in `upgradation/change-log.md`).

---

## 1. The finding

The framework hosts the main bot and any number of personas in **one process**. The module-facing
contract, `CommandContext` in the SDK, carried exactly two things:

```ts
export interface CommandContext {
  readonly config: Readonly<Record<string, unknown>>;
  readonly data: Readonly<Record<string, unknown>>;
}
```

**No identity. No guild. No profile.** A module could not tell which of the hosted identities was
running its command, which application it should speak as, or which guild it was bound to. Every
module-facing decision that depended on that had to be made by the core on the module's behalf — which
is precisely how the core came to hold facts the modules own (UR-20261012-066).

The operator's three requirements are one requirement: a real execution context, flowing root to surface.

## 2. What the contract now states

```ts
export interface ExecutionIdentity {
  profileId: string; // 'main', or the persona's id
  kind: "main" | "persona"; // the main bot serves every guild; a persona serves one
  applicationId: string; // the application this identity speaks as
  profileName: string; // the bot's username, or the persona's registered name
  guildId: string | null; // where the signal came from — null in a DM
  boundGuildId?: string; // the ONE guild a persona serves; absent for the main bot
}

export interface ModuleStanding {
  moduleId: string;
  tier: "admin" | "core" | "standard" | "marketplace";
  enabled: boolean; // enabled in this guild; core is always enabled
  owner: string; // 'main', a persona id, or 'shared' for core
  ownedByCaller: boolean; // is the caller the one who holds it
}
```

Both are **required** on `CommandContext`. A handler that needs to know whose signal it is answering can
ask, instead of the core deciding for it.

## 3. One source, compiler-enforced

`identity` is built in **one place** — the router's dispatch — from what the interaction states plus what
the router already knows about its own identity, and never re-derived downstream. The application comes
from the interaction, which is the same value the emoji scope uses and the only thing that can be right
for a message. Requiring the field made TypeScript enumerate every construction site: there was **one**.

`module` is read from the registry's own tier declaration and the binding service — the same source the
pages consult (UR-20261012-061) — so a module's standing cannot disagree with what `/browse` shows.

## 4. The registry's identity dimension

The registry cannot know _which profile_ a command runs under — that is a per-guild binding, resolved at
dispatch. What it can state, and now does, is the tier that decides who MAY run it:
`modulesByTier(tier)`, beside the `getModuleTier` the standing is built from.

## 5. Acceptance criteria

- **ACC-UR-077-1** — a persona dispatch carries its id, kind, application, name and bound guild.
- **ACC-UR-077-2** — the main bot declares no bound guild.
- **ACC-UR-077-3** — a module's standing reports its tier, enablement and owner.
- **ACC-UR-077-4** — the owner is the binding service's answer, not a second computation.
- **ACC-UR-077-5** — 115 files, 1173 tests, 0 failures; coverage 68.57% branch, no threshold error.

## 6. Recorded

**A contract that omits identity forces the core to hold it.** The piecemeal patches of the past week —
`residentPersonaId`, `residentApplicationId`, `actingProfileId` — were all attempts to carry identity
through layers that had no concept of it. One object, built once, replaces them.

**A silent-swap hazard, found while writing this.** `isModuleEnabledInGuild(moduleId, guildId)` takes two
strings, so a swapped argument **typechecks**. I made that exact mistake here and caught it by reading the
signature rather than trusting the compiler. Two same-typed parameters are a class of defect the type
system cannot see.
