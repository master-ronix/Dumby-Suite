# UR-20261012-066 — The Module Logos Go Home

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.71` entry in `upgradation/change-log.md`).
**Supersedes:** UR-20261012-065 (proposed), whose blocker this record resolves.

---

## 1. What was wrong

Seven first-party module logos were hardcoded in the **core** (`module-emoji-upload.ts`), with paths into
`apps/main/assets/module-icons/` — while each module **already declared its emoji name** in its own
manifest. One fact, two owners, and the wrong one authoritative.

The intended layout already existed and was empty: `structure.md` lists
`packages/modules/<slug>/assets/` for all eight modules, and `building-a-module.md` calls it _"static
assets your module serves"_.

## 2. Why the earlier record did not execute it

UR-065 named the blocker: **the core could not locate a module's assets at runtime.** `LoadedModule`
carried no path, `loader.ts` reads no directory, and the first-party modules reach the process through a
baking pipeline. Moving the PNGs on that basis would have left the per-asset upload skipping every logo
— non-fatal by design, and therefore silent — and rendered every module logo as the fallback.

## 3. The chain, verified end to end

Traced through the deployment, not assumed:

```
packages/modules/<slug>/assets/icon.png
  → build:modules            (build-first-party-modules.ts)
  → apps/main/dist-modules/<slug>/assets/icon.png
  → place-first-party-modules.mjs   cpSync of the whole built directory
  → /mnt/modules/modules-<tier>/<slug>/assets/icon.png
  → apps/main/Dockerfile     COPY --from=builder /mnt/modules /app/baked-modules
  → MODULES_DIR=/app/baked-modules   ← what the loader reads
```

**The one missing link was `build:modules`, which copied `locales/` but not `assets/`.** That is a
one-line addition mirroring the copy beside it, and it is the change that makes the move safe rather
than the change that risks it. Confirmed by running it: the asset now appears in `dist-modules` and in
the baked tree.

## 4. The change

1. **`build:modules` carries `assets/`** into the built module, exactly as it carries `locales/`.
2. **`LoadedModule.root`** — set in `swastik-loader` where `moduleDir` is already computed and was
   previously only logged.
3. **`ui.iconAsset`** on the manifest UI schema — a module-relative path, mirroring how `ui.banner`
   already carries a module-supplied asset.
4. **The seven PNGs move** to `packages/modules/<slug>/assets/icon.png` and each manifest declares
   `"iconAsset": "assets/icon.png"`.
5. **The upload takes its module-icon list from the registry** — name from `ui.icon`, path from
   `root + ui.iconAsset`. The core's hardcoded list is reduced to **framework chrome only**
   (`dumby_status_online`, `dumby_status_offline`, `dumby_info`, `dumby_identity`, `dumby_profile`,
   `dumby_refresh`, `dumby_home`, `dumby_discover`, `dumby_uninstall`, `dumby_module`,
   `dumby_module_fallback`) — which ADR-012 places with the framework alongside the default banner.

A module that declares no asset — or whose root the loader did not record — is **skipped**, and the
framework fallback applies. That is ADR-012's rule: _absent a declaration, the default applies._

## 5. Acceptance criteria

- **ACC-UR-076-1** — no module logo path is hardcoded in the core.
- **ACC-UR-076-2** — `build:modules` carries each module's `assets/` into the built bundle.
- **ACC-UR-076-3** — a module-declared icon registers from the path the caller resolved.
- **ACC-UR-076-4** — framework chrome still registers from the core.
- **ACC-UR-076-5** — 115 files, 1170 tests, 0 failures; coverage 68.25% branch, no threshold error.

## 6. Recorded

**The blocker was a packaging fact, and it was worth finding.** UR-065 could have shipped on the
assumption that a file move is a file move. Tracing the chain instead showed that `build:modules` copies
locales and not assets — so the move alone would have reproduced the exact fallback symptom this week
was spent removing, silently. **The fix was one line in the build, and it could only be written after
the chain was read.**

**Still open (recorded):** the framework's own chrome assets remain in `apps/main/assets/` — correct per
ADR-012, but they are the last visual assets the core carries, and a future record may move them behind
the same declared-asset mechanism.
