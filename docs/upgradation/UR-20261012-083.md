# UR-20261012-083 — A Revoked Persona Stayed Online With Every Command Loaded

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.88` entry in `upgradation/change-log.md`).

---

## 1. The finding

The operator revoked ELSA. The API returned `204`, the row was retired and soft-deleted, and the list
came back empty. **She kept answering every command.**

`DELETE /twill/personas/:id` removed her from the database and stopped there. The runtime still held her
gateway client, so she stayed online; Discord still held her registered commands, so the picker still
offered them and she still answered them. Nothing the operator could see had changed. The delete had
"worked" in every way the API could observe and in no way the operator could.

## 2. The mechanism

Three stores held a piece of the persona, and the revoke reached one of them:

- **Postgres** — the row. Soft-deleted. Correct.
- **The runtime's client map** — her live gateway connection, held in `PersonaRuntime.clients`, populated
  at boot. Untouched.
- **Discord** — her commands, registered against her APPLICATION by `deployPersonaCommands`. Untouched.
  Commands belong to an application, not a session, so they outlive the client: destroying the client
  alone would leave the picker offering commands that nothing answers.

The runtime had `stop()` — every persona, for shutdown — and no way to stop one.

## 3. What changed

- **`PersonaRuntime.stopPersona(persona)`** — destroys the persona's client (taking her offline) and
  clears her commands (taking her out of the picker). Non-fatal on both halves: a `destroy` that throws
  must not stop the commands being cleared, and a failed clear must not leave her running.
- **It takes the persona's identity, not an id.** By the time it runs the row is already retired, so a
  lookup would not find her — and her client and her commands would be exactly the two things left
  behind. The route reads her *before* the revoke.
- **`clearCommands` reuses the deploy path with empty payloads.** `deployPersonaCommands` clears both
  scopes before it writes, so an empty set is precisely a deregister — the same code, not a second
  implementation of the same Discord call.
- **The DELETE route reads her, revokes her, then stops her**, and says so when there was no running
  client to stop.

## 4. Acceptance criteria

- **ACC-UR-083-1** — revoking destroys the running client; `hostedCount` drops.
- **ACC-UR-083-2** — revoking clears her registered commands.
- **ACC-UR-083-3** — a persona that is not hosted reports `false`, but her commands are still cleared.
- **ACC-UR-083-4** — a failing `destroy` does not prevent the commands being cleared.

## 5. Recorded

**This is UR-082's lesson, one hour old, unapplied to the very next operation.** UR-082 recorded: *a
write that reaches the database is not a write that reaches the world.* The revoke was written and
recorded before UR-082 existed, and UR-082 did not go back and ask which *other* operations have the
same shape. The lesson was learned for presence and not carried to revoke.

**The general form, stated so it can be checked mechanically:** for every operation, ask which stores
hold a piece of the entity, and confirm the operation reaches all of them. A persona lives in Postgres,
in the runtime's client map, and in Discord. An operation that touches fewer than all three is
incomplete, and the API will still report success.

**"It returns 204" is not evidence the operator's problem is solved.** The revoke was correct at every
layer the API could see. Only the operator, looking at Discord, could tell that nothing had happened —
which is why their report is the finding and the logs are not.

**A per-entity stop was missing because only the fleet-wide one was needed until now.** `stop()` existed
for shutdown, where every persona stops at once; a single persona stopping while the process lives is a
different operation, and the absence was invisible until something needed it.
