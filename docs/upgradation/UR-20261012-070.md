# UR-20261012-070 — The Context Reaches the Other Three Entry Points

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.75` entry in `upgradation/change-log.md`).

---

## 1. The finding

UR-20261012-067 gave a command an `identity` and a `module` standing. It could, because a command
carries an interaction, and the interaction is where the guild and the application come from.

A module has **four** entry points, and the other three carry no interaction:

| Entry point | What it receives today |
|---|---|
| command | an interaction, and now a full context |
| gateway event | Discord's own argument list |
| job | its payload |
| cron task | **nothing at all** |

So *which profile is running this, and where* had no answer on three of the four paths — and that
answer is precisely what a module needs to behave correctly when the main bot and a persona both run
it, in different guilds.

## 2. Why the context is not a parameter

The obvious fix — pass it in — fails on the event path. A handler is declared
`handle: (...args: unknown[])`, so:

- an **appended** context lands inside a rest parameter and is invisible;
- a **prepended** one silently breaks every handler ever written.

The context therefore travels out of band, with `AsyncLocalStorage` — the mechanism the framework's
own event bus already uses for its emit context — so **no handler signature changes**, and the context
is reachable identically on all four paths.

## 3. Where the carrier lives, and why

`AsyncLocalStorage` is a Node builtin. The SDK is deliberately environment-neutral — `"types": []`,
`"lib": ["ES2023"]`, and until now not one Node import — so putting it there would have broken that
property for every module that consumes the package.

Instead the SDK declares a `ModuleContextStore` interface and the host **installs** an implementation.
The app installs the `AsyncLocalStorage`-backed one at boot. A module imports only
`currentModuleContext()` from the SDK, and the SDK gains no dependency.

## 4. The resolver

One resolver, built from what boot already knows:

- the **process identity** — `profileId` (`PERSONA_ID` or `'main'`), `kind`, `applicationId` and
  `profileName` — is a fixed tuple, because the router is built per identity (UR-20261012-049). Only
  the guild varies per invocation. It is **late-bound and async**: the application id comes from the
  Discord client, which is not ready when Stage 12 registers a module's handlers, and a persona's
  bound guild is a database read.
- the **standing** reuses the enablement read (UR-20261012-069) and the binding service, so a module
  cannot get two different answers from two surfaces.

It **never throws**, for the reason UR-20261012-068 settled: a context is advisory. A fault falls back
to the conservative standing — `enabled: false`, `owner: 'main'` — rather than taking the work down.

The loader is the single place all three non-command entry points register, so one wrap covers events,
jobs and tasks together, and a module's handler receives the context without knowing it was wrapped.

## 5. Acceptance criteria

- **ACC-UR-070-1** — with no store installed the accessor is inert and `run()` is a plain call.
- **ACC-UR-070-2** — `requireModuleContext()` names the reason rather than guessing.
- **ACC-UR-070-3** — the identity carries the process profile plus the guild of this work; a persona
  carries its id and bound guild.
- **ACC-UR-070-4** — a Core module is `shared`/`enabled` without reading a dependency.
- **ACC-UR-070-5** — a failing read yields the conservative standing, never a confident wrong "yes".
- **ACC-UR-070-6** — an event handler, a job processor and a cron task each observe their context, and
  a task observes `guildId: null` because it has no guild.
- **ACC-UR-070-7** — 118 files, 1210 tests, 0 failures; coverage at or above the branch floor.

## 6. Recorded

**A package's constraints are part of its contract.** The first attempt put `AsyncLocalStorage` in the
SDK and the build failed on `node:async_hooks` — the SDK's `"types": []` is not an accident. Inverting
it — the SDK declares the shape, the host installs the carrier — keeps the neutrality AND gives modules
one documented way to ask.

**The three entry points are not symmetric, and the design has to say so.** A job may name a guild; an
event usually does; a task never does. A task's context honestly reports `guildId: null` rather than
inventing one.
