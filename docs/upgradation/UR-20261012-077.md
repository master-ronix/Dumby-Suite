# UR-20261012-077 — A Refusal Names the Actor

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.82` entry in `upgradation/change-log.md`).

---

## 1. The report, and what it actually was

The Railway session reported:

```
PersonaOccupiedError: Command key "hello-world" … is occupied by another persona
(… already bound to persona "39eaaf0f-…")
```

and read it as *"a persona claiming a module it already holds is being treated as a conflict"* — i.e.
that ELSA had been refused her **own** module.

**The log says otherwise.** The same line carries `actor=main`: the actor was the **main bot**, and the
persona named is the **owner**. The refusal was **correct** — the main bot may not install or claim a
module a persona holds. The diagnosis was wrong, and it was reached from the message alone.

## 2. A message that names one party is half a message

A refusal has two parties: who was refused, and who owns the thing. The message named only the owner,
in wording ("occupied by another persona") that invites the reader to assume the actor *is* a persona.
When the actor is the main bot — which is not a persona at all — that assumption is exactly wrong.

`PersonaOccupiedError` now takes the actor and says both:

```
Command key "hello-world" in guild "…" is owned by persona "39eaaf0f-…",
so "main" may not install or claim it
```

Both throw sites pass the actor — the install path its resolved actor, the dispatch assertion its own
identity.

## 3. What the misdiagnosis was standing on: an asymmetry

Investigating it surfaced a real gap, **recorded here rather than fixed silently**, because it changes
the ownership model:

**The main bot never records a claim.** The claim branch is `if (owner === undefined && acting !==
undefined)` — persona-only. So a module the **main bot** installs leaves no binding, `owner` stays
undefined, and any persona may later claim what the main bot enabled.

The operator's own model is the opposite: *"if the hello module is enabled by the main bot then it is
the property of the main bot only."* Under the current code that is not enforced, because the main bot's
ownership is never written down. Closing it means the ownership read must answer `'main'` for an enabled
but unbound module — a change to the shared read every page consults, so it wants its own UR and its own
tests rather than a footnote on this one.

## 4. Acceptance criteria

- **ACC-UR-077-1** — `PersonaOccupiedError` names the actor and the owner.
- **ACC-UR-077-2** — the install path passes its resolved actor; the dispatch assertion passes its own
  identity.
- **ACC-UR-077-3** — the main-bot case reads as `"main"`, never as a persona.
- **ACC-UR-077-4** — the ownership asymmetry is recorded, not silently changed.

## 5. Recorded

**A message that misled a careful reader is a defect, not a documentation gap.** The Railway session
read the log correctly in every respect except the one the message obscured. Wording that makes the
wrong reading the natural one is worth fixing even when the behaviour is right.

**The correct diagnosis was one field away.** `actor=main` was already in the log line. The
investigation that produced the wrong conclusion had the right answer in front of it — which is the
argument for putting the two parties in the message rather than in a sibling field.

**A model the code does not enforce is a model the operator does not have.** "The main bot's property"
cannot be true while the main bot's claim is never recorded.
