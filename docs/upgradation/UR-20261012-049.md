# UR-20261012-049 — The Other Half of A2.1

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.55` entry in `upgradation/change-log.md`).

---

## 1. The gap

UR-20261012-043 extracted the **component** dispatch, which fixed a persona's buttons. It did not
extract the **command** dispatch, and nothing else supplied it:

- `buildDiscordClient` attaches only `error` and `warn` — **no `interactionCreate`**.
- The persona runtime attached only `buildComponentInteractionHandler`, which returns early for
  anything that is not a button or a select menu.

So a hosted persona's slash commands were **deployed to the guild and then reached nothing**. In
Discord the command appears, runs, and the application never acknowledges it — _"The application did
not respond"_ after three seconds. The persona looked online and half-working, which is the most
confusing possible state to debug.

Found by reading the runtime's wiring while bringing the first live persona online, **before** the
operator hit it.

## 2. The fix

- **`buildPersonaInteractionHandler`** is the full handler for one identity: chat-input commands go to
  the persona's own router; buttons and select menus go to the shared component registry; anything else
  is ignored. It **never throws** — one bad interaction must not take a gateway listener down.
- **The router is built from a thunk**, once per persona rather than per interaction, and a router that
  cannot be constructed **degrades that persona to components-only** instead of stopping it from
  starting. The failure is logged.
- **`commandRouterOptions(residentPersonaId?)`** in bootstrap is now the single description of how a
  router is configured, so a persona's router is configured exactly as the main bot's is — system-map
  §11's "the framework running again under a different identity". `residentPersonaId` is the only thing
  that varies: the main bot sets it only when the process itself is a persona (`PERSONA_ID`), while a
  hosted persona always sets its own id, so **command ownership is enforced for it** by the router's
  existing `assertPersonaOwnsCommand`.

## 3. Why this is the correct shape

A persona dispatches through the **same adapters** (UR-20261012-043) and the **same router
configuration**, over a registry filtered to its own modules. Nothing about the persona path is a
parallel implementation, which is what makes "the framework running again" true rather than aspirational.

## 4. Acceptance criteria

- **ACC-UR-059-1** — a slash command is dispatched through the persona's router, adapted first.
- **ACC-UR-059-2** — the router is built **once**, not per interaction.
- **ACC-UR-059-3** — a router that cannot be built degrades to components-only and does not throw.
- **ACC-UR-059-4** — with no router, a command is **reported**, not silently dropped.
- **ACC-UR-059-5** — a dispatch failure is logged and never propagated.
- **ACC-UR-059-6** — buttons and selects still reach the component registry; other interactions are
  ignored.
- **ACC-UR-059-7** — full suite green with coverage: 113 files, 1147 tests, 0 failures, no threshold
  error; `typecheck`, `lint`, `format`, corpus gates 27/27.

## 5. Recorded for the next reader

**A handler that answers some interaction types and silently drops the rest is worse than one that
answers none.** The persona's state — online, commands visible, buttons working — made it look like a
narrow bug rather than a missing dispatch path. Where a handler covers a set of interaction types, the
uncovered ones should be **reported**, which is what `persona-command-unhandled` now does.
