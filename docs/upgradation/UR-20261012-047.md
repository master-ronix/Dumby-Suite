# UR-20261012-047 — The Eighth Layer

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.53` entry in `upgradation/change-log.md`).

---

## 1. UR-046 did not fix it, and this record says why

`a76cdd3` went live with UR-20261012-046 and `/dashboard` **still** failed in guild
`1062427177326497863`:

> `Command "dashboard" from core module "dashboard" is not available in guild 1062427177326497863`

UR-046 made a stale `enabled:false` row harmless for a core module. That was **not** the cause, and the
code shows why: `assertCommandInScope` already contains `if (tier === 'core') return;` — a core command
**never reaches** the enablement check at all. UR-046 was a real hardening (two paths disagreed), but it
was applied to a branch core commands do not take. The earlier diagnosis was an inference from message
wording, and it was wrong.

## 2. The actual cause

`CommandScopeDeniedError` is thrown from **two different checks that share one message**:

- `assertCommandInScope` — module scope and enablement.
- `assertPermissionAllowed` (`command-router.ts:433`) — the **permission resolver**, which throws the
  _same class with the same wording_ when `result.allowed === false`.

So "not available in guild" was never only about scope; it is also how a permission refusal reads. The
notice's `reason: FORBIDDEN` is the tell — `FORBIDDEN` comes from `reasonFromRejection`, i.e. the
permission path.

Inside the resolver, the refusal was the **last block**:

```ts
if (ctx.hasExplicitPermissionDeclaration !== true) {
  return deny(7, "no explicit permission declaration exists for this action");
}
```

## 3. Why that block is a defect, not a policy

**It is not a layer.** DIAGRAM 21-A of `permission-authorization-engine.md` lists seven, in order: bot-owner
override, blacklist, guild & module availability, grant override, channel restriction, Discord permission
bitfield, RBAC rank. **None of them is a declaration check.**

**It inverts the documented default.** The diagram closes: _"Only if every layer passes without a
definitive answer does the framework fall through to the final default: **allow**."_

**Declaring nothing is normal.** §21.3: MEMBER is _"the default requirement every command carries when it
declares nothing"_.

**It misuses Layer 7.** Layer 7's real job is a **grant override** — an applicable grant's outcome is
final, and with no applicable grant resolution _continues_ to Layers 4–6. Turning "no applicable grant"
into a refusal is the opposite of that.

**The production effect was total.** `dashboard.command.ts`, `modules.command.ts` and
`health.command.ts` all declare **no permissions** — they are host-registered core commands (§1.7), so
they never carry a module-authored declaration. Every core command was therefore denied to every member
who was not a bot owner. The bot owner short-circuits at **Layer 1**, which is exactly why this read as
one guild's problem (`1062427177326497863`) instead of a blanket one.

## 4. The fix

The block is **removed**; resolution falls through to `ALLOW` as documented. `hasExplicitPermissionDeclaration`
remains on the context for any caller that wants to know whether an action declared a posture — it simply
no longer denies.

Two tests had _encoded the defect_ and were corrected to the spec, and a third now forces its denial the
legitimate way (a declared Discord permission the member lacks, refused at Layer 5).
