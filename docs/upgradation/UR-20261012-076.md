# UR-20261012-076 — Unblocking the Deploy

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.81` entry in `upgradation/change-log.md`).

---

## 1. The finding, and it is the important one

The operator reported that the core modules were "outdated and not compatible with new changes —
totally corrupted". Investigating that turned up the cause, and it is not the modules.

**Two commits were failing CI, and Railway skipped those deploys.** The `Gates (D-8.4 strict
sequence)` check concluded `failure` on the tip, and a skipped deploy means the build did not ship.

**Correction, recorded 2026-10-14.** This UR first claimed "every recent commit was skipped". That was
wrong, and the Railway session's log reading is the authority: UR-066 through UR-073 each deployed and
were replaced in turn; the live build was `d36d5f3` (UR-073). **Only UR-074 and UR-075 were skipped.**
The distinction matters: the execution-context, lifecycle-hook, disable-flow and module-icon work WAS
live, and only the honest notice and the first-render profile fix were not. Reading one red check as a
week of lost work overstated the damage, and the operator's "corrupted modules" report was therefore
partly a stale build and partly a real one.

The failing test was one:

```
tests/flow/command.flow.test.ts
  > flow: a command travels the full dispatch path
  > denies a non-owner and renders a FORBIDDEN notice
AssertionError: expected '…' to contain 'FORBIDDEN'
Received: "…⚠ This module is switched off … reason: MODULE_DISABLED"
```

## 2. Why it failed — and why the failure is correct

The test registers `stdcmd` in the **command** registry and asserts that a non-owner gets a `FORBIDDEN`
notice from the RBAC rank check. But the guild-scope check runs **first**, and it resolves a module's
tier from the **module** registry — where `flow-std` was never registered. An unknown module falls
through to `marketplace`, which defaults to **disabled**. So the scope check refused the command before
the rank check this test exists to exercise was ever reached.

**It passed before only because a scope denial happened to render `FORBIDDEN`** — the very wording
UR-20261012-074 corrected. Making the notice honest turned a passing-for-the-wrong-reason test into a
failing one. The failure is right: the command really was being refused for a reason the test did not
intend, and the old notice concealed it.

## 3. What changed

The flow harness now registers `flow-std` in the **module** registry with its `standard` tier, so the
scope check resolves correctly, the module is enabled by the tier default, and the command reaches the
RBAC rank check the test is about.

## 4. Acceptance criteria

- **ACC-UR-076-1** — the flow test reaches the RBAC rank check and renders `FORBIDDEN` for a non-owner.
- **ACC-UR-076-2** — the harness registers the module's tier, so the scope check does not deny first.
- **ACC-UR-076-3** — `typecheck`, `lint` and `format` are clean.
- **ACC-UR-076-4** — CI's Gates job passes, so the pending commits deploy.

## 5. Recorded

**A failing gate is a silent outage.** Every fix of the past days — the execution context, the lifecycle
hooks, the disable flow, the honest notices — was committed, green locally, and **never reached
production**, because one test failed and Railway skips on a red check. The operator's report of
"corrupted modules" was a report of a *stale build*, and the honest reading of it was to check the
pipeline before the code.

**A test that passes for the wrong reason is a trap that springs later.** This one asserted a string the
defect happened to produce. When the defect was fixed, the test broke — which is the test doing its job
late, not badly. The lesson is to assert the *cause*, not the wording, wherever the wording is a symptom
of the thing being tested.
