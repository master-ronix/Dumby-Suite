# UR-20261012-075 — The Primary Render Carries the Acting Profile

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.80` entry in `upgradation/change-log.md`).

---

## 1. A reported defect that was already fixed — recorded before it is "fixed" again

A screenshot showed `/modules` rendering every module icon as literal text (`:dumby_browse:`) while
`/dashboard` rendered the same icons correctly. It was logged as a live defect.

**Checking it showed it was almost certainly stale.** `moduleIcon` cannot produce that output: when a
declared emoji name does not resolve, it falls back to a glyph rather than printing the name, precisely
so a page never shows literal text. And the screenshot showing the failure is **older** than the one
showing the same emoji fix working on `/dashboard`.

The raw-text form is what Discord renders when a message carries **another application's** emoji id —
the failure UR-057 and UR-062 already fixed, and which the screenshot predates. So no icon change was
made: changing working code on the strength of a stale screenshot would have been a guess dressed as a
fix.

## 2. What checking it DID find

Two declarations of the page-data provider's signature exist — one on the router's dependency, one as
the factory's return type — and they had drifted. Chasing that drift surfaced a **live** defect:

The router calls the provider from three places. Two of them passed `actingProfileId`; the **primary
render at dispatch did not**. The dispatcher defaulted it to `'main'`. So:

- a persona's **first** page render reported the **main bot's** modules;
- the **same page after an effect** — which did pass the profile — reported correctly.

Two renders of one page, disagreeing about whose page it is. That is the defect class UR-20261012-061
was written to close, still open one level up.

## 3. What changed

- `applicationId` and `actingProfileId` are now **required** on both declarations of the provider
  signature, with no defaults. UR-060 removed the default from the emoji *readers* for exactly this
  reason — a default lets a call site forget silently — and the dispatcher had kept its own.
- `page` and `query` become required-but-nullable, because a required parameter may not follow an
  optional one.
- The primary render now passes the acting profile.
- The factory's return type is brought back into line with the dependency's.

## 4. Acceptance criteria

- **ACC-UR-075-1** — a persona dispatch renders the page with the persona's id as the acting profile.
- **ACC-UR-075-2** — the same dispatch carries the persona's application id.
- **ACC-UR-075-3** — a main-bot dispatch renders for `'main'`.
- **ACC-UR-075-4** — the provider signature is required in both declarations, so a future call site that
  omits either is a compile error.
- **ACC-UR-075-5** — 120 files, 1230 tests, 0 failures; coverage at or above the branch floor.

## 5. Recorded

**A screenshot is evidence with a timestamp, and the timestamp matters.** It showed a real failure; it
did not show a *current* failure. Before changing code, the first question is whether the artefact
predates the fix — the second screenshot on the same page answered it.

**A type declared twice will drift, and the drift hides a defect.** The two signatures disagreed, which
is why one call site could omit an argument the other passed and still compile. Making both required in
both places is what makes the compiler able to see the next omission.
