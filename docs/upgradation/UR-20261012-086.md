# UR-20261012-086 — A Registered Persona's Presence Was Dropped Before It Reached the Row

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.91` entry in `upgradation/change-log.md`).

---

## 1. The finding

A persona registered with `presenceStatus: "dnd"`, `note: "Magma"`, `accent: "#E964A7"` came up
**online**, with no status note on its profile. A screenshot of the profile shows the default green
presence indicator and no custom status.

Nothing errored. The registration returned `201`. The runtime started her. The presence was simply
never there to apply.

## 2. The mechanism

Two independent faults, one behind the other. The first hid the second, which is why it took a
screenshot to find.

**Fault 1 — the builder dropped the fields.** `buildPersonaIdentity(input)` constructs the row that
gets inserted. UR-081 added `presenceStatus`, `note` and `accent` to `PersonaRegistrationInput`, and
the surface parsed and validated them — but `buildPersonaIdentity` never copied them into the object it
returns. So the insert wrote **nulls**, and the runtime's `persona.presenceStatus` was `undefined`. The
apply branch is guarded by `presenceStatus !== undefined`, so it never ran, and never logged.

The value was accepted at the boundary, typed all the way through, and discarded in the middle.

**Fault 2 — a CUSTOM activity renders its `state`, not its `name`.** The presence was sent as
`{ name: note, type: 4 }`. Activity type 4 is CUSTOM, and Discord renders the custom-status text from
the **`state`** field; `name` is ignored for that type (it must be `"Custom Status"`). So even with the
status applying, the note would not have appeared.

**A third fault, latent — the silent no-op.** The wiring used `client.user?.setPresence(...)`. If
`client.user` were not yet available, the optional chain would swallow the call entirely, and the
runtime would still log `persona-presence-applied`, because its log sits after the call and the call
does not throw. A false confirmation.

## 3. What changed

- **`buildPersonaIdentity` carries the presentation**, so the fields reach the row. Absent stays absent
  rather than becoming an empty string, so "not configured" remains distinguishable from "blank".
- **The CUSTOM activity carries the quote in `state`**, with `name: 'Custom Status'` as Discord requires.
- **The no-op is gone.** If `client.user` is unavailable the wiring logs
  `persona-presence-no-user ... the presence was NOT applied` and returns, rather than silently doing
  nothing while the caller reports success.

## 4. Acceptance criteria

- **ACC-UR-086-1** — `buildPersonaIdentity` carries `presenceStatus`, `note` and `accent` onto the row.
- **ACC-UR-086-2** — absent presentation stays absent, not an empty string.
- **ACC-UR-086-3** — the custom status is sent as the activity `state`.
- **ACC-UR-086-4** — an unavailable `client.user` is logged, not silently swallowed.

## 5. Recorded

**A field can be declared, parsed, validated and typed — and still never arrive.** Every layer UR-081
touched was correct and reviewed; the one function that actually builds the persisted object was not,
and it is the only one that mattered. The general form: after adding a field, follow it from the wire
to the **row**, and confirm there is a test that asserts it on the object being written — not on the
input being parsed. The tests added here assert the built persona, which is the artefact the insert
consumes.

**Two faults in series hid each other.** Had only the builder been broken, the note bug would have gone
unnoticed; had only the activity shape been broken, the builder bug would have looked like "the note
doesn't render". The screenshot separated them, and neither was findable from the logs.

**A silent no-op reported success.** `client.user?.setPresence()` cannot fail, so the surrounding
`try` never fired and the log line after it was unconditional. The log said "applied" for a call that
did nothing. This is the third time in five URs that the defect was a claim of success the code was not
in a position to make.

**The unconfirmed was stated as unconfirmed.** This was reported to the operator as a gap that could
not be verified from the logs, before it was proven a bug. The alternative — assuming the presence had
applied because no error appeared — would have left the feature broken and believed working.
