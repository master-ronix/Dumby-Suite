# UR-20261011-018 — Disable-Flow Corrections

**Identity:** UR-20261011-018 · **Version:** 1.0 (Template v1.0, filled instance) ·
**Date:** 11/10/2026 · **Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-11 (see the `v5.5.18` entry in `upgradation/change-log.md`).

**Basis:** the operator's four live requests of 11/10/2026, after the module-disable fix (UR-20261011-017) went live.

---

## 1. Summary

Four corrections to the module disable/enable flow:

1. **No confirmation.** Disabling replaced the detail card with the refreshed card, not a definitive result.
2. **The instant hide/restrict never ran.** `setModuleCommandAccess` wrote the per-guild command-permission override with the **bot** REST client. Discord's *Edit Application Command Permissions* endpoint accepts **only a Bearer token** (scope `applications.commands.permissions.update`) — a bot token is rejected (`403`, "Bots cannot use this endpoint"). So the override silently failed and only the batched BCCM deregistration remained.
3. **The disable control appeared on the `/browse` Info view**, which is informational.
4. **A spurious `FORBIDDEN`.** The router's rank input omitted `isGuildOwner` (both paths) and the component path omitted member context, so an actor could evaluate as `RESTRICTED`.

---

## 2. The fixes

- **R1 — Compact (Mode C) confirmation (request 1).** A successful disable now replaces the card with a formal **Mode C** frame: a single identity line plus the outcome (`✅ **<module>** disabled — its commands are hidden and queued for deregistration. Re-enable it from /browse.`). New `disableConfirmation` dependency in `core-frame.handlers.ts`; the payload lives in `bootstrap.ts`.
- **R2 — instant hide/restrict (request 2).** `setModuleCommandAccess` now writes the override with a **Bearer token** from `DISCORD_COMMAND_PERMISSIONS_TOKEN` (a new env key), via a direct `PUT /applications/{app}/guilds/{guild}/commands/{command}/permissions`. Absent the token it logs `command-access-token-missing` and returns — the state write and the BCCM deregistration still apply. This is the guild's *Integrations* permission model (Server Settings → Integrations), which is the only mechanism that hides a command from members instantly.
- **R3 — no disable control on `/browse` (request 3).** The `dumby:info:` customId now carries the surface (`dumby:info:<invoker>:<surface>:<module>`); the `/modules` card carries the control, the `/browse` Info view does not.
- **R4 — owner rank (request 4).** Both interaction adapters now pass `isGuildOwner`; the component adapter also passes `memberPermissions`/`memberRoles`. A guild owner evaluates as `OWNER` ahead of any permission bit.

## 4. Acceptance criteria

- **ACC-UR-028-2** — with `DISCORD_COMMAND_PERMISSIONS_TOKEN` set, the module's commands are denied for `@everyone` at once; without it, the run is logged and BCCM still queues the deregistration.

## 5. Rollout

1. Set `DISCORD_COMMAND_PERMISSIONS_TOKEN` on the Railway service (user OAuth2, scope `applications.commands.permissions.update`) to enable the instant hide/restrict.
2. `BCCM_BATCH_PUSH_DRY_RUN=false` still gates the batched deregistration (UR-20261011-016 §6).

## 6. Risks & open questions

- **The Bearer token expires.** A user OAuth2 access token is short-lived; the operator must refresh it, or a refresh flow must be added. Recorded, not solved here.
- **A disabled module's page may still be reachable from a page listing**, and selecting it yields the module-scope `FORBIDDEN`. The denial is correct (§13.7). *(Amended v1.1: the "navigation dropdown" the first draft named has no code path — see below — so the observation needs a screenshot to place.)*
- **Retraction (v1.1).** An earlier draft of this record claimed `personas/persona.repository.ts` binds `guild_persona_bindings` with a `moduleSlug` key the table lacks. That claim is **false**: migration `20260101000034_align_persona_model.ts` recreates the table with a `moduleSlug` column and a `PRIMARY KEY ('guildId', 'moduleSlug')`, so `.onConflict(['guildId', 'moduleSlug'])` resolves. There is no defect.
- **Dead code (v1.1).** `CommandRouter.navigationControl` and the renderer's `navigation?` descriptor field are never called/populated; the `dumby:nav:` ids in use are the Home/Next/Prev buttons, not a select. The "navigation dropdown" the original note referred to therefore has no code path — the observation needs a screenshot to place it.
