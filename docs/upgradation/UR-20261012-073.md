# UR-20261012-073 — Is the Redirect URL Configured?

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.78` entry in `upgradation/change-log.md`).

---

## 1. The requirement

A persona is a separate Discord application, so its OAuth2 **redirect URL** must be registered on that
application before its combined install+authorize invite can work. The operator's ask: once the redirect
URL is configured, the **Invite** control should be available at Info — and, ideally, the framework
should be able to *check* whether it is configured rather than assume.

## 2. A proposed method that does not work — recorded so it is not re-proposed

The suggestion on the table was a server-side probe: request Discord's authorize endpoint with the
candidate redirect URI and read whether it is accepted, since Discord validates the redirect *before*
rendering the consent screen. **That is not reliable, and this UR records why.**

- Discord's OAuth2 documentation describes the authorize URL as prompting the user to authorize; it
  documents no pre-consent redirect validation, and there is no API to read an application's
  registered redirect URIs.
- The documented behaviour is a **JSON error for a malformed** URI
  (`{"redirect_uri": ["Not a well formed URL."]}`) — a *syntax* check, not a registration check. An
  unregistered-but-well-formed URI surfaces as an **error page after the user reaches the consent
  step**, i.e. it needs a logged-in browser session. A server-side request therefore receives the login
  page, not a verdict.
- The token endpoint *does* validate `redirect_uri` against the registered list — but it requires a
  real authorization `code` first, which only exists after a user completes the flow.

So the probe cannot answer the question without a user, which is the one thing it was meant to avoid.

## 3. The honest signal, which already exists

**A successful code exchange is proof.** The exchange cannot succeed unless the `redirect_uri` the
authorize leg sent is one of the application's registered ones. The callback already performed that
exchange and already logged `oauth2-connected` — and then **threw the proof away**.

So the framework now **records** it: `persona_identities.oauthVerifiedAt`, written on the callback's
success path, keyed by application id. Absent means "never completed", which is the honest default and
the state every existing persona is in.

This answers the operator's question with a fact rather than an assumption, and it is a signal the
system was already producing.

## 4. What changed

- A migration adds `persona_identities.oauthVerifiedAt` (nullable).
- `PersonaIdentityStore.markOauthVerified(applicationId)` writes it; `PersonaIdentity` and the row type
  carry it; the in-memory store mirrors it.
- The OAuth callback calls it on success, **guarded**: the authorization itself succeeded, so a
  bookkeeping failure must not turn a working connect into an error page.
- `page-data` exposes `oauthVerified` on the persona row. The page reports the **fact**; the persona
  module decides how to present it — the same core/module split as every other persona fact.

## 5. Acceptance criteria

- **ACC-UR-073-1** — a successful callback records the verification, keyed by application id.
- **ACC-UR-073-2** — a failing verification write does not fail the callback.
- **ACC-UR-073-3** — `page-data` reports `oauthVerified` as a boolean, false when never completed.
- **ACC-UR-073-4** — the migration adds and drops the column cleanly.
- **ACC-UR-073-5** — 120 files, 1227 tests, 0 failures; coverage at or above the branch floor.

## 6. Recorded

**A capability I described confidently and had not verified.** The probe was proposed as workable on
an assumption about Discord's endpoint. Checking it showed the assumption was wrong, and the honest
thing was to say so in the record rather than build the thing and let it fail in production. The
verification a feature rests on is worth as much scrutiny as the feature.

**The system was already producing the answer.** The callback had the proof in hand and discarded it.
Where a question feels unanswerable, the first move is to ask what the system already knows — the
signal often exists and is simply not kept.
