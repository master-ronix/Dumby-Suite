# UR-20261012-068 — The Dispatch Path Must Not Fail, and Must Not Lie

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.74` entry in `upgradation/change-log.md`).

---

## 1. The finding

Three faults sat on the same path — the one every command takes — and all three had the same shape:
**the framework told the member something untrue, or lost their command entirely, because a lookup
failed.**

1. **A failing read was reported as a refusal.** `assertCommandInScope` and `assertPersonaOwnsCommand`
   called the database **unguarded**. A fault propagated, the dispatch was refused, and the member was
   told `"…is not available in guild …"` — a permission error for an outage.
2. **One message, two meanings.** `CommandScopeDeniedError` carried a single message for two unrelated
   failures: a module being disabled, and the state being unreadable. The second was reported as the
   first.
3. **An advisory read could take a command down.** `moduleStanding` — which builds the `module` field of
   the SDK's `CommandContext` (UR-20261012-067) — called both `resolveCommandOwner` and
   `isModuleEnabledInGuild` **unguarded**. That field is *informational*: a module reads it to decide
   how to present itself. It is not a gate. Yet a fault in either read threw out of the context build
   and failed the command.

## 2. What changed

**The assertions fail closed, but say which it was.** Both are wrapped. On a fault they log
(`command-scope-state-unreadable`, `command-scope-owner-unreadable`) and throw
`CommandScopeDeniedError` with a new `scopeCause: 'state-unreadable'`. Failing closed is deliberate:
refusing a command is recoverable, running one for a disabled guild is not.

**The notice states the cause.** `NoticeReasonCode` gained `STATE_UNAVAILABLE`, and
`noticeReasonFromError` reads the error's `scopeCause`. A member now sees *"Could not check this
server"* — *"a fault on our side, not a permission decision"* — instead of a permission error they
would waste time arguing with.

**The standing fails open, to the conservative value.** Both reads are wrapped and logged
(`module-standing-owner-unreadable`, `module-standing-enabled-unreadable`), falling back to
`owner: 'main'` and `enabled: false`. The asymmetry with the assertions is the point: a **gate** fails
closed because a wrong "yes" is dangerous; an **advisory** read fails open to "claim nothing" because
the command is not the lookup's to lose.

## 3. Acceptance criteria

- **ACC-UR-068-1** — a throwing enablement read refuses with the unreadable-state notice, not a fake
  permission error; the dispatch resolves rather than throwing.
- **ACC-UR-068-2** — the notice contains "Could not check this server" and never "is not available in
  guild" on that path.
- **ACC-UR-068-3** — a throwing owner read in the standing yields `owner: 'main'`; a throwing
  enablement read yields `enabled: false`.
- **ACC-UR-068-4** — a Core module is `shared` and `enabled`, without reading either dependency.
- **ACC-UR-068-5** — 117 files, 1200 tests, 0 failures; coverage at or above the branch floor.

## 4. Recorded

**Two failure modes on one path, and they want opposite defaults.** A gate that fails open is a
security hole; an advisory read that fails closed is a self-inflicted outage. The distinction is not
which call it is, but whether the caller's decision depends on it. Writing that down is the fix;
the try/catch is the mechanical part.

**A defect class the type system cannot see, again.** The standing's two reads and the assertions'
two reads are all `(moduleId, guildId)` — two strings, so a swap typechecks. It is the same hazard
recorded in UR-20261012-067; it was hit again here.
