# UR-20261012-028 — OAuth Install Flow (Phase 1)

**Identity:** UR-20261012-028 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.32` entry in `upgradation/change-log.md`).

## 1. Summary

The operator chose the combined install flow ("Option A"): one journey in which the bot joins a guild
AND that guild is authorized for instant command-hiding. This record is **Phase 1 — the main bot**.
Phase 2 (personas, each a separate Discord application) is deliberately not built here; see §6.

## 2. The revision

- **The install link.** `/dashboard` gains *Add Dumby to your server*, pointing at
  `/auth/authorize?bot=1`. That leg mints the CSRF state, sets the cookies, and redirects to Discord
  with the install scopes — `bot applications.commands applications.commands.permissions.update
  identify guilds`. Requesting scopes beyond `bot`/`applications.commands` is what makes Discord
  continue into the full code grant; with `Requires OAuth2 Code Grant` on, the bot is added only
  after the code is exchanged, so the guild arrives already authorized.
- **The callback prefers the guild Discord returns.** A bot grant returns `guild_id` in the query;
  it wins over the cookie (which for an install holds only the default guild), so the token is
  stored against the guild the bot actually joined.
- **The token is keyed by (applicationId, guildId).** The endpoint is
  `/applications/{application.id}/guilds/{guild.id}/commands/…`, so a token belongs to the
  application that issued it, not to the guild alone. The store, the service and the dashboard
  status all move to the composite key.
- **Pre-change rows are adopted, not dropped.** A migration adds `applicationId` and re-keys the
  primary key. Rows written before it have no application id; `adoptLegacy` re-keys them to the
  running application at boot (a migration has no access to config), so an authorization granted
  before the change keeps working. A legacy row whose guild already has a real row is deleted
  instead, since re-keying it would collide. Adoption is non-fatal: a failure is logged, never thrown.

## 4. Acceptance criteria

- **ACC-UR-038-1** — `/auth/authorize?bot=1` requests the install scopes and leaves the guild to
  Discord's picker unless one is named.
- **ACC-UR-038-2** — the callback stores the token against the guild Discord returns.
- **ACC-UR-038-3** — tokens are held per (application, guild); another application in the same guild
  resolves none.
- **ACC-UR-038-4** — pre-change rows are re-keyed at boot, non-fatally.
- **ACC-UR-038-5** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 5. Rollout

Ordinary deploy. The migration re-keys the table; existing authorizations are adopted at boot, so no
re-authorize should be needed. **The code-grant toggle must stay ON for this flow**, and the plain
Add App invite is expected to fail while it is on — that is what this record fixes.

## 6. Risks & open questions

- **Phase 2 (personas) is not built.** A persona is a separate Discord application, so it needs its
  own OAuth2 credentials and its own authorization; the composite key added here is the groundwork.
  The operator reports that persona credentials arrive only through the one-time Twill registration,
  so the client-secret question is unresolved and deliberately not guessed at.
- **`guild_id` is only a hint in general**, but under a required code grant the exchange is the
  authority, and this flow runs only with the code grant on.
- **A legacy row is invisible until adopted.** If boot adoption fails, the dashboard reads "Not
  connected" and a re-authorize restores it.
