# UR-20261012-042 — The Registry Is the Trust Set

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.49` entry in `upgradation/change-log.md`).

---

## 1. Summary

§15.8 and finding #21 place build-signing public keys in the `signing_keys` registry — public keys
only, never a private one. Until now the verifier's trust set was a single deployment variable
(`BUILD_SIGNING_PUBLIC_KEY`), so rotating a key meant a redeploy and revoking one was not possible at
all. A2.2 recorded this as optional; the operator directed that every optional be built.

## 2. The revision

- **`PostgresSigningKeyStore.listActive()`** reads the active, non-revoked rows. It is **best-effort**:
  an unreadable registry returns `[]` rather than throwing, because arming happens on the boot path
  and must never be able to stop boot.
- **`armRegistryKeys(verifier, rows)`** registers them. A malformed row is **skipped**, not fatal — one
  bad key is that key's problem, not a reason to disarm the rest.
- **`armBuildProvenance` takes the registry rows** and arms config **and** registry together. The
  configured key is registered last so it wins on a same-id collision.
- **A registry-only deployment is now armed.** Previously, with no config key, the guard stayed off
  however many keys the registry held.
- **Boot is unchanged in shape:** one extra argument and one extra statement, no new branch.

## 3. Acceptance criteria

- **ACC-UR-052-1** — every well-formed registry key registers; a malformed row is skipped and the
  others survive.
- **ACC-UR-052-2** — empty ids and blank keys are ignored; an empty registry registers nothing.
- **ACC-UR-052-3** — a registry-only deployment is **armed**; config and registry arm together; a bad
  config key leaves the registry keys armed and does not throw.
- **ACC-UR-052-4** — neither source leaves the guard disarmed.
- **ACC-UR-052-5** — `typecheck`, `lint`, `format` green; corpus gates 27/27.

## 4. Risks & open questions

- **An operator can now arm the guard by inserting a row.** That is the point, and it is also why the
  registry is public-key-only: a row can enable verification, never forge a signature.
- **Revocation takes effect at boot.** `revokedAt` is honoured on the next start; a live rotation still
  needs a restart.

# UR-20261012-043 — The Dispatcher, Extracted

## 1. Summary

A2.1 was the last structural gap: a persona was **online with its commands registered** and still
silent when one of its own buttons was pressed. The dispatch path lived inside bootstrap's
`interactionCreate` closure, entangled with the router, the registry, the database and the logger, so
only the main bot had it.

system-map §11 settles what a persona is: "A Persona is not a lighter bot — it is *the framework
running again under a different identity*, sharing the same PostgreSQL primary, Redis, and queues as
the main bot." So it must dispatch as the main bot does.

## 2. The revision

- **`interactions/interaction-adapters.ts`** — three pure functions lifted out of bootstrap:
  `toCommandInteraction`, `toComponentInteraction`, `readDiscoverModalSubmission`. They read no
  configuration and close over nothing, so the main bot and every persona dispatch through the SAME
  code, and the behaviour is testable without a gateway.
- **`personas/persona-interaction-handler.ts`** — the dispatch itself, also lifted: adapt, hand to the
  registry, log an unhandled control. It **never throws**, because one bad button must not take a
  gateway listener down.
- **`PersonaRuntime` attaches the handler to each client BEFORE `login`**, so no early interaction is
  missed, and builds it per persona against that persona's filtered registry.
- **Bootstrap shrinks**: ~90 lines of inline adapter construction become three calls. The
  UR-20261011-018 guild-owner fix and the channel/permission mapping moved into the tested module
  rather than being rewritten.
- **Controls are additive**: with no handler supplied, a persona still starts and answers commands.

## 3. Acceptance criteria

- **ACC-UR-053-1** — the command adapter carries the name, user, guild, channel (NSFW and category),
  member roles, the admin permission bits actually held, and `isGuildOwner` (the UR-018 fix).
- **ACC-UR-053-2** — a guild-less interaction has a null `guildId`; absent optional members are
  omitted rather than set to `undefined` (the repo runs `exactOptionalPropertyTypes`).
- **ACC-UR-053-3** — the component adapter carries `values` only on a select menu, and
  `deferUpdate`/`showModal` only when offered.
- **ACC-UR-053-4** — the Discover modal reads its query only for the invoker it was minted for, and
  refuses every other modal.
- **ACC-UR-053-5** — the persona handler dispatches buttons and selects, ignores non-controls, logs an
  unhandled control, and **swallows a throwing registry**.
- **ACC-UR-053-6** — the runtime subscribes to `interactionCreate` **before** `login`.
- **ACC-UR-053-7** — `typecheck`, `lint`, `format` green; corpus gates 27/27.
