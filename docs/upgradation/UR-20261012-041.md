# UR-20261012-041 — Ownership, Not Allowlist

**Identity:** UR-20261012-041 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.48` entry in `upgradation/change-log.md`).

---

## 1. Summary

The operator challenged UR-20261012-037's registrar allowlist — "Dumby is a public platform, anybody
can register a persona themselves" — and the documents agree with them. **UR-20261012-037 built the
wrong mechanism.**

**What the records say.**

- **ADR-011:** registration is a *bring-your-own-identity* model — "the administrator supplies their
  own bot token and application in a bring-your-own-identity registration, Dumby hosts the resulting
  instance". "**Guild administrators** follow one documented path: register through the API."
- **ADR-008:** "a guild administrator supplies their own bot token and application, Dumby hosts the
  instance, and one persona is bound to exactly one server."
- **system-map §11:** "a **Persona** is a complete additional Discord Application whose token the
  guild administrator supplies (bring-your-own-identity), hosted and operated by Dumby".

So the registrar is the **guild administrator**, not the platform operator. An allowlist of platform
usernames gates the wrong party, and `PERSONA_REGISTRAR_AUTHORITIES=master_ronix` encodes a false idea
— that the operator registers personas on everyone's behalf.

## 2. The revision

- **Ownership is the gate.** `verifyApplicationOwnership` asks Discord
  (`GET /applications/@me`, `Authorization: Bot <token>`) which application a bot token belongs to, and
  requires it to be the one being claimed. Holding the token *is* holding the application, so this is a
  real proof — and it needs no operator in the loop, which is what bring-your-own-identity requires.
- **The registry becomes an OPTIONAL allowlist.** Enforced **only when it has entries**; empty means
  the operator has not asked for one, and registration proceeds on ownership alone. The previous
  fail-closed-on-empty rule was the defect.
- **`registrarAuthority` is what it always should have been** — a recorded identifier of who
  registered, not a permission.
- **The surface refuses before creating anything**, with a 403 that names the mismatch ("the bot token
  belongs to application X, not Y").
- **One control on the persona page.** The invite link now lives inside the info card, so the flow is
  "open info, read, invite" rather than a row of competing options.

## 3. Acceptance criteria

- **ACC-UR-051-1** — a token matching the claimed application is accepted; a different one is refused
  and both ids are named.
- **ACC-UR-051-2** — a refused token, an empty token, an empty application id, a missing id in the
  response, and an unreachable Discord are each refused without throwing.
- **ACC-UR-051-3** — an EMPTY registry leaves registration open; a CONFIGURED one is enforced.
- **ACC-UR-051-4** — the persona page offers one admin control, with the invite inside its card.
- **ACC-UR-051-5** — `typecheck`, `lint`, `format` green; the corpus gates unchanged.

## 4. Risks & open questions

- **Ownership verification costs one Discord request per registration.** Acceptable; it happens once
  per persona, ever.
- **A token with the wrong permissions still identifies its application** — `GET /applications/@me`
  needs no scope, which is what makes this a clean ownership check rather than a permission check.
- **The operator should leave `PERSONA_REGISTRAR_AUTHORITIES` unset** unless they deliberately want to
  narrow who may register.
