# UR-20261012-081 — The Persona Management Surface

**Freeze status:** Executed — 2026-10-14 (see the `v5.5.86` entry in `upgradation/change-log.md`).

---

## 1. The finding

Registration existed. Everything that makes a registered persona *liveable* did not.

The Twill persona surface carried `POST /twill/personas/register`, the registrar registry, three
detail reads, and the binding pair. There was **no way to change a persona, no way to revoke one, and
no way to replace a credential**. A persona could be created and then only ever bound or unbound. Its
bot token, once sealed at registration, was immutable for the life of the row — so a token Discord had
invalidated could not be replaced, and a persona whose secret leaked could not be recovered, only
abandoned.

That is the operator's own request, and it is a defect in the surface, not a missing convenience: a
credential that cannot be rotated is a credential that cannot be secured.

## 2. The mechanism

Two things were absent, and one thing was present but inert.

- **No mutation surface.** The routes were reads plus bindings. Nothing wrote to `persona_identities`
  after creation.
- **No presentation.** A persona had no presence, no status quote and no accent. The operator's
  requirement names all three: *"Status: discord bot status on profile like online/dnd/idle/invisible"*,
  *"Note: discord profile status quotes"*, *"Accent: hex accent of persona"*.
- **Registration was already credential-gated, and that is the right shape.** The operator requires
  that *"registration of persona via twill must only be done using sensitive credentials"*. It already
  is: `verifyApplicationOwnership` proves the applicant holds the application by the bot token before
  anything is created (UR-20261012-041, ADR-011). No change was needed, and none was made — the
  property is recorded here so a later reader does not "relax" it by mistake.

## 3. What changed

**Presentation (migration `20260101000051_add_persona_presentation`).** Three nullable columns —
`presenceStatus`, `note`, `accent`. Nullable because absent means "not configured", which is the honest
default and the state of every existing persona; nothing is backfilled, because there is nothing true to
backfill it with.

`presenceStatus` is deliberately **separate from `status`**. `status` is the persona's *lifecycle*
(active/retired); `presenceStatus` is the bot's Discord presence (online/dnd/idle/invisible). Conflating
them would make "retire this persona" and "set its status to idle" the same write, which is a
data-loss bug wearing a feature's clothes.

**The presence is applied, not stored.** A configured presence that nothing reads is a lie in a
column. `persona-runtime` calls `client.setPresence` **after login** — `client.user` does not exist
until the gateway is ready — non-fatally, like the emoji upload: a presence that fails must not stop
the persona. Activity type 4 is CUSTOM, which is what renders as the status quote beside the bot's name
rather than a playing/watching line.

**The operations.** `updatePersona`, `revokePersona` and `rotatePersonaCredentials`, each with the
validation in one place so every caller — route, CLI, a future dashboard — shares it.

- **Update** writes only the keys present. An omitted field is left alone; an explicit `null` clears a
  presentation field. An invalid value is refused **by name** (`Invalid accent: must be a hex colour
  like #7A5AF8 or #7AF`), because a 400 that says "bad request" is a support ticket.
- **Revoke** retires the persona, soft-deletes it, and **releases its bindings first**. A revoked
  persona that still held a module would leave that module occupied by a profile that no longer exists —
  uninstallable by anyone. Its application id becomes free to register again, which is the difference
  between "revoked" and "temporarily switched off".
- **Credential rotation** takes the *sealed* envelope: the surface holds the root key and seals, so the
  service never sees a plaintext credential. The two credentials are independent. `oauthClientSecret:
  null` **clears** it, dropping the persona to the bot-token fallback (Route B). A new secret resets
  `oauthVerifiedAt`, because a new application may not be the one that was verified.

**The credential is never logged.** The rotation records *which* credential changed and nothing about
its value — asserted in a test, because a log line is forever.

## 4. Acceptance criteria

- **ACC-UR-081-1** — a persona can be updated; only the fields present change.
- **ACC-UR-081-2** — an explicit `null` clears a presentation field.
- **ACC-UR-081-3** — an invalid field is refused by name, and nothing is written.
- **ACC-UR-081-4** — revoking retires the persona, soft-deletes it, and releases its bindings.
- **ACC-UR-081-5** — a bot token can be rotated; the digest and the sealed value both change.
- **ACC-UR-081-6** — an OAuth secret can be replaced, and cleared with `null`.
- **ACC-UR-081-7** — the credential value never appears in a log line.
- **ACC-UR-081-8** — registration still proves ownership by the bot token, and accepts the three
  presentation configs.
- **ACC-UR-081-9** — a configured presence is applied after login, non-fatally.

## 5. Recorded

**A credential that cannot be rotated is a credential that cannot be secured.** The surface could
create a persona and never repair one. Every operation added here is one an operator needs *after*
something has gone wrong — which is exactly when an absent route is most expensive.

**The validation belongs where every caller reaches it.** `toPersonaUpdateColumns` is exported and
takes the patch, so the route is not the only place the rules live. A rule enforced at the surface is a
rule the next surface re-implements, usually differently.

**A field nothing reads is a claim, not a feature.** The presence is applied at login and logged. The
alternative — a column that is written and never consulted — would have looked identical in a test and
been worthless in production.

**One operation was already correct and was left alone.** Registration's ownership proof already
satisfied the operator's "sensitive credentials only" requirement. Recording that, rather than
re-implementing it, is the point: the risk was never that the check was missing, it is that a later
change removes it.
