## 1. Summary

A systematic upgrade + migration pass over the live module framework that (a) migrates the visual
identity from the legacy blurple accent to **AMBER `#FFCA6D`**, (b) makes module theming, banners,
and identity **self-declared** by module developers with sane global fallbacks, (c) removes static
coupling from the command registry, dashboard, and marketplace, (d) rewrites the two broken
end-user surfaces (the queue command page and the hello module page) to a clean standard, and
(e) fixes the bccm rename-queue identity bug and hardens its arguments. This is an **upgrade +
migration**, not a greenfield build.

---

## 2. Motivation & the governing conflict (read first)

The directive's first clause (A.1) replaces the legacy "Burple" identity with AMBER `#FFCA6D` and
makes accent a per-module property (B.1/B.2). **This directly reverses a current normative
decision.** The corpus today fixes the accent as a *single, non-configurable* value — blurple
`#5865F2` — recorded in ADR-010 and stated in the interface specification, and the code enforces
it: `apps/main/src/shared/utils/components-v2.ts` exports `DEFAULT_ACCENT_COLOR = 0x5865f2`, and
the renderer/interface specs state modules "do not override the accent".

Per the project's own governance — *anything that departs from how a thing is already defined goes
through a formal Upgradation Request and the original trigger chain first* — this reversal **must
be recorded as a new ADR** (the ADR series is the binding record for design tensions) and the
interface/renderer specs must be amended to match. R1 and R2 below therefore carry an ADR
requirement, not just a code change.

## 4. Requested changes (by workstream)

### A. Theming & accent
- **R1 — Purge the legacy identity.** Replace the legacy "Burple" name and every associated hex
  value across the entire codebase and documentation with **AMBER `#FFCA6D`**: names, constants,
  theme tokens, comments, docs, and stray hardcoded literals. Code touchpoints include
  `apps/main/src/shared/utils/components-v2.ts` (`DEFAULT_ACCENT_COLOR`), the renderer, and the
  renderer/interface specs (`spec/request-layer/division-1-the-renderer-presentation-authority.md`,
  `_inbox/interface.md` frozen record) and the ADR that fixed the old value.
- **R2 — Record the reversal.** Raise a new ADR (ADR-015 candidate) superseding ADR-010's fixed
  accent, and amend the interface/renderer specs so accent is a per-module, overridable property
  with the AMBER default.

### B. Modules, banners & identity
- **R3 — Per-module banner + accent.** Extend `contracts/module-manifest.schema.json` and
  `apps/main/src/module-system/manifest.schema.ts` so each module may declare its own `banner` and
  `accent`. Fallback: DEFAULT banner asset + AMBER `#FFCA6D`.
- **R4 — Migrate existing modules.** Every existing module uses the DEFAULT banner — **except the
  dashboard**, which keeps its own.
- **R5 — Module logo icon.** Add an optional module logo `icon`; use it in the dashboard dropdown
  beside the module name; where absent, the DEFAULT WHITE icon.
- **R6 — Footer grammar.** Module-page footer renders **exactly** `<ModuleName> [<module_id>]` —
  no version, no developer credit, no extra tokens.

### C. Commands & bccm queue
- **R7 — Queue main page.** Rewrite the queue command's main page to a clean, consistent,
  well-structured layout.
- **R8 — bccm rename suggestion fix.** After a command is renamed via the bccm queue, the
  command-argument suggestion bars must show the **current** name, not the original.
- **R9 — Required argument.** Make the bccm command argument **required** (currently optional).
- **R10 — "Reset" argument.** Add a `Reset` argument to the bccm queue so queued changes can be
  reverted.

### D. Dashboard
- **R11 — Dynamic registration.** All core commands register **dynamically** under the dashboard
  module; remove every static hardcoded command list; the dashboard renders whatever is registered
  at runtime.
- **R12 — Schema-driven scale switch.** The D/M/C scale switch becomes **backend behaviour driven
  by a per-module, per-page schema declaration** — not a public/global utility. One page may be
  size D and another M, declared by the module developer.
- **R13 — Dropdown is dashboard-only.** The module-page-switch dropdown is a **dashboard-only**
  property; module developers have full freedom over their own flow actions and interactions, with
  no imposed grammar.
- **R14 — Core modules have no separate pages.** Only **STANDARD-tier** modules get separate
  dashboard pages (e.g. hello).
- **R15 — Module pages show only commands.** Module-specific pages show **only** the registered
  commands (as listed) — nothing else.
- **R16 — `/modules` rebuild.** Show only installed/enabled modules, each with its name and its
  icon behind the name, then two buttons `[ info ]` and `[ uninstall/disable ]`; then a DIVIDER
  with page-switch buttons in correct order (next / previous / first). Use a **user-private embed**
  for module info and the deactivation alert.
- **R17 — Hello page rebuild.** Rebuild the hello STANDARD-tier module page to a single clean
  layout: no duplicate credits, no stray version, coherent order consistent with R6.

### E. Marketplace `/browse`
- **R18 — Dropdown membership.** Modules are selected from the dropdown to install; only
  MARKETPLACE modules are visible there. An **unloaded STANDARD** module is also listed; an
  **installed** module is **not** in the dropdown.
- **R19 — Search bar.** Add a search bar (GRAY button, WHITE search icon) at the TOP of `/browse`
  that accepts a module NAME and filters both the page list and the dropdown options to the
  matching modules (the 25-option dropdown limit motivates this).
- **R20 — Main content.** The main space shows only available marketplace modules (ranking
  deferred), each with its logo icon behind the name and an interactive info button after the name.
- **R21 — Info display.** Show module info via a separate embed or a **private** sender embed
  (private recommended).

## 6. Migration paths (nothing breaks on upgrade)

- **Accent rebrand:** a migration that rewrites persisted accent tokens/theme configs from the old
  value to AMBER; reversible.
- **Module schema (banner/accent/icon/per-page scale):** additive optional fields with defaults, so
  existing manifests validate unchanged; a codemod sets the DEFAULT banner on all modules except
  the dashboard.
- **Dynamic command registration:** replace the static list with runtime registry reads; no data
  migration, but a behavioural verification on a pre-upgrade state.
- **bccm queue changes:** migrate queued rename entries to the new suggestion source; the `Reset`
  argument is additive.

## 9. Risks, assumptions & open questions

- **Assumption (flagged, per operating mandate).** The directive's "provided/attached" DEFAULT
  banner asset and DEFAULT WHITE icon were **not present** among the supplied artifacts (only the
  directive text was). R4/R5/R16/R20 depend on them; the implementation cannot complete without the
  two image assets.
- **Open question — accent vs ADR-010.** The directive makes accent per-module/overridable; the
  corpus fixes it. This request takes the directive as authoritative (it is the newer, operator
  instruction) and records the reversal as an ADR; if the reversal is not intended, A.1/B.1 must be
  re-read as "AMBER is the new single fixed accent, still not per-module."
- **Open question — marketplace ranking.** Explicitly deferred by the directive (§4, E.4); the
  interim is "available marketplace modules".
- **Scope risk.** The version-string purge (§4 constraint) touches shared renderer paths; it must
  not remove diagnostics that are not end-user surfaces.
