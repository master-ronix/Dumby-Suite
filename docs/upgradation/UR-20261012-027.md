# UR-20261012-027 — BCCM Command-Skip Observability

**Identity:** UR-20261012-027 · **Version:** 1.0 · **Date:** 12/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.31` entry in `upgradation/change-log.md`).

---

## 1. Summary

The first successful BCCM push (`bccm-batch-push-complete dryRun=false guilds=1 sent=1`) also
emitted `bccm-batch-command-skipped` with no readable detail: the command's name and reason were
structured fields, and the operator's log viewer renders only the message. UR-20261011-019 settled
that self-describing rule for other warnings; this one was missed.

## 2. The revision

- `bccm-batch-command-skipped` now carries the dropped name and its reason in the message string
  (`bccm-batch-command-skipped: <name> (<reason>)`) as well as in the fields.

## 3. What the warning means

`resolveCommandPayloads` drops a name for `invalid-name` and *keeps* one for `unresolved` (it sends a
minimal `{ name, description }` object). So the observed skip was an **invalid name**, not an
unresolved one. The desired set is `registered ∪ rename targets ∪ aliases`, and every first-party
manifest command name is valid — so the dropped name was a **guild rename or alias target** that is
not a legal Discord command name.

## 4. Acceptance criteria

- **ACC-UR-037-1** — the skip warning names the command in its message.

## 5. Rollout

Ordinary deploy. Log-only change.

## 6. Risks & open questions

- **Resolved in v1.1 by UR-20261012-032.** A rename/alias name is now validated at submit and
  rejected through a formal `INVALID_INPUT` notice, so it can no longer be accepted and then dropped
  silently at push. The original finding is kept below for the record.
- **A rename could be accepted and then silently dropped.** `isValidCommandName` is enforced only
  at push time; the `/queue` submit path (`bccm-effects.ts`) does not validate a `newName`/`alias`.
  The rename is then dropped at push and never happens. Rejecting it at submit is the correct fix but
  needs a notice reason code that does not yet exist (the union is fixed and `MODULE_ERROR` would
  misdescribe it), so it is deliberately left as a follow-up rather than half-fitted here.
