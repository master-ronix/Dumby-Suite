# UR-20261011-023 — New-Guild Deploy, Per-Guild Auth, BCCM Payload

**Identity:** UR-20261011-023 · **Version:** 1.0 · **Date:** 11/10/2026 ·
**Requester:** operator directive, formalised by Dumby Core Engineering

**Freeze status:** Executed — 2026-10-11 (see the `v5.5.25` entry in `upgradation/change-log.md`).

---

## 1. Summary

Three operator-reported problems, one of which was a genuine latent defect:

1. **A newly-installed guild had no commands at all.** Two causes. `NODE_ENV` defaults to
   `development`, and in development the command deployer registers **every command to `DEV_GUILD_ID`
   only** — so any other guild gets nothing (the operator's fix: set `NODE_ENV=production`). And even
   in production, the boot deploy only covers the guilds known *at that moment*; a guild joining
   afterwards got no per-guild commands until the next deploy, because the `GuildCreate` handler only
   wrote the guild row.
2. **Authorization was fixed to one guild.** The authorize link used `defaultGuildId`, so the operator
   could only authorize the dev guild — the consent screen never offers a guild, because the scope is
   user-level.
3. **`bccm-batch-put-failed`, `sent=0`.** The BCCM sent `desired.map((name) => ({ name }))` — a payload
   with **only a name**. Discord's bulk-overwrite endpoint requires a **`description`** on every
   CHAT_INPUT command, so the request was rejected. It was latent because the push had always been in
   dry-run; the first real send failed.

## 2. The fixes

- **`CommandDeployer.deployForGuild(guildId)`** registers one guild's commands, mirroring `deploy()`'s
  semantics (development: everything to the dev guild; production: the admin commands for the dev
  guild plus each module's commands where it is enabled). `registerKnownGuilds` now takes an
  `onGuildJoin` callback, and bootstrap wires it to `deployForGuild`, so a guild that joins gets its
  commands immediately.
- **Per-guild authorization.** `OAuthRoutesDeps.listGuilds` supplies the bot's guilds; `/dashboard`
  renders one row per guild, each with its own `/auth/authorize?guild=<id>` link and its own status.
- **The BCCM payload.** `resolveCommandPayloads(names, registry, onUnresolved)` resolves each desired
  name to its registered definition (`{ ...definition.data, name }`), keeping the requested name so a
  rename target still works, and falling back to a minimal valid object for an unresolved name. The
  bootstrap's `putCommands` uses it. The logic lives in `bccm-batch-push.ts` (covered by tests) rather
  than in `bootstrap.ts` (0% covered).

## 5. Rollout

1. Set `NODE_ENV=production` on the Railway service (the operator's step).
2. Authorize each guild from the dashboard once.

## 6. Risks & open questions

- A rename target is not a registry key, so it takes the minimal-object fallback; that is valid to
  Discord but carries the name as its description until the rename is registered.
- `NODE_ENV=production` also changes other behaviour (admin-tier registration, some feature gates), so
  it should be confirmed rather than flipped blindly.
