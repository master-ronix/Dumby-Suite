# UR-20261027-106 — Module Ownership

**Identity:** UR-20261027-106 · **Version:** 1.0 · **Date:** 27/10/2026 · **Requester:** operator directive

**Freeze status:** **Open — raised 2026-10-27.** It edits no frozen record.

**Basis.** The corpus states the rule; the tree breaks it. `REC-040` records the breach.

> "Modules — self-contained vertical slices owning commands, events, services, data, and config."
> — `spec/foundations/the-unified-modular-doctrine.md`, Table 2-A

> "Each module owns its own database tables (enforced by the repository pattern), its cache keys are
> namespaced, and its events are namespaced."
> — `spec/foundations/the-unified-modular-doctrine.md` §2.6

> "The commands that let a guild owner enable or disable features are themselves shipped as a module …
> loaded through the identical manifest contract, the identical DI container, the identical lifecycle
> hooks a third-party author would use."
> — `documentation/overview/the-philosophy.md`

What the tree holds today: every one of the eight packages under `packages/modules/` is two `.ts` files,
45–101 lines, one command whose whole body returns `{ page, data }` supplied by the host. Every
`services/`, `jobs/`, `events/`, `repositories/`, `migrations/`, `ui/`, `tests/` and `config/`
directory contains only `.gitkeep`. The implementation of all seven core modules — every page, every
button, every dropdown, BCCM, RBAC, the module views — lives in `apps/main/src`, including
`rendering/page-data.ts` (1,170 lines serving seven pages).

**A module is a plugin.** It is a separate application deployed onto the Dumby core base. Its code,
assets, services, jobs, tables and configuration are its own. The core base owns the loader, the
registries, the dispatch and the capability supply — and nothing that belongs to a module.

---

## 1. Objective and rationale

**Objective.** After this record lands, each module's implementation lives in its own package, the core
base carries only the mechanism that loads and dispatches it, and the doctrine's three sentences above
are true of the code rather than only of the documentation.

**Rationale.** Three concrete harms today:

1. **Ownership is unenforceable.** A module cannot be developed, tested, versioned, published or
   replaced independently, because its behaviour is not in its package. `packages/modules/dashboard`
   can be deleted and the dashboard keeps working — which means it was never a module.
2. **The isolation policy is untested.** MB-1's guarded container is a boundary with nothing behind it,
   because no module resolves anything. The capability model can only be proven by code that actually
   uses it.
3. **The marketplace is a fiction.** A third-party author has no reference implementation to copy,
   because no first-party module does what the manifest advertises.

---

## 2. Scope

**In scope.** `packages/modules/*` (the eight modules), `packages/swastik` (the authoring surface they
need), and the host-side mechanism that must remain: `module-system/loader.ts`, a new page registry, and
the capability supply.

**Out of scope.** Changing what a Core module may do; the specification's HTTP layout (`REC-036` …
`REC-038`); the frozen archive.

**Branch boundary.** `feature/dev` only.

---

## 3. The contract this needs

A module that owns its page must read its own data, and the lint boundary forbids a module importing the
core base. So the guarded container has to hand a **core module** a typed handle it can use without
importing internals. That is the design decision this record settles; everything after it is mechanical.

```
packages/swastik
  definePage({ id, tier, render(ctx, data) })      → a module-declared page
  ModulePageContext                                 → { guildId, applicationId, identity, standing }
  ModuleData                                        → the typed read handle, core/admin tiers only:
                                                       query(table, filter) · scoped to the module's
                                                       own tables by the guard, not by convention
```

Host side:

```
module-system/page-registry.ts   pageId → { moduleId, render }   (the loader fills it)
loader.ts                        registers mod.pages alongside mod.commands/jobs/events/tasks
rendering/page-data.ts           consults the registry FIRST; the built-in switch becomes the
                                 fallback for any page no module claims
```

A module declares `export const pages = [definePage(...)]`; the host never imports the module's code.

## 4. Extraction order

One module per pull, `dashboard` first as the reference. Each slice moves the page composition **and**
the interaction handlers it owns, and deletes the host-side copy in the same commit.

| # | Module | What moves | Depends on |
|---|---|---|---|
| 1 | `dashboard` | the page composition, the navigation order (install-rank sort), the accent and icon resolution | the contract in §3 |
| 2 | `health` | the page, the probe reads, the module inventory | slice 1 |
| 3 | `queue` | the page, the `guild_command_queue` read | slice 1 |
| 4 | `permit` | the page, the grant-resolution explanation | slice 1 |
| 5 | `persona` | the page, the binding and identity reads | slice 1 |
| 6 | `browse` | the page, the install dropdown handler, the catalogue read | slices 1, 3 |
| 7 | `modules` | the page, the install/disable controls, the BCCM enqueue | slices 1, 6 |

`hello-world` already carries its own command body and needs nothing.

---

## 5. Acceptance criteria

- **ACC-1** — for each extracted module, deleting its package breaks its page: a test asserts the page
  is unregistered when the module is absent.
- **ACC-2** — no module package imports `@workspace/dumby`; the lint rule already enforces this and
  must stay green.
- **ACC-3** — `apps/main/src/rendering/page-data.ts` shrinks by the extracted module's share each slice;
  the final state carries no module-specific page body.
- **ACC-4** — the guarded container is exercised: a core module resolves its data handle and is refused
  everything outside its capability set, with a test per case.
- **ACC-5** — CI green (Gate 1 typecheck, Gate 2 lint, Gate 3 format, Gate 4 unit tests, Gate 5 build)
  after each slice.
- **ACC-6** — the corpus gates stay green; `REC-040` flips to `match` only when every row of §4 is done.

---

## 6. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A module's page needs a host service the capability model does not expose yet | high | medium | extract the capability, not the module's dependency on the host: the data handle in §3 is the first such capability, and each slice may add one |
| Behaviour drift while moving code | medium | high | each slice moves code, not rewrites it; the page-data unit tests move with it and are the gate |
| The registry becomes a second dispatch path that drifts from the switch | medium | medium | the switch is deleted as the last slice lands; until then a test asserts registry-first, switch-fallback |
| A half-migrated tree is worse than none | medium | high | one module per commit, CI green each time; no slice leaves both copies live |
