# UR-20261012-069 — The Rest of a Disabled Module's Processing

**Freeze status:** Executed — 2026-10-12 (see the `v5.5.73` entry in `upgradation/change-log.md`).

---

## 1. The finding

§13.2 is explicit about what a disable does:

> **Standard** … a disabled Standard module's commands disappear from that guild's command list
> immediately and **its event handlers stop firing**.

Three of the four paths already honoured it. **Commands** fail closed at dispatch; **gateway events**
are gated (UR-20261011-011); the **instant command-access deny** and the **BCCM deregistration** are the
two-phase suspension. Two paths did not:

- **Queued work.** `QueueManager.registerQueue` took a processor and nothing else. The loader passed the
  module's jobs straight through, so a job enqueued for a guild that had disabled the module still ran.
- **The schedule.** `Scheduler.register` took a task and nothing else, so a module's cron kept firing
  regardless of whether any guild still wanted it.

Neither is currently exercised — no module declares `jobs` or `tasks` today — so this was a **latent**
hole: the framework promised termination it could not deliver the moment a module used either surface.

## 2. What the design had to respect

§13.7, the sentence that decides the shape:

> **Toggle vs. reload.** Toggling a module off or on is a state-table write on the order of
> milliseconds — it **never touches the module's loaded state, DI registrations, or event
> subscriptions**.

So a per-guild disable is **not** an unload. The module stays loaded — it can be enabled in guild A and
disabled in guild B at the same time — and the enforcement is a **gate at execution**, not a teardown.
This is why the fix is a gate and not a `worker.close()`.

## 3. The gate

Every unit of module processing that **names a guild** is gated per guild:

| Surface | Carries a guild? | Gated on |
|---|---|---|
| Command | yes (the interaction) | the guild |
| Gateway event | yes (from the event's args) | the guild |
| Job | yes, when the payload names one | the guild |
| Cron task | **no** — `execute()` takes nothing | whether *any* guild wants it |

A job with no guild, and a task with no owner, run as before. **All gates fail open** on a read error —
an unreadable state must not silently drop live work — with one deliberate exception: command dispatch
fails **closed**, because refusing a command is recoverable and running one for a disabled guild is not.

## 4. One enablement read

The per-guild standing was computed inline in `bootstrap()` and, separately, in the worker path. Two
implementations of one rule is a gate that denies what another allows. It is now
`module-system/enablement.ts` — `isModuleEnabledForGuild` and `isModuleEnabledAnywhere` — used by both
paths and by every gate.

## 5. A divergence found and closed

`isModuleEnabledInGuild` (the command router) short-circuits **Core** — §13.2, Core carries no disable
mechanism — added by UR-20261012-046. `isModuleEnabledForGuild` (the event gate) did **not**. A stale
disabled row could therefore drop a Core module's events while dispatch allowed its commands: the same
two-paths-two-answers defect, still live in the event gate. The shared read short-circuits Core and Admin
once, for everyone.

## 6. Acceptance criteria

- **ACC-UR-069-1** — a job whose payload names a guild that disabled the module is skipped.
- **ACC-UR-069-2** — a job for a guild that still wants the module runs; the gate is asked with the
  job's own guild and the queue's owner module.
- **ACC-UR-069-3** — a fleet-wide job, and a queue with no owner, are not gated.
- **ACC-UR-069-4** — a cron task whose module no guild wants does not execute; one still wanted does.
- **ACC-UR-069-5** — every gate fails open on a read error.
- **ACC-UR-069-6** — a Core module is enabled for a guild without consulting a row.
- **ACC-UR-069-7** — 117 files, 1197 tests, 0 failures; coverage 68.98% branch, no threshold error.

## 7. Recorded

**"Instantly terminated" and "never touches subscriptions" are not in conflict — the gate is how both
hold at once.** The subscription stays; the work does not happen. Reading §13.7 first is what stopped
this becoming a teardown that would have broken every other guild.

**A fleet-wide task cannot be per-guild suppressed, and pretending otherwise would be a lie.** A cron
task takes no guild, so the honest gate is "does any guild still want this module". A per-guild disable
of a module that other guilds still use must not stop their schedule.
