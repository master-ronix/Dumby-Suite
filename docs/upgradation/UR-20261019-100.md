> **v1.1 — the runtime value is now confirmed.** `MODULES_DIR=/app/baked-modules` at runtime (and in
> the Railway env example at the repo root). The image places the baked modules at `/app/baked-modules` —
> **outside any volume mount** — precisely so a `/mnt/modules` volume cannot shadow them
> (`apps/main/Dockerfile`). The open question in v1.0 is therefore resolved, and the baked path is
> viable.

## 1. Summary

Modules packed into the image (the first-party Core Command Surface) never pass through Swastik
promotion, so they have no `builds` row. This request defines, as its own change-set, how such
**baked** modules prove provenance under the D-4.10 floor. **UR-20261018-093 depends on it** — without
it, enabling the floor would refuse every baked module.

## 2. Business / engineering justification

The production build (`apps/main/Dockerfile`) runs
`node apps/main/scripts/place-first-party-modules.mjs /mnt/modules`, then
`COPY --from=builder /mnt/modules /app/baked-modules` and sets `MODULES_DIR=/app/baked-modules`. Those
modules have no `builds` row, so the UR-093 floor refuses them. The baked case needs a rule that is not
self-attesting — the expected hash must not sit beside the artifact on a writable volume.

## 3. Scope & impact

- **In scope:** the image build manifest; the loader's baked path; the `BAKED_MODULES_MANIFEST` env;
  `place-first-party-modules.mjs` (the production writer).
- **Out of scope:** Swastik promotion (UR-093 W1) and the signature ceremony (W5).
- **Audiences affected:** operators of self-contained images; the loader.

## 4. Current state (evidence)

- `apps/main/Dockerfile` bakes the first-party modules at **`/app/baked-modules`**, outside the volume
  mount, and sets `MODULES_DIR=/app/baked-modules`; the writer is `place-first-party-modules.mjs`.
- The loader scans **one** root: `MODULES_DIR` + the four `MODULE_VOLUME_NAMES` sub-directories
  (`swastik-loader.ts`). It does **not** scan `/mnt/modules` separately, so whatever root is set must
  be the one promotion targets.
- **The deployment docs conflict (DA-10):** the Railway deploy README says mount the volume at
  `/mnt/modules` so promoted modules survive redeploys; the Railway env example sets
  `MODULES_DIR=/app/baked-modules` and warns the `/mnt/modules` volume shadows the baked tree.
- The loader (UR-093) refuses a module with no `builds` row.

## 5. Proposed change (implemented)

1. `place-first-party-modules.mjs` writes a per-module `build-provenance.json` sidecar (marked
   `baked`) and a **`baked-manifest.json`** (`<volume>/<slug>` → artifact hash) at the module root.
2. The loader verifies a **row-less** module only against that manifest. The manifest path is
   **derived from `MODULES_DIR`** (`<MODULES_DIR>/baked-manifest.json`) unless `BAKED_MODULES_MANIFEST`
   overrides it — so it is always co-located with the modules the loader reads, and, because
   `MODULES_DIR` is the image layer, it is off the volume. The manifest keys are **relative**
   (`<volume>/<slug>`) and the hashes are over file **contents**, so the tree survives the Docker
   `COPY /mnt/modules → /app/baked-modules` unchanged (verified by a relocation run: write to root A,
   copy to root B, load from B).
3. **Precedence:** a `builds` row **wins**; a row whose hash disagrees with the module quarantines it.
   The manifest is consulted only when there is no row.
4. **Image-update / volume rule (open — §8).** The loader scans **one** root — `MODULES_DIR` and its
   four tier sub-directories (`MODULE_VOLUME_NAMES`: admin/core/standard/marketplace) — so **promotion
   must target that same root**. Where that root is a **persistent volume**, a promoted module can be
   stale after a new image, or a promoted `<slug>__<version>` can sit beside a baked `<slug>` — the
   loader discovers **both** and the duplicate manifest name aborts the boot. Where the root is the
   image layer, a new image replaces the modules wholesale. **Which applies is unresolved, because the
   deployment docs contradict each other:** the Railway deploy README mounts the volume at
   `/mnt/modules` "so promoted modules survive redeploys", while the Railway env example
   sets `MODULES_DIR=/app/baked-modules` and warns that a `/mnt/modules` volume **shadows** the baked
   tree (leaving zero commands). See audit finding **DA-10**.

## 6. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| `MODULES_DIR` overridden to the volume so the manifest is on a writable mount | Low | The image keeps the modules at `/app/baked-modules`; the env example pins `MODULES_DIR` there |
| Image update vs persistent volume mismatch | Medium | Adopt a stated rule (§8) |
| A volume-planted manifest downgrades a module | Low | Manifest is read from `MODULES_DIR` (image layer); a volume deploy leaves it absent |

## 7. Rollback / reversal plan

Unset `BAKED_MODULES_MANIFEST` and drop the manifest: baked modules then need `builds` rows, and the
baked path is inert. No other artefact depends on it.

## 8. Implementation plan & open questions

- **`MODULES_DIR` — confirmed** = `/app/baked-modules` (image, non-mounted). Closed.
- **Open:** the image-update rule (§5.4).
- **Verification (done in the audit sandbox):** `pnpm -C apps/main typecheck` clean; a writer→loader
  end-to-end run (`place-first-party-modules.mjs` into a temp root, then the loader reading its output)
  loaded both modules with an empty `builds` store; the loader's baked/downgrade/mismatch cases pass.

## 9. Acceptance criteria

- **ACC-UR-20261019-100-1** — A baked module with a matching manifest entry loads with no `builds` row.
- **ACC-UR-20261019-100-2** — A module absent from the manifest is refused even with a `baked` sidecar.
- **ACC-UR-20261019-100-3** — A `builds` row wins over the manifest; a disagreement quarantines.
- **ACC-UR-20261019-100-4** — `MODULES_DIR` is `/app/baked-modules` and the manifest co-locates with it.
